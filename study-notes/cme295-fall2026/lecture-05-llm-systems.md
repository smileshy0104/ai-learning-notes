## GPU与单位：算得快，不代表搬得快

### 1. 为什么用GPU？

PDF第3–12页。Transformer大量使用矩阵乘法，各输出元素可以并行计算，GPU的并行执行与专用矩阵运算单元适合这类任务。但模型还包含归一化、数据搬运、通信与采样，不是只有矩阵乘法。

补充例子：A为2×3、B为3×2，C=AB为2×2。每个C元素需要长度3的点积。精确数4×(3次乘法+2次加法)=20次标量运算；性能估算常用约2mnk=24 FLOPs，忽略边界项。FMA通常按乘与加计2 FLOPs，使用哪种计数应说清。

### 2. 四种指标不要混

| 指标 | 单位 | 回答什么问题 |
| --- | --- | --- |
| 运算量 | FLOPs | 一共做多少工作 |
| 算力／计算吞吐 | FLOP/s | 每秒最多／实际完成多少工作 |
| 内存容量 | bytes、GB、GiB | 能同时放多少数据 |
| 带宽 | bytes/s、GB/s、TB/s | 每秒能搬多少数据 |

小写s的FLOPs和大写S的FLOPS容易混，用FLOP/s最明确。硬件峰值依赖精度、稀疏条件等；不能不看条件就把一个TFLOP/s数字当所有算子的实际速度。

### 3. 参数多大，权重至少占多少？

```text
权重bytes = 参数数P × 每参数bytes
100 billion = 100×10^9
FP16或BF16每元素2 bytes
总计200×10^9 bytes = 200 GB ≈ 186.2645 GiB
```

GB按10^9、GiB按2^30。这个例子只算权重，不含梯度、优化器、激活、KV Cache、工作区和运行时开销。

所以“显卡容量超过权重大小”只是必要考虑之一，不等于训练或服务必然能运行。

### 4. HBM与SRAM的角色

- HBM（High Bandwidth Memory）：容量较大，相对片上存储访问更慢，用于权重和大量中间状态。
- SRAM：片上较小、较快的存储资源；实际硬件还区分寄存器、共享内存与缓存，不能把整片GPU汇总容量理解为每个线程块都能独占。
- Compute units：执行计算的单元；若数据供应不及时，再高峰值算力也可能闲着。

教学类比：HBM像大仓库，片上存储像操作台。不是让操作台放下整个仓库，而是合理分批取货，减少重复搬运。

### 5. “不够快”可能指不同事

相同模型计算，有时缺算力，有时缺内存带宽，有时缺跨GPU互联带宽，有时只是排队。先测瓶颈，再决定是换算子、加batch、分片还是减少生成轮数。

课件引用GPU规格作数量级示意，不意味着所有GPU都拥有相同容量或带宽；本笔记不把课件中的版本截图推广为当前市场事实。

## FlashAttention：在线Softmax为何不用存整张表？

### 1. 大矩阵在哪里？

PDF第14–29页。先只看一个注意力头：

```text
Q,K: n×d_k，V: n×d_v
S=QKᵀ/√d_k: n×n
P=softmax(S+mask): n×n
O=PV: n×d_v
```

标准分离算子可能把S写入HBM、再读出算P、再写P、再读出乘V。实际实现可以已有局部融合，课件是用于对比的朴素基线。

n=4096时，一张n×n矩阵有16,777,216项，假设2 bytes每项是32 MiB；n=32768时单张为2 GiB。这里只算一个头的一张表，还没乘batch与头数。

### 2. Softmax不是必须先保存整行

PDF第30–39页。对某个query，得到得分s₁,…,sₙ和value向量vᵢ：

```text
O = [Σ_i exp(s_i) v_i] / [Σ_i exp(s_i)]
```

分子是d_v维向量，分母是标量。可以逐个累加，最后相除。仍然要处理全部允许的key，只是不需要同时保存所有得分和权重。

例如s=[0,ln2,ln4]，v=[2,4,8]，未缩放指数权重为[1,2,4]：

```text
O=(1×2+2×4+4×8)/(1+2+4)=42/7=6
```

### 3. 为什么还要维护最大值？

PDF第40–47页。直接算exp(1000)会溢出。稳定做法是对已读部分维护最大值m、缩放后的分母ℓ和分子u：

```text
m_t = max(s₁,…,s_t)
ℓ_t = Σ_{i≤t} exp(s_i−m_t)
u_t = Σ_{i≤t} exp(s_i−m_t) v_i
O_t = u_t/ℓ_t
```

新得分到来时：

```text
m_new=max(m_old,s_new)
α=exp(m_old−m_new)
ℓ_new=αℓ_old+exp(s_new−m_new)
u_new=αu_old+exp(s_new−m_new)v_new
```

α把旧累积值从旧刻度换到新刻度。只缩放新项、不缩放旧项，会把不同比例尺的数混加。


交互图解（l5-online）见[对应章节源文档](../../content/collections/cme295/l5-flash.md)，构建网站后可在该章节操作。


上例三步为：(m,ℓ,u)=(0,1,2)、(ln2,1.5,5)、(ln4,1.75,10.5)，最终6。整体得分加1000，权重与结果都不变，稳定算法也不必计算exp(1000)。

第一项可直接初始化m=s₁、ℓ=1、u=v₁。完全被mask掉的行须单独约定，不能直接计算−∞−(−∞)；真实kernel需处理边界。

### 4. 从单个元素到GPU分块

实际FlashAttention按块读Q、K、V到片上资源，计算局部得分，逐行合并最大值与归一化统计，最终写回O。块内也有最大值与分子分母，再用同样的重缩放合并。

<div class="flow"><span class="chip">HBM读小块</span><span class="arrow">→</span><span class="chip">片上得分与累积</span><span class="arrow">→ 下一个块 →</span><span class="chip">写最终输出</span></div>

它减少HBM读写，不是完全不用HBM，也不是把整个n×n矩阵挪到SRAM。块大小受片上资源、线程调度和数据类型约束。

### 5. 反向为什么可能重算反而更快？

PDF第58–60页。反向需要注意力中的相关量。与其保存整个S、P再从HBM读回来，可以保存必要小统计并在反向分块重建。

额外FLOPs换更少内存搬运，整体可能更快；这是对特定大中间矩阵的取舍，不是“任何计算都重算更好”。通用activation checkpointing也有类似时间／空间权衡，但范围与实现不完全相同。

课件表的一个历史配置里，运算量66.6→75.2 GFLOPs、HBM读写40.3→4.4 GB、时间41.7→7.3 ms，约5.71倍加速。不是对所有长度、精度和GPU的承诺。

### 6. Exact具体指什么？

没有用稀疏或低秩近似替代原注意力，实数数学上结果相同；有限精度与求和顺序仍可能带来舍入差异，不保证bitwise identical。

标准密集注意力的计算仍随n²增长，FlashAttention主要消除大中间表和降低IO，不是将所有长上下文算术复杂度降为线性。版本演进还涉及调度和硬件适配，本讲聚焦共同核心。

### 理解检查

<details><summary>m变大时，为何分子分母都乘α？</summary><p>它们原来都用exp(−m_old)刻度，现在要统一改成exp(−m_new)。只改一边或只改新项会改变结果。</p></details>
<details><summary>不保存权重表，是否就不关注某些key？</summary><p>不是。所有未被mask的key仍参与计算，区别是按块累积而非保存整张表。</p></details>

## 训练内存：权重之外还要存什么？

### 1. 沿一次训练循环盘点

PDF第64–70页。模型不能只把权重放进显存就开始训练：

| 阶段 | 主要存储 | 规模与什么有关 |
| --- | --- | --- |
| 初始化 | 权重 | 参数数、数据类型 |
| 前向 | 激活与loss所需信息 | 层数、隐藏维度、batch、长度 |
| 反向 | 梯度、临时中间值 | 参数规模、计算图、算子实现 |
| 更新 | 优化器状态 | 算法与状态精度 |

FlashAttention减少注意力大中间量，不会自动消除所有FFN激活或优化器状态。

### 2. Adam为什么需要额外数组？

每个参数都维护梯度的一阶与二阶移动统计：

```text
m_t=β₁m_{t−1}+(1−β₁)g_t
v_t=β₂v_{t−1}+(1−β₂)g_t²
θ←θ−η m̂_t/(sqrt(v̂_t)+ε)
```

m、v与θ同形状；若θ展平为P维，两者也是P维。m̂和v̂为偏差修正后统计，课件为简图可能省略。AdamW还涉及解耦权重衰减，不能把这条简式当成完整训练器。

### 3. 一个明确假设的预算

教学设定：BF16权重2 bytes、BF16梯度2 bytes、FP32主权重4 bytes、FP32 m和v合计8 bytes。

```text
每参数：2+2+4+8=16 bytes
P=1×10^9 → 状态合计16 GB
P=100×10^9 → 状态合计1600 GB=1.6 TB
```

这里只称“模型训练状态”，不含激活和临时空间。具体实现未必保留FP32主权重，梯度也可能FP32，因此**16 bytes不是所有训练的普遍常数**。

### 4. 激活为什么跟batch和长度有关？

一个B×T×d的BF16隐藏状态需要2BTd bytes。B=2、T=4096、d=4096时，单个这样的张量64 MiB。

真实模型每层可能保存多个张量，不能只乘层数就当精确峰值；重计算、融合、生命周期、并行方式都影响同时驻留的数据。

减小microbatch、激活重计算、分片、并行都能减少某类内存，但可能付出计算、通信或吞吐代价。

### 5. 梯度累积是什么？

若单次只能处理2条样本，可做4次microbatch前后向再更新一次，累计相当于8条样本的梯度贡献（loss缩放需一致）。加入2个DP副本时，全局batch为2×4×2=16。

累积不意味着省掉权重、梯度和优化器；它主要降低单次激活规模，不保证与完整大batch在随机性和数值上逐位相同。

### 理解检查

<details><summary>m和v是否只是两个标量？</summary><p>不是，每个参数各有对应统计，因此是与参数同规模的数组。</p></details>
<details><summary>activation checkpointing能否直接把Adam状态省掉？</summary><p>不能。它针对前向中间量，优化器状态需要其他分片、精度或算法措施。</p></details>

## 数据并行与ZeRO：分数据，也分冗余状态

### 1. DP把什么分开？

PDF第71–74页。Data Parallelism把一个batch分成多个子批，各卡执行模型前向与反向。朴素同步DP各卡保留完整模型，再同步梯度，使更新后的副本保持一致。

不是每张卡自己训练出不同模型，最后把答案拼起来。需要通信归约和一致的优化器更新。

教学例子：两卡各处理相同数量有效样本，局部平均梯度为[2,4]与[4,0]，全局平均[3,2]。若有效token数不同且目标按token平均，不能总是无条件对各卡平均再平均，需正确加权。

### 2. ZeRO为什么仍属于分片数据并行？

ZeRO = Zero Redundancy Optimizer。各卡仍为自己的数据执行完整模型路径，但不长期重复保存所有训练状态；需要时收集相应参数，梯度与状态分摊到所属卡。

相比TP将单层矩阵运算拆到多卡，ZeRO主要处理**模型状态的冗余与生命周期**。实现也可以把两者结合。

### 3. 三阶段怎样分？

沿用前一篇明确假设：参数2P、梯度2P、优化器相关状态12P bytes；把FP32主权重与m/v合计归入最后一项。D为同一DP组卡数。

| 方案 | 每卡长期状态，理想化 |
| --- | --- |
| 普通DP | 2P+2P+12P |
| ZeRO-1 | 2P+2P+12P/D |
| ZeRO-2 | 2P+(2P+12P)/D |
| ZeRO-3 | (2P+2P+12P)/D |


交互图解（l5-zero）见[对应章节源文档](../../content/collections/cme295/l5-zero.md)，构建网站后可在该章节操作。


P=1 billion、D=4：每卡分别16、7、5.5、4 GB。别误读成整个集群只需4 GB；ZeRO-3理想状态总量仍是16 GB，只是不再每卡复制一份。

### 4. 为什么表里的数字不是峰值？

还需激活、通信bucket、预取、收集后临时完整层参数、算子工作区等。ZeRO-3会在需要时all-gather参数，并对梯度reduce-scatter或执行相应同步。

所以它不是“任何时候本卡都只接触四分之一参数”，也不是“显存严格按D无限下降”。分片粒度、预取和保留策略决定实际峰值与通信重叠。

### 5. 省内存的代价

更多通信、同步和调度；互联慢时可能损失吞吐。但模型完全放不下时，能运行本身就是首要目标。

DP与ZeRO、TP、PP并非四个互斥按钮。常见系统把它们配置在不同通信组中，具体如何组合要根据模型、集群拓扑和预算测量。

<details><summary>stage 3算出4GB，能否断言4GB显卡足够训练例子？</summary><p>不能。这只是理想长期状态，不包含激活、临时收集和工作区等峰值开销。</p></details>

## 模型并行：TP、PP、CP与EP分别切哪里？

### 1. 先用一句话区分

PDF第75–88页：DP分数据；TP分张量计算；PP分层／阶段；CP分上下文位置；EP分专家。它们是在不同轴上组织工作，不是算法优劣排名。

### 2. Tensor Parallelism：一层内部拆开算

看FFN：X为T×d，A为d×f，B为f×d：

```text
Y=GELU(XA)，Z=YB
A=[A₁ A₂]：沿列拆，各d×(f/2)
B=[B₁; B₂]：沿行拆，各(f/2)×d
Z=GELU(XA₁)B₁+GELU(XA₂)B₂
```

每卡算一部分隐藏通道，最后求和。GELU在各分块独立应用，不能随便把非线性越过矩阵求和。

教学简例：X=[1,2]，A=单位矩阵，B=[[1,2],[3,4]]，暂以恒等激活替代GELU。两卡输出[1,2]与[6,8]，相加[7,10]，与直接XB一致。这里仅验证分块代数，不是完整FFN模型结果。

多头注意力也可把不同头分配到多卡，再进行输出投影与通信。每层都有通信成本，互联质量很重要。

### 3. Pipeline Parallelism：把层串成生产线

前几层在GPU 0，中间层在GPU 1，后几层在GPU 2。激活向后传，反向梯度向前传。

如果只送一个microbatch，后面卡等待前面，前面卡又等反向，这些空闲区叫bubble。引入多个microbatch和合适前后向调度能减少空闲，但要管理激活与负载均衡。

补充理想模型：p个等时阶段，m个microbatch，仅前向流水需要m+p−1个时间槽，利用率 `m/(m+p−1)`。p=4时m=1为25%，m=4约57.14%，m=16约84.21%。这是简化前向模型，不是任意训练调度的精确效率公式。

### 4. Context Parallelism：同一长序列分位置

每卡负责一部分query位置，K/V块按通信策略交换，使每个query最终看到所有应见的key。

两个块时：卡A先处理Q_A与K_A/V_A，卡B处理Q_B与K_B/V_B；交换K/V后再处理另一块。各块结果要用在线Softmax的统计正确合并，**不能对各块独立Softmax后直接平均**。

因果mask仍需保留：早位置不能因跨卡交流而偷看未来。CP不是把长文切成互不通信的独立样本，也不消除密集注意力总算术成本。

### 5. Expert Parallelism：Token去找专家

在MoE中，专家FFN放到不同GPU；router决定token发往哪些专家，all-to-all dispatch后计算，再combine回原逻辑位置。

共享注意力部分可以采用其他并行；专家负载不平衡、热点、容量策略与通信可能成为瓶颈。只看总参数数，无法推断每步激活参数和实际吞吐。

### 6. 怎么组合？

教学组网：DP=2、TP=2、PP=2，三轴独立时总计8张GPU，不是2+2+2=6。EP／CP若复用某些通信组，不能机械把所有数再乘一遍，需看实际布局。

更多GPU可能带来更大容量和吞吐，也可能因每卡工作太小、流水线失衡、通信等待而降低利用率。成本要按完成任务的总GPU时间计算，不只看单步墙钟时间。

### 理解检查

<details><summary>把不同head放不同GPU，与把不同层放不同GPU有何区别？</summary><p>前者是层内部张量并行，后者是阶段式流水并行，通信内容与调度不同。</p></details>
<details><summary>CP各块输出能否直接平均？</summary><p>不可以。各块Softmax分母不同，需合并最大值、归一化和分子统计才能恢复全局注意力。</p></details>

## 推理瓶颈：Prefill、Decode与Roofline

### 1. 输入和输出Token不是同样的工作

PDF第89–96页对比：10,000 token输入、10 token输出，与10 token输入、10,000 token输出。

Prefill已知全部输入，可并行处理多个位置并构建KV；Decode要等待前一个采样结果才能继续，串行轮数多。通常长输出请求更受串行生成拖累，但长度本身不足以保证任何部署中谁必定更快：排队、上下文注意力、batch、硬件也影响结果。

Prefill并行不等于能看到未来；对decoder仍保持因果mask。

### 2. 延迟怎样拆？

课件约定Prefill包含产生首个token所需的初始计算：

```text
TTFT = T_queue + T_prefill
TTLT ≈ TTFT + (O−1) × TPOT
```

O为输出token数，TPOT在此是首token后各间隔的平均。O=1时没有后续间隔，不能再除O−1求TPOT。

教学例子：排队0.10s、prefill 0.40s，O=11，TPOT=0.03s：TTFT=0.50s，TTLT=0.80s。保持其他项不变，输出101个时TTLT=3.50s；真实TPOT未必恒定。

不同平台可能把首次decode另列，还会包含网络、流式缓冲、隐藏推理与用户可见输出边界，要先统一测量口径。用户感知的首字不总等于模型内部首token。

### 3. 吞吐与延迟不同

请求并发多时，batch可增加设备每秒总token数，却可能让某条请求排队更久。报告系统吞吐、单请求TTFT、TPOT及尾延迟，比单看“tokens/s”更完整。

价格截图说明课件时点常见输入／输出／缓存输入价差，不给出固定5倍或10倍的物理定律。计费还受产品策略影响，不能由价格直接反推FLOPs。

### 4. Roofline的三个量

PDF第97–102页：

```text
F：执行FLOPs
M：在所分析内存层次搬运的bytes
I=F/M：算术强度，FLOPs/byte
C：峰值计算吞吐，FLOP/s
W：内存带宽，bytes/s
可达吞吐上界 ≤ min(C, W×I)
理想耗时下界 ≥ max(F/C, M/W)
```

这是乐观模型，假定可有效重叠等，不计所有调度、网络和同步；预测上界不是实测保证。


交互图解（l5-roofline）见[对应章节源文档](../../content/collections/cme295/l5-latency-roofline.md)，构建网站后可在该章节操作。


教学硬件C=100 TFLOP/s、W=1 TB/s，ridge point为C/W=100 FLOPs/byte。I=10时带宽上限10 TFLOP/s，I=200时计算上限100 TFLOP/s。

图中斜线是W×I，水平线是C；没有把容量GB直接乘强度。带宽与容量不能混为一谈。

### 5. 为什么Decode常Memory-bound？

简化权重主导的线性层，P个权重、每权重2 bytes，每个序列一步约2P FLOPs。如果一个batch内b个序列共享这次权重读取：

```text
F≈2Pb，M_weights≈2P → I_weights≈b FLOPs/byte
```

小batch复用少，常受权重搬运限制；batch增大可提高复用和吞吐。但真实长上下文还要读KV、有其他算子，不能把I=b当精确全模型公式。

Prefill有很多位置一起运算，通常复用更多，优化得当更可能compute-bound。大batch decode或长上下文会改变瓶颈，所以不是“decode永远带宽受限、prefill永远算力受限”。

### 理解检查

<details><summary>Roofline算出10TFLOP/s，是否实测一定达到？</summary><p>不是。它是给定模型下的乐观上界，执行效率、同步和额外开销可能降低表现。</p></details>
<details><summary>把输入从1000增到10000，Prefill完全免费吗？</summary><p>不是，计算与KV存储都会增长；并行只说明不必像自回归输出那样逐个等待采样。</p></details>

来源：PDF第89–102页；延迟数字与简化Roofline例子为教学补充。


## KV Cache与分页：不重算，也不乱占空间

### 1. 为什么可以复用过去K与V？

PDF第104–109页。因果decoder中，已计算位置的表示不受后面新token影响。因此在模型、位置和前缀等条件不变时，可以保存每层过去K/V。

新token只算自己的Q/K/V，再用当前Q关注允许的历史KV。不必重跑全部前缀投影，但仍需读取和处理相关历史KV，不是上下文越长也没有额外代价。

为什么通常不存旧Q？未来位置用自己的新Q查询过去K/V，不需要过去query作为未来attention的输入。旧位置的输出已经算完。

### 2. 存多少？

对于等长batch、K/V维度相同的简化模型：

```text
KV bytes = 2 × L × B × T × H_kv × d_h × b_elem
```

2代表K和V，L层数，B活跃序列数，T缓存长度，H_kv是KV头数，不是query头数；b_elem为每元素bytes。不同长度时改为对各序列有效T求和。

L=32、B=1、T=4096、H_kv=8、d_h=128、b_elem=2，结果512 MiB。B=4时2 GiB；分页余量、元数据和其他模型状态尚未计入。

### 3. 三种“缓存”不要混

| 名称 | 保存什么 | 目的 |
| --- | --- | --- |
| 请求内KV缓存 | 当前生成已算前缀KV | 避免每个decode步重算 |
| 跨请求／轮次前缀缓存 | 完全匹配前缀的KV块 | 后续请求少做prefill |
| 答案缓存 | 完整响应 | 命中时可能不运行模型 |

课件缓存输入计价例子主要指第二类，不是说请求内每一步KV复用都会单独按缓存输入收费。

前缀复用必须匹配token、位置、模型版本及影响结果的配置；同义文本不代表KV相同。服务还要考虑租户隔离、缓存失效和隐私，不能让跨用户共享泄漏内容。

### 4. 朴素连续预留的浪费

若每条请求一开始都预留最大输入加输出空间，实际输出较短时空余被占住；请求完成回收后还可能留下不便放大块的孔洞。

保留但未用是预留浪费，非连续空洞是外部碎片，块尾未填满是内部碎片。它们相关但不是一个概念。

### 5. PagedAttention的块表

PDF第111–120页。把逻辑token位置划成固定大小块，每条请求维护逻辑块→物理块映射，物理块无需连续；attention kernel按块表读取。

```text
某请求：逻辑块0、1、2 → 物理块7、2、9
释放物理块2后，可供其他请求重新分配
```

不是把模型attention变成稀疏：逻辑上所有允许历史token仍要被关注，只是物理地址管理更灵活。


交互图解（l5-paging）见[对应章节源文档](../../content/collections/cme295/l5-kv-paging.md)，构建网站后可在该章节操作。


教学请求长度[5,9,13]，有效27 token；块长4时分配[8,12,16]，共36个token槽、尾部浪费9；块长8时[8,16,16]，共40槽、浪费13。一个token槽包含其对应层与KV信息，不是一个标量byte。

### 6. 块越小越好吗？

小块通常降低尾部浪费，却增加块表与地址处理成本，并可能影响kernel效率；大块反之。课件举16作为量级例子，不是所有后端固定最优值。

完成请求可以归还块，运行中按需追加；调度器仍须考虑总容量、并发、驱逐与重新计算。分页不等于拥有无限显存，也不会把KV数据本身压缩成更少向量。

### 理解检查

<details><summary>KV缓存是否等于不再计算attention？</summary><p>不是。省的是旧前缀的投影等重复计算，新Q仍要读取相关K/V并计算注意力。</p></details>
<details><summary>分页是否把较远的token自动丢弃？</summary><p>不是，它改变物理管理，逻辑关注范围仍由模型和mask决定。</p></details>

来源：PDF第103–120页；缓存容量、块表和碎片数字为教学构造。


## GQA与MLA：KV向量更少，也更短

### 1. 分页只管摆放，还能减少数据吗？

PDF第121–137页从“摆放更好”走向“向量更少”和“表示更小”。这些方法并非无条件叠加的三个开关：GQA和MLA有各自架构设计，需看具体模型。

### 2. GQA：多组Query共享K/V

H_q个query头，H_kv组key/value头，通常H_q可被H_kv整除：

| 架构 | H_kv | 关系 |
| --- | --- | --- |
| MHA | H_q | 每query头一套KV |
| GQA | 介于1和H_q | 每组query共享KV |
| MQA | 1 | 全部query共用KV |

不是把query头也删成H_kv个。每个query仍有自己的查询表示，只是去访问共享K/V。

相同层数、长度、head维度与精度下，KV缓存比例为H_kv/H_q。课件H_q=24、H_kv=2，保留1/12，节省91.6667%。这不是总模型显存或总推理时间节省91.6667%。

对前一篇配置，若H_q=32：MHA的KV为2 GiB，H_kv=8为512 MiB，MQA为64 MiB。每个数字只算KV，且不含分页余量。

### 3. 能直接合并预训练模型的头吗？

不能假定无损。共享K/V改变表达能力，通常需匹配训练或转换再训练。MQA并非普遍“不能用”或一定质量差；效果取决于任务和训练，是质量、速度、容量间的选择。

### 4. MLA：共享一个小潜变量

MLA标准术语为Multi-head Latent Attention，课件和口语可能省略head。它为每token构造共享低维KV潜变量，避免缓存各头完全展开的K/V。

下面是列向量约定下的**简化内容分支**：

```text
h_t: d_model×1
W_down: d_c×d_model
c_t=W_down h_t: d_c×1
W_upK: (H_q d_k)×d_c
W_upV: (H_q d_v)×d_c
k_t=W_upK c_t，v_t=W_upV c_t
```

各头可以有不同上投影，共享的是c_t，不是所有头得到完全相同的K/V。缓存c_t后，可以在需要时重建，或通过矩阵吸收避免每步把全部展开KV写回缓存。

### 5. 低维的教学手算

取h=[1,2]ᵀ，W_down=[1,1]，得到c=3。令W_upK=[1,2]ᵀ、W_upV=[2,−1]ᵀ，则展开k=[3,6]ᵀ、v=[6,−3]ᵀ。

这只是说明“一份潜变量生成不同K/V”；没有证明任意原始k/v都能无损压成一维。低维表达是训练出来的架构约束，不是通用无损文件压缩。

忽略位置分支时，传统内容缓存每token约H_q(d_k+d_v)元素，潜变量为d_c元素。实际MLA还涉及解耦位置编码与额外缓存，不能仅用d_c就当完整模型公式。

### 6. 为什么RoPE不能忽略？

简单非旋转内容项可以写：`qᵀ(W_upK c)=(W_upKᵀq)ᵀc`，这让查询变换后直接与潜变量交互。

但位置相关旋转插入计算，会限制简单矩阵吸收。DeepSeek式MLA使用解耦位置处理等设计；本讲图只讲共享压缩直觉，不应把完整实现描述成两层线性就结束。

MLA与[LoRA](../../content/collections/cme295/l3-lora.md)都有低秩投影的联系，但LoRA主要是权重增量参数化，MLA是注意力架构与缓存表示，目的和对象不同。

### 理解检查

<details><summary>GQA节省92%是否表示权重也节省92%？</summary><p>不是，这个比例特指同维度假设下的KV缓存，不包含query、FFN、其他权重与状态。</p></details>
<details><summary>MLA里的共享潜变量会让所有头完全相同吗？</summary><p>不会，各头上投影可不同。共享编码不等于共享全部展开表示。</p></details>

## 推测解码：先起草，怎样保持目标分布？

### 1. 为什么要一个Draft模型？

PDF第138–147页。目标大模型逐步生成慢，但已知一串候选后，可以并行计算各位置条件概率。先让便宜的draft连续起草k个token，再让target一次前向验证。

draft本身通常仍自回归，只是更便宜；target验证不是判断整句逻辑对错，而是按概率接受与校正。前缀的因果mask仍保持，各位置使用该位置之前的草稿条件。

### 2. 一个位置上的规则

在同一已接受前缀下，草稿分布D、目标分布T，先采x~D：

```text
接受概率 a(x)=min(1,T(x)/D(x))
```

- T(x)≥D(x)：一定接受。
- T(x)<D(x)：按比率接受，否则拒绝。
- 拒绝后从 r(x)∝max(T(x)−D(x),0) 重新采一个纠正token。

比例只对D能采到的候选求值；D=0的token不会由draft提出，却仍可通过残差分支输出。T=D时拒绝率0，不必去归一化全零残差。

### 3. 为什么不是拒绝后直接从T重采？

已接受分支已经贡献一部分概率质量。再次直接从T采会重复分配，必须从尚未被接受分支覆盖的残差里补齐。


交互图解（l5-speculative）见[对应章节源文档](../../content/collections/cme295/l5-speculative.md)，构建网站后可在该章节操作。


教学三候选：D=[0.6,0.3,0.1]，T=[0.3,0.4,0.3]。

```text
接受率：[0.5,1,1]
各token接受分支的无条件质量=min(D,T)=[0.3,0.3,0.1]
总接受概率=0.7，拒绝概率=0.3
正残差=[0,0.1,0.2]，归一化=[0,1/3,2/3]
最终质量=[0.3,0.3,0.1]+0.3×[0,1/3,2/3]=T
```

若错误地从T重采，最终变成[0.39,0.42,0.19]，不是目标。

### 4. 用公式证明

总拒绝概率Z为：

```text
Z=1−Σ_x min(D(x),T(x))
 =Σ_x max(T(x)−D(x),0)
```

对任意候选x：

```text
P(output=x)
= D(x)×min(1,T(x)/D(x)) + Z×r(x)
= min(D(x),T(x)) + max(T(x)−D(x),0)
= T(x)
```

这也解释接受率与分布重合质量的关系。可证明它等于1减总变差距离，但本讲不要求额外距离理论。

### 5. 从一个位置走到一段草稿

按顺序检验各草稿token，接受前缀一直保留；遇到第一次拒绝，输出一个残差采样token，并丢弃其后的草稿，因为条件前缀已变。

如果k个全部接受，target已有末尾位置的下一token分布，可再采一个bonus token。不是每次只要发生验证就无条件多领一个；bonus也不是没有输出头、采样或调度成本，只是通常省了一次完整target前向。

缓存要回滚拒绝后无效草稿的位置，否则后续条件不对。EOS、停止条件和长度限制也需一致处理。

### 6. 哪些条件下才叫保持分布？

D与T需指同一token空间、同一前缀下的实际归一化采样分布；温度、top-p等处理要与所证明目标一致，不能一边按截断分布采样、一边拿未截断原始概率做接受率。

数学分布相同不代表同随机种子逐token结果相同；有限精度、实现和采样策略也要验证。greedy的匹配式验证是另一种设定，不能随意套这条随机采样证明。

### 7. 会快多少？

draft必须明显便宜，且与target有足够重合。拒绝越早，后续草稿浪费越多；k太大也有更大验证和KV开销。

教学独立固定接受率α、每轮起草k个时，若拒绝后纠正或全接受后bonus都计1个，期望输出数：

```text
E[N]=1+α+α²+…+α^k
```

α=0.8、k=3时2.952；α=1时4。这个近似假设每位置接受率相同且独立，真实序列不必满足。

若草稿每步2ms、target验证20ms，这轮成本约26ms，假设普通target一步也20ms，速度比约2.27倍。不含其他开销，不能当实际跑分或保证。

### 理解检查

<details><summary>为什么target给某token概率更高就能直接接受？</summary><p>draft提出它的质量不超过target需要的质量，全部接受也不会超配；剩余质量由残差补齐。</p></details>
<details><summary>一次拒绝后，为什么不能继续采用后面的草稿？</summary><p>后面草稿按原先被拒绝token作为前缀生成，纠正后条件改变，需要重新开始或采用另有正确性的算法。</p></details>

来源：PDF第138–147页及字幕中的全概率证明；三候选、接受期望与时间例子为教学构造。


## 蒸馏与MTP：让草稿更便宜、更接近目标

### 1. 草稿好不好，不只看它小不小

PDF第147–149页。便宜却经常被拒绝的draft可能拖慢系统。除了速度，也要让草稿分布接近target，以减少无效提议。

课程用知识蒸馏连接两者：教师提供下一token软分布，学生学习它。对一个固定前缀，常用：

```text
KL(T∥D)=Σ_i T_i ln(T_i/D_i)
```

教师冻结时，其熵是相对学生参数的常数，最小化该KL等价于最小化教师软标签交叉熵。

注意这与[第四讲OPD](../../content/collections/cme295/l4-opd.md)讨论的reverse KL方向不同。蒸馏不是固定只有一个KL方向，也不能只看到“distillation”就断言采样前缀来自谁。

### 2. 软分布的教学例子

T=[0.75,0.25]、D=[0.5,0.5]：交叉熵约0.693147，KL约0.130812；当D匹配T时KL为0。

本例的接受率为min(0.75,0.5)+min(0.25,0.5)=0.75，匹配后为1。它展示改善分布匹配的动机，不证明任何训练loss单步下降都让所有前缀的接受率单调上升。

温度、训练前缀覆盖、草稿架构与硬件效率同样重要。教师接近不等于任务绝对正确；这层“质量”首先指接近被加速的target。

### 3. MTP是什么？

PDF第150–151页。Multi-Token Prediction在共享主干上设计多个预测头，分别学习预测后续第1、第2、…个token。课件展示并列头的概念图，实际模型还可能使用顺序模块或其他条件化结构。

若共享隐藏状态H为B×T×d，第j个线性头W_j为d×V，则logits_j为B×T×V，标签向后移j个位置。

```text
补充训练结构：L=Σ_j λ_j CE(logits_j, shifted_target_j)
```

不同头可有不同权重与有效位置mask。边界处没有后续标签时不能硬算loss，也不能把未来真实token偷偷送入推理输入。

### 4. 多个头不等于正确联合采样

从同一前缀同时预测t+1和t+2，第二个预测未必以实际采出的t+1为条件。因此独立采各头，不自动等于自回归联合分布：

```text
P(y₁,y₂|x)=P(y₁|x)P(y₂|x,y₁)
```

课件把额外头用作起草，主头／目标路径验证。若希望保持目标分布，还要使用符合相应条件的校正算法；并非把多个head的argmax直接拼接就完成无损加速。

### 5. 与独立Draft模型有什么不同？

共享主干可减少维护第二套模型和部分重复计算，但增加训练头与推理管理，效果仍需测量。MTP训练本身也可以是改善表示的训练目标，不仅仅是一种服务加速开关。

这里的“same draft and target model”应理解为模型内部自起草／验证的思路，不表示同一组多步预测分布天然等于普通next-token目标。

### 理解检查

<details><summary>第二个head预测了未来两步，能否省掉条件依赖直接输出？</summary><p>可以定义这样的生成器，但它不自动保持原自回归模型分布；要保持目标分布需验证与校正。</p></details>
<details><summary>蒸馏KL很小，能否忽略Draft的运行成本？</summary><p>不能。真正加速要同时满足草稿便宜、接受率足够高、验证与缓存开销合理。</p></details>

来源：PDF第147–151页；交叉熵数字、张量形状和训练loss为教学补充，不是某个具体MTP实现的复刻。


## 第五讲复习：先找瓶颈，再选优化

### 1. 回答开场的两个问题

PDF第152–156页。

| 方法 | 怎么放得下？ | 怎么跑得快？ | 主要边界 |
| --- | --- | --- | --- |
| FlashAttention | 不物化完整大注意力表 | 减少HBM搬运 | 不消除密集n²计算 |
| ZeRO | 分片长期训练状态 | 有时支持更大有效训练规模 | 通信与临时峰值 |
| DP／TP／PP／CP／EP | 不同轴分摊状态或激活 | 并行执行更多工作 | 互联、负载、气泡 |
| KV Cache | 需要额外KV空间 | 不重复计算旧前缀 | 长上下文读写仍有成本 |
| PagedAttention | 少预留浪费与外部碎片 | 更有效使用缓存、承载并发 | 块表开销与内部碎片 |
| GQA／MLA | 减少KV头或缓存表示大小 | 可能减少读写 | 架构与训练配套 |
| Speculative decoding／MTP | 不以节省所有缓存为主要目的 | 一轮target验证产出多个token | 草稿、接受率与校正成本 |

并不是所有方法都直接降低TTFT，有些主要改善decode吞吐或容量。服务质量还涉及排队与尾延迟。

### 2. 收到“模型很慢”，先问什么？

1. 是训练还是服务？单请求还是高并发？
2. 是放不下、TTFT高、TPOT高，还是整体吞吐低？
3. 输入／输出长度、有效batch、精度、模型结构是多少？
4. 显存分别被权重、训练状态、激活还是KV占用？
5. 计算、HBM带宽、跨卡通信中谁在等待？
6. 优化前后是否在同等质量、相同采样配置与负载下比较？

如果只是排队太久，加速attention不必然消除全部等待；如果是权重与Adam状态超容量，分页KV也不是对症方案。

### 3. 手算自测

<details><summary>100 billion参数、2bytes/参数，只算权重是多少？</summary><p>200GB，约186.2645GiB；不含训练或服务额外状态。</p></details>
<details><summary>s=[0,ln2,ln4]，v=[2,4,8]，注意力输出？</summary><p>指数比例1:2:4，输出42/7=6。得分整体加1000后不变，稳定在线算法仍可算。</p></details>
<details><summary>FlashAttention是否减少所有query-key配对？</summary><p>不是。它主要减少物化与IO，对标准密集注意力仍计算所需配对；因果mask依然生效。</p></details>
<details><summary>假设每参数状态16bytes、P=1B、4卡，ZeRO-1与3每卡多少？</summary><p>在本文2P参数、2P梯度、12P优化器相关状态假设下，stage 1为7GB，stage 3为4GB，均非完整峰值。</p></details>
<details><summary>TTFT=0.5s、输出11token、TPOT=0.03s，TTLT？</summary><p>0.5+(11−1)×0.03=0.8s。不是再加11个完整间隔。</p></details>
<details><summary>C=100TFLOP/s、W=1TB/s、I=10FLOPs/byte，Roofline上界？</summary><p>min(100,1×10)=10TFLOP/s，属于带宽受限区域，实测可能更低。</p></details>
<details><summary>GQA把24套KV改成2套，是否总显存省91.67%？</summary><p>只是在相同其他条件下KV数据减少91.67%，不能推广为总显存或总时间。</p></details>
<details><summary>Draft拒绝后直接从Target重采是否正确？</summary><p>一般不正确。已接受分支已有质量，应该从归一化正残差max(T−D,0)采样补齐。</p></details>
<details><summary>为什么多Token head不自动等价普通自回归模型？</summary><p>多个head可能条件在同一前缀，未来头未条件在实际已采出的前一个token，需要校正或明确定义另一种生成分布。</p></details>
