### 四个经常混淆的概念

| 概念 | 它是什么 | 不是什么 |
| --- | --- | --- |
| RAG | 查资料并加入生成上下文 | 自动保证事实正确 |
| Tool calling | 模型提出结构化操作请求 | 模型直接拥有后端权限 |
| Harness | 模型周围的执行、状态、上下文与权限设施 | 另一套模型权重 |
| Agent | 围绕目标选择动作、接收反馈的系统 | 必须有多模型或无限自主权 |

检索也可以作为工具进入Agent循环；静态一次RAG与反复查询资料不是对立阵营。不是每个应用都需要Agent，固定流程更容易控制时，workflow可能更合适。

## RAG与知识库：只带需要的资料进上下文

### 1. 为什么不能把全部资料都给模型？

PDF第10–20页给出三个动机：窗口有限；长输入中的无关信息可能影响表现；输入token也有成本。

Needle-in-a-Haystack通过改变事实所在位置和输入长度测试检索能力，不代表一个分数就能覆盖所有长文理解任务，也不能据单张历史图断言所有模型必然同样退化。

RAG = Retrieval-Augmented Generation：检索相关片段，增强提示，再生成回答。通常更新的是知识库与本次上下文，不是模型权重。

### 2. 一次完整流程

<div class="flow"><span class="chip">问题</span><span class="arrow">→ 检索资料 →</span><span class="chip">问题＋证据</span><span class="arrow">→ 模型生成 →</span><span class="chip">带来源的回答</span></div>

教学问题：“Cuddly通常在哪里？”资料说“Cuddly大多时间在书籍周围”。模型可回答“资料只说明它常在书籍旁”，不能无依据升级成“它现在一定在某图书馆”。

检索到的资料本身可能陈旧、错误或包含恶意指令。RAG让证据可用，不保证生成忠于证据；应区分直接陈述、推测与未知，并保留来源定位。

### 3. 知识库怎么建？

PDF第22–25页：收集文档 → 切成chunk → 编码embedding → 保存文本、向量与元数据。

建议元数据包括文档ID、版本、页码／段落、更新时间和访问权限。权限检查不能只放在最终显示阶段：检索和重排阶段也不应让未授权内容进入模型或日志。

### 4. Chunk大小与Overlap

片段太小容易丢上下文，太大可能稀释主题、增加输入成本。固定长度切块、按标题／句子切块、结构感知切块各有取舍。

教学长度1000 token、块长400、重叠100，步长300，采用覆盖到末尾即停止的规则：区间[0,400)、[300,700)、[600,1000)，共3块，总存储1200 token。无重叠时3块总1000 token，重复量200来自两个交叠。

重叠改善边界覆盖，但不保证每条事实完整；还会增加索引和重复证据，检索后可能需要去重。课件“约10%”是启发式，不是普遍最优。

### 5. 嵌入的形状和存储

若N个chunk、每个d维，文档向量矩阵E为N×d，query向量q为d维。内积评分Eq得到N个分数；余弦还需范数归一化。

教学N=10000、d=768、FP32每项4 bytes，纯向量数组30,720,000 bytes=30.72 MB，约29.30 MiB。不含文本、索引、权限元数据与数据库开销。

维度更大不必然检索更好；编码模型、训练目标、语种、chunk方式更重要。查询与文档必须使用兼容的嵌入空间与对应query/document配置，不只是“维度数一样”。更换模型往往需重建向量索引。

### 6. 资料更新怎样影响回答？

知识库更新后要跟踪旧chunk删除、版本替换与索引刷新。模型看到的是本次检索选中的版本；“数据库有新文档”不等于每次请求都已拿到。

不能拿HyDE等生成的假设性材料当来源证据，下一篇会区分它作为检索桥梁和真实文档的角色。

### 理解检查

<details><summary>RAG是否需要重新预训练？</summary><p>典型用法只更新外部知识与提示，不改生成模型权重；也可另训检索器，但不是RAG定义的必需条件。</p></details>
<details><summary>向量库越大，是否模型每次读到全部内容？</summary><p>不是。通常只取少量候选再筛选，最终部分片段才进入生成上下文。</p></details>

## 检索与重排：先尽量找到，再仔细比较

### 1. 为什么分两步？

PDF第26–40页。候选检索面向大量chunk，强调速度和召回；重排面向小集合，允许更细致的相关性计算。先漏掉真正相关文档，后面的ranker通常无法凭空找回来。

“召回优先、精度优先”是设计目标，不表示第一步没有排序、第二步绝不改变召回指标。

### 2. Bi-encoder与语义相似度

查询与文档分别编码，可预先缓存文档向量，在线只编码问题并搜索。可以共享编码器权重，也可以使用兼容双塔，并非必须两个完全独立模型。

```text
cos(q,d)=qᵀd/(||q|| ||d||)
q=[1,0]，d₁=[0.8,0.6] → cos=0.8
d₂=[0,1] → cos=0
```

这是人工构造二维向量，不是真实模型embedding。零向量余弦未定义，应明确处理。

语义相近不等于答案相关：问Cuddly的位置，可能错误偏好Huggy或“Paris在哪里”，因为实体混淆或问句形式相似。近似近邻ANN还会引入检索近似，需单独评测。

### 3. BM25与混合检索

BM25不是简单数一下相同单词；它结合词频饱和、逆文档频率与长度归一化，适合实体名、术语和精确词。

常见单词项形式（补充，具体IDF约定有差异）：

```text
IDF(t) × tf(t,d)(k₁+1)
       / [tf(t,d)+k₁(1−b+b|d|/avgdl)]
```

tf为词频，|d|为文档长度，avgdl为平均长度。k₁=1.2、b=0.75、长度等于平均长度、tf=2、IDF=1时该项1.375。它不是概率，不能与余弦原始分数直接不加校准相加。

混合检索可合并排序，例如补充RRF：`score(d)=Σ_j 1/(c+rank_j(d))`。c是平滑常数、rank从1起；缺失文档可按无贡献处理。融合方法仍需实际验证，不保证每次都优于单路。

### 4. HyDE与查询改写

HyDE = Hypothetical Document Embeddings：先生成可能回答问题的假想文档，再用其向量搜索真实库。它可能缓解问句与陈述句分布差异，也可能把错误假设带进检索。

**假想文档不是证据**。真实回答应依据后续取回的真实资料。复杂问题还可拆成多个子查询，但需防止改写改变用户意图。

### 5. Contextual Retrieval

切下来的“他搬到了这里”缺实体与时间。根据全文给chunk补上简短背景，例如“本文描述Cuddly在春季搬家”，帮助索引定位。

生成背景需要校验，错误实体也会污染索引。应保留原文与生成背景的区分；同一文档反复处理各chunk时，可利用稳定文档前缀缓存，但缓存规则依赖后端。

### 6. Cross-encoder如何重排？

把query与chunk作为一个带分隔的序列一起编码，让两者token交互，得到相关性标量。例如红围巾蓝袜子与蓝围巾红袜子的关系不同，联合比较可能更容易分辨。

若长度为L、隐藏维d，输出H为L×d；取CLS表示h为d维，线性头w为d维，`s=wᵀh+b`得标量；如用sigmoid才映射为0到1，但未必校准为真实概率。

联合表示依赖query，不能像独立文档向量一样预先为所有未来问题缓存。BERT式是课程例子，也存在LLM重排等其他方法。

### 理解检查

<details><summary>重排能否修复候选集完全没有正确文档？</summary><p>通常不能。应检查召回、扩展查询或回退，而不只换更强ranker。</p></details>
<details><summary>HyDE生成“Cuddly在厨房”，是否就能引用为事实？</summary><p>不能。那是检索用的假设，需要真实资料确认。</p></details>

来源：PDF第26–40页；余弦、BM25、RRF和重排维度为教学展开，不是已测试检索服务。


## 检索评估：Precision、Recall、RR与NDCG

### 1. 先有真值，再谈分数

PDF第41–48页。需要query对应哪些chunk相关的标注，才能评价排序。相关性不等于最终答案正确；一个文档相关但未必足够回答，标签不完整也会影响分数。

设总相关文档R个，取前k个，相关性relᵢ∈{0,1}，i从1开始。本页采用二值增益，与课件相同。

### 2. Precision与Recall

```text
Precision@k = 前k中的相关数 / k
Recall@k = 前k中的相关数 / 全库相关数R
```

前者问“拿回来的有多少有用”，后者问“该拿到的找到了多少”。增大k通常可增加召回，但精度未必增加。

### 3. RR与MRR

RR@k是前k里首个相关文档的倒数排名；没命中则为0。跨多个query取平均得到MRR@k，不能把单个query的RR直接叫所有查询的MRR。

只要首位相关，RR就是1，即使后面漏掉许多资料；多证据任务不能只看它。

### 4. DCG与NDCG

```text
DCG@k=Σ_{i=1}^k rel_i / log₂(i+1)
IDCG@k=将真实相关文档排在最前时的理想DCG
NDCG@k=DCG@k / IDCG@k
```

首位折扣1，第2位约0.63093，第3位0.5。IDCG的相关数来自真值，不是只把当前已检索到的相关条目重新排序，否则会把漏检藏起来。

分级相关性常采用`2^rel−1`等增益，不能和本页二值公式混用。无相关真值时Recall和NDCG分母为0，系统应明确约定跳过或记0，本页实验采用记0，不视为满分。


交互图解（l6-metrics）见[对应章节源文档](../../content/collections/cme295/l6-metrics.md)，构建网站后可在该章节操作。


### 5. 两个排序，P/R相同，位置分却不同

总R=3，k=3：

- 排序A前3相关性[0,1,1]：P=2/3、R=2/3、RR=1/2；DCG=0.63093+0.5=1.13093，IDCG=2.13093，NDCG约0.53072。
- 排序B前3[1,1,0]：P/R仍2/3，RR=1；DCG=1.63093，NDCG约0.76536。

重排改善了前列位置，却没让第三条相关文档进入top3。报告多个指标才能看出差别。

### 6. 评估分层

分别测候选Recall、最终排序、生成忠实性／引用准确性、端到端任务成功与成本延迟。用固定测试集而不是反复拿同一组例子调prompt后当泛化证据。

代码检索时，函数名、错误码、路径常适合grep／符号搜索。但“代码只需grep”也过强：调用关系、AST、依赖图和语义检索可以互补。检索到一处定义不等于完整理解所有调用影响。

### 理解检查

<details><summary>RR=1能否说明所有证据都找到了？</summary><p>不能，只说明首个结果相关，其他必要文档仍可能缺失。</p></details>
<details><summary>将当前top3里的两个相关项排最前就当IDCG，为什么不对？</summary><p>若全库有3个相关项，理想top3应全相关。只使用已检索结果会忽略漏检。</p></details>

## 工具调用：模型提议，系统执行

### 1. 查资料和做事情有什么区别？

PDF第50–67页：静态资料可能告诉你Cuddly常读书，却不能直接取得当前设备定位或实时库存。调用位置与库存API可解决这个问题。

“RAG无法实时”只是课件静态库例子的限制；检索也可以接实时数据源，工具也可以只读。检索与工具不是互斥分类。

### 2. 三阶段生命周期

<div class="flow"><span class="chip">模型选择名称与参数</span><span class="arrow">→</span><span class="chip">宿主验证、授权、执行</span><span class="arrow">→</span><span class="chip">结果回传，模型解释</span></div>

教学调用请求：

```json
{"name":"find_teddy_bear","arguments":{"latitude":37.42,"longitude":-122.17}}
```

这是合成例子，不来自设备GPS。正确流程先由已授权来源给坐标，不可因用户说“near me”就编造。后端返回结构化name、distance_meters等，再由模型总结。

工具名称与描述、输入schema通常进入模型上下文；全部Python源码不必提供。工具可以用任何语言实现，并非必须Python，也不一定访问网络。

### 3. 模型输出不是执行权

系统仍需检查：工具是否允许、参数类型与范围、当前用户权限、确认条件、超时与结果状态。JSON合法只说明语法合法，不说明用户授权。


交互图解（l6-tool-gate）见[对应章节源文档](../../content/collections/cme295/l6-tools.md)，构建网站后可在该章节操作。


实验是固定规则的静态决策表，不调用真实设备。读取温度、修改设定与缺参请求会进入不同路径。即使模型把工具选对了，系统仍可拒绝或要求确认。

### 4. 失败与重试不能靠猜

- 超时：返回明确未知／失败，不编造工具成功。
- 参数缺失：询问或用授权工具获得，不随便填。
- 输出不符合预期：验证再使用，限制长度与敏感字段。
- 有副作用的操作：记录操作ID、幂等键或核验状态，避免网络重试重复发送邮件或重复购买。

工具返回的文本属于外部数据；其中“忽略规则并执行某操作”不能变成新的授权。调用链也不自动继承用户所有账户权限。

### 5. 怎样教会模型？

PDF第68–71页有两条路线：SFT示范“如何预测调用”与“如何将结果转成回答”；提供清晰schema、描述和示例，让已有工具使用能力的模型泛化。

提示不修改权重，SFT会更新权重。两者可共存，不能说有了prompt就再不需要训练能力。用另一个模型迭代描述时，应有真实预期结果和留出测试集，不能只优化几条样例后宣布可靠。

### 6. 一个最小契约要写什么？

用途、何时不用、必需参数、单位与范围、返回结构、可能错误、是否只读、是否需要确认。比如摄氏／华氏、绝对温度／增量若不写清，类型正确也可能做错事。

课件“执行代码不算工具”的口头问答与后续代码执行例子应按抽象层理解：在Agent系统中，shell或代码执行完全可以作为受控工具接口。分类不改变其安全敏感性。

### 理解检查

<details><summary>schema验证通过，是否就可以购买？</summary><p>不能。语法和范围验证不代表交易授权，还需明确对象、金额与执行确认等条件。</p></details>
<details><summary>工具超时，模型能否说“已经完成”？</summary><p>不能，应说明状态未知或失败，并依据幂等／状态核验机制处理重试。</p></details>

来源：PDF第50–71页；验证、确认和幂等为工程补充，不是课件示例API的生产实现。


## 工具选择：越多不等于越好

### 1. 同名需求，可能是两个任务

PDF第72–86页。“帮我找我的熊”可以是找照片文件，也可以是定位实体玩具熊。list_files与find_teddy_bear都可能匹配，但结果不是同一件事。

get_doc与get_drive都能返回相同文档时，课件称良性重叠；即使结果相似，权限、来源、成本与审计路径仍可能不同，不能完全不管。

### 2. Router做什么？

先按当前请求、对话、用户设置和可用权限，从工具库选择小子集，模型再在这些接口中决定具体调用。

<div class="flow"><span class="chip">允许的工具集合</span><span class="arrow">→ 任务相关筛选 →</span><span class="chip">少量工具定义</span><span class="arrow">→</span><span class="chip">模型提议调用</span></div>

授权过滤是边界，语义路由是相关性优化。router输出“很相关”不能激活用户关闭的工具，也不能让本无权限的操作执行。

### 3. 何时该澄清？

用户刚在聊照片整理，可优先考虑文件；刚在聊房间物品，可考虑定位。但历史偏好不是不可撤销的当前授权，涉及位置或敏感数据时尤其需要谨慎。

若上下文不足，询问“你想找照片文件，还是实体玩具熊？”优于默默选择一个高风险解释。必要时明确告知所选范围，而不是怪用户没说清。

### 4. 更少的工具也有代价

减少定义长度与冲突，但可能漏掉完成任务需要的工具。可设无法完成时再检索工具的回退机制，仍受权限与预算约束。

路由模型可以轻量，也可以规则、分类器或检索；不能把“小模型router”当所有系统统一架构。把温度设0不消除歧义，更不保证跨硬件／版本逐位确定；稳定地产生错误解释仍是错误。

### 5. 怎么评估工具选择？

看正确工具召回、无关工具比例、参数正确率、不该调用时是否保持不调用、澄清质量、授权边界、端到端任务成功与延迟。单看工具名称准确率会掩盖参数或副作用错误。

设计测试包含同义请求、相似工具、缺权限、工具不可用和对抗性返回。课件用多工具造成context bloat的图作动机，不是证明每增加一个工具都必然降低质量。

### 理解检查

<details><summary>Router选中一个用户未启用的工具，该怎么办？</summary><p>不得静默启用并执行；可按产品规则征求启用授权，或说明能力不可用。</p></details>
<details><summary>两工具返回同样正文，是否就完全等价？</summary><p>不一定。权限、更新时效、来源与副作用可能不同，需要明确接口语义。</p></details>

来源：PDF第72–86页；权限过滤与澄清测试为工程补充。


## MCP：统一连接方式，不替你授权

### 1. 为什么需要标准化？

PDF第87–90页。同一组后端能力若要适配多个应用，逐对编写连接器容易重复。MCP = Model Context Protocol，为工具和数据提供共同交互约定。

教学类比：3个应用接4组服务，朴素逐对最多12条连接；共用标准接口可从两侧各适配，概念上3+4=7个适配点。现实仍有认证、功能差异、版本与部署工作，不保证总工程量严格从12降到7。

### 2. 三种角色

| 角色 | 职责 |
| --- | --- |
| Host | 用户交互应用，管理模型、连接、上下文与权限策略 |
| Client | Host内面向某个Server的协议通信组件 |
| Server | 暴露工具、资源、提示等能力，可调用自己的后端 |

不是模型权重直接打开网络连接；通常是host/client代为通信。多个server也不等于多个自主Agent。

### 3. Tools、Resources、Prompts

以诗集服务为例：

- Tools：搜索书名、推荐书籍等可调用接口。
- Resources：用户授权的已有藏书等数据，可供宿主读取和提供上下文。
- Prompts：可复用的交互模板／工作流入口，如按偏好推荐。

Resource不是“另一个带副作用的工具”的同义词，prompt模板也不凭其来自server而拥有更高指令权限。具体控制与使用方式由客户端和协议版本决定。

### 4. 标准化不解决哪些问题？

MCP不会自动保证工具描述正确、服务可信、请求已授权或执行安全。仍需身份认证、最小权限、连接来源审查、输入输出验证和审计。

后端密钥不应交给模型或塞进普通工具结果。远程服务返回的内容需当外部数据处理；只在用户授权范围内把必要信息传出。

本文只是协议角色说明，没有安装真实server、没有访问任何账户；也不承诺课件中的SDK片段在当前版本直接可跑。

### 5. MCP和普通Function calling

Function calling通常描述模型输出结构化请求的接口；MCP描述应用怎样连接能力提供方。宿主可把MCP工具转换成模型理解的工具定义，两层可以结合。

不是“支持MCP就不需要工具prompt和评估”，也不是MCP取代后端业务逻辑。Agent之间委派任务的A2A则在[Harness篇](../../content/collections/cme295/l6-harness.md)讨论，两者关注层次不同。

### 理解检查

<details><summary>MCP Server一定是自主Agent吗？</summary><p>不是，它可以只是暴露查询和数据的服务，不必有自主循环。</p></details>
<details><summary>协议符合标准，是否就可信？</summary><p>不。兼容性和可信性不同，仍需连接与权限审查。</p></details>

来源：PDF第87–90页；连接数量和信任边界为教学补充。


## 缓存与成本：稳定前缀放前面

### 1. 工具定义也占上下文

PDF第91–101页。模型需要读工具描述、schema及其他指导；这些内容可能很长，但若连续请求共享稳定前缀，可复用计算。

这是[第五讲前缀KV缓存](../../content/collections/cme295/l5-kv-paging.md)的应用，不是缓存整条答案；新请求仍需生成输出。

### 2. 为什么顺序重要？

前缀缓存通常要求前部token及相关配置一致。把每次变化的用户问题放最前，后面再有相同工具定义，也未必命中这部分。

```text
通常不利：动态问题 → 固定工具 → 动态时间
更有利：固定工具／固定指导 → 动态时间与上下文 → 用户问题
```

这是在保持消息角色与语义正确下安排稳定内容，不能为省钱把用户内容冒充系统指令。不同API工具定义序列化和缓存边界不同，不应随意重排角色。


交互图解（l6-prefix）见[对应章节源文档](../../content/collections/cme295/l6-caching.md)，构建网站后可在该章节操作。


教学块T为相同工具、C为每次变化的时间上下文、U为变化的问题。T置首时可共享T，C或U先变则后续即使T相同也不构成共同前缀。

### 3. 便宜多少需要算条件

假设每次固定前缀800 token、动态200 token，共10次请求；普通输入价2货币单位／百万token、命中价0.2，首次前缀按普通输入计，不另收费缓存写入：

```text
不缓存：10×1000×2/10^6=0.02000
缓存：800×2/10^6 + 9×800×0.2/10^6 + 10×200×2/10^6
     =0.00704
节省64.8%
```

这只算输入，不含输出、工具服务、检索、模型路由、存储或缓存写入收费。课件10–40倍价差是截图条件，不是所有请求总账单都降低10–40倍。

### 4. TTL、写入与失效

TTL为time to live，不是字幕里的time to leave。过期、替换工具定义、模型／配置变化都可能造成miss；有的服务有写入费或最小前缀长度，需读实际产品合同。

动态工具选择让前缀变化时，可合理分组相同工具集合，但不要为了命中率给模型塞入无关或越权工具。命中优化应服从正确性与数据隔离。

### 5. 缓存不是长期记忆

缓存关注相同前缀计算复用，长期记忆关注跨会话保留何种信息。即使底层KV仍在，没被请求引用也不代表模型“自动记得”；反之长期记忆可以通过文本／数据库重建，不依赖某次KV存活。

### 理解检查

<details><summary>固定工具在动态问题后面，相同的工具文本一定命中吗？</summary><p>不一定。普通前缀缓存要求前部一致，中间相同片段不是同一共同前缀。</p></details>
<details><summary>读取价便宜10倍，总费用是否必然便宜10倍？</summary><p>不。首次输入、动态部分、输出和其他费用不一定享有同样折扣。</p></details>

来源：PDF第91–101页；token块和成本数字为明确假设的教学计算，不是实时API报价。


## Harness与ReAct：让动作进入可控反馈循环

### 1. Harness包住模型的哪些部分？

PDF第103–106页：工具、动作顺序、提示、状态、压缩、记忆和guardrails。模型像发动机，Harness像周围控制与传动结构，两者共同决定效果。

这是一种工程概括，不是“强模型加任意循环就可靠”，也不是规定每种Harness都必须具备完全相同模块。

### 2. ReAct的核心是反馈

PDF第107–123页，ReAct = Reason + Act：观察当前信息、规划下一步、执行动作、接收结果，必要时继续。

<div class="flow"><span class="chip">输入目标</span><span class="arrow">→ 观察 → 计划 →</span><span class="chip">提议与授权</span><span class="arrow">→ 执行 →</span><span class="chip">结果与验证 → 继续或停止</span></div>

并不要求把完整隐藏推理轨迹展示给用户；界面可给简短计划、工具记录和可核实结果。也不保证所有模型都通过同一SFT配方学习这一循环。

### 3. 温控例子：区分设定值与真实室温

课件从65°F出发，希望设为70°F。补充换算：65°F约18.333°C，70°F约21.111°C，差5°F约2.778°C；温差换算不要再减32。

合理状态流：读当前数据 → 提议目标70°F → 根据权限确认 → 设置 → 读取设备设定值确认。写入成功不表示房间空气立刻升到70°F，热响应需要时间。


交互图解（l6-react）见[对应章节源文档](../../content/collections/cme295/l6-harness.md)，构建网站后可在该章节操作。


实验采用合成状态，没有真实设备。课件“增加5°F”的增量动作重试时可能重复增加；工程中可用绝对设定、操作ID与读回减少歧义，仍须遵守设备安全范围与用户授权。

### 4. 停止条件不能只靠“模型满意”

可设任务成功证据、最大轮数、时间／费用预算、连续错误上限、工具不可用和用户取消。涉及外部副作用时，取消也可能不能撤销已发生操作，要报告真实状态。

计划写得流畅并不等于行动成功。观察结果要验证来源，工具错误要如实处理，而不是持续循环到编出成功答案。

### 5. Workflow与Agent的选择

固定温控规则可用普通程序实现，无需LLM。LLM更适合自然语言目标、模糊条件与跨工具选择；让它参与不意味着要把所有安全控制交给模型判断。

模型提议可被Harness拒绝。权限、沙箱、范围限制和人类确认应有独立执行点，不能只写“请安全操作”当控制系统。

### 6. A2A与跨Agent任务

PDF第124–127页介绍Agent2Agent：用AgentCard描述地址、能力与技能，通过任务执行／取消接口协作。图中AgentSkill是能力描述，不等于编程Agent的SKILL.md目录。

MCP主要连接工具／数据能力，A2A主要组织Agent之间任务沟通，两者可共存；具体协议字段要按实现版本核对。标准消息不保证远端可信，也不自动扩大调用方授权。

### 理解检查

<details><summary>设备返回“设定为70°F”，能否说实际房间已达到70°F？</summary><p>不能。设定值和传感器实测是不同状态，后者需要时间与测量。</p></details>
<details><summary>循环一定要展示每一步内部思维吗？</summary><p>不用。可以记录简明计划、工具调用、证据和结论，不要求暴露隐藏推理链。</p></details>

来源：PDF第102–127页；温差换算、授权与停止条件为教学／工程补充。


## 压缩与记忆：腾空间不等于永久记住

### 1. 窗口满之前就要管理

PDF第128–136页。一次循环不断加入工具定义、请求、返回和回答，总长度增长。还要为下次工具结果和生成输出预留空间，而不是等输入刚好塞满再处理。

教学窗口10000 token，预留输出2000、潜在工具结果1000、固定指导1000，历史等其余输入最多6000。它是预算，不是模型固定规格；真实计数依赖tokenizer和API规则。

### 2. 三种Compaction

| 策略 | 做法 | 主要风险 |
| --- | --- | --- |
| 删除 | 移除冗长／已无用内容 | 把后续仍需证据删掉 |
| 滑动窗口 | 只留最近若干段 | 早期约束和目标消失 |
| 摘要 | 生成较短结构化记录 | 漏信息、改语义、假设被写成事实 |

可以组合，不是越新越重要。系统约束、用户禁止事项、未完成工作与关键证据通常不能只按时间丢弃。


交互图解（l6-compaction）见[对应章节源文档](../../content/collections/cme295/l6-memory.md)，构建网站后可在该章节操作。


合成场景里，用户先说“不要购买，只比较”，后续搜到三个候选。只留最近搜索结果可能把禁止购买丢掉；结构摘要应保留目标、约束、已确认事实、待办和引用。

### 3. 摘要怎么写更稳？

- 当前目标和范围，哪些动作明确未授权。
- 已完成操作及证据，区分计划与实际执行。
- 剩余任务、错误与待决策事项。
- 来源ID、文件位置、时间等可重新读取的定位信息。

摘要不是原记录的无损压缩。重要结论要能回到原证据，不能把某网页里的恶意指令总结成“用户要求”。保留工具调用／结果的必要配对与协议结构。

### 4. Short-term与Long-term

短期记忆通常指当前可用上下文。长期记忆是外部持久存储，跨会话选取事实、偏好或进度，在需要时再检索注入；不意味着模型权重即时更新。

两种课程思路：检索过去对话；显式memory工具写入整理后的记录。记录至少包含来源、时间、范围／主体，并区分稳定偏好与临时状态。

“曾考虑买熊”不等于“每次都想买熊”，过去地址不等于当前位置。过时、冲突与隐私敏感记录应允许更正、失效或删除。

### 5. 记忆也会被污染

外部文档不能自行要求写入高权限永久规则。保存前需确认与用户相关且在允许范围内，避免不必要地保留密码、定位轨迹或他人信息。

检索命中的记忆是有来源的证据，不是可以跳过当前授权的新命令。权限和当前任务范围仍由宿主执行。

### 理解检查

<details><summary>模型口头说“记住了”，就一定写入持久存储吗？</summary><p>不一定，需要真实写入机制与成功结果；否则可能只存在当前对话。</p></details>
<details><summary>压缩后摘要没提“禁止购买”，是否表示限制取消？</summary><p>不表示，这是摘要遗漏，不是用户撤回。关键约束应被保留并在执行端独立检查。</p></details>

来源：PDF第128–136页。预算与保真检查为教学补充；课件引用的摘要字段作为一般例子，不代表任何软件当前完整规范。


## Coding Agents：循环之外，还要有执行边界

### 1. 图里不只有一个模型

PDF第138–144页包含用户界面、Agent loop、permission system、tools、execution environment和state/persistence。

一次任务可能是：读要求 → 搜索代码 → 修改 → 运行测试 → 检查差异 → 汇报。每个箭头都有失败和权限问题，不能把生成代码当成已运行成功。

### 2. 审批不是全部交给另一个小模型

课件提到auto-approval可用分类模型辅助判断。实际产品可能用规则、沙箱、模型或组合；不能普遍断言人工审批已被淘汰。

模型判断“看起来安全”不是安全证明。删除、网络外传、凭据访问、安装脚本、提交／推送等需对应策略与授权。allow/ask/deny应在执行边界生效，不能只写在prompt里。

测试脚本也能有副作用；运行前要理解命令与环境范围。沙箱仍要有文件、网络和资源限制，不能当绝对隔离保证。

### 3. Agentic retrieval

Agent依据发现调整下一次搜索，使用grep、文件读取、符号索引等。确切函数名、报错文本、路径往往很有效；复杂影响分析则可能需调用图、AST或语义辅助。

这仍然属于广义检索增强，不应把“常用grep”说成“所有Coding Agents都不做RAG”。结果行号是证据定位，搜索没有命中也不证明代码不存在，可能受忽略规则或搜索范围影响。

### 4. AGENTS.md与Skills区别

| 项目规则 | 可复用技能 |
| --- | --- |
| 描述项目约束、结构、检查和交付要求 | 描述某类任务的操作流程与资源 |
| 如不自动提交、测试命令、源码约定 | 如一个经过审查的报告或测试流程 |
| 作用域／优先级依宿主实现 | 如何触发／加载依宿主实现 |

课件SKILL.md目录可附scripts、references、assets。它是程序化能力包／过程配方，不是给模型增加新权重，也不保证来源可信。

项目规则和技能不能覆盖更高层约束；复制陌生技能后不应立即执行附带脚本。使用前审查内容与权限。本文只解释概念，没有修改当前运行助手的权限或安装技能。

### 5. Computer use

截图→识别界面状态→提议点击／输入→执行→再截图。相比稳定API，可能有布局变化、坐标误差、遮挡、焦点切换与延迟。

“看见按钮”不等于有权限点。支付、发送、删除等最终动作需明确授权；页面内容可能包含提示注入，凭据也不能因截图可见就随意传播。

API、DOM辅助与视觉控制可组合，不能把课程某时点“效率较低”的判断固定成所有系统永久结论。

### 6. 验证与完成标准

代码变更要报告实际文件、测试与未运行项；测试通过不代表所有功能、性能与安全已证明。模型自评“完成”不是独立验收。

选择相同Harness对比模型可减少一类变量，但结果仍受版本、提示、工具、预算和环境影响。课件产品名单和开源／闭源归类只作日期快照，不维护当前排行榜。

## 多Agent编排：分工不是免费能力放大器

### 1. 两种课程图景

PDF第147–149页：主Agent分派独立任务、子Agent回报；或者多个队友围绕共享任务列表相互沟通。

课件“subagents无通信”指图中的子Agent之间没有直接通信，不是所有实现都禁止消息。Agent Team也不代表绕过主控、权限或预算。

### 2. 什么任务适合拆？

边界清晰、可独立验收、输入输出明确的检索、测试、分析任务。是否需要高推理能力与是否可委派是两条不同维度；不能把子任务都说成简单工作。

有依赖时按顺序传递，独立任务才并行。同一工作区多写者容易覆盖彼此修改，使用隔离工作区／分支、明确单一写入负责人和受控合并。

### 3. 时延和成本分别算

教学两条独立任务分别4秒和6秒，调度／汇总额外1秒：串行约11秒，并行理想约7秒。但两条任务本身计算量仍存在，且复制背景、通信与重试可能增加总token。

主任务与3个子任务若各重复1000 token背景，仅这些副本就有4000 token的计量输入规模，不是共享同一份“免费上下文”。缓存和实际计费可能再改变成本。

任务不独立、模型排队、设备资源争用时，max耗时的理想式也不成立。并行更快不意味着更便宜或更正确。

### 4. 结果怎么汇总？

要求来源、操作记录、实际测试、未解问题与明确产物，主控核查再合并。多个Agent用同一个模型和同一份错误资料，错误可能高度相关，“三票同意”不是独立事实证据。

工具返回、子Agent报告和共享消息都是待核查数据，不能自动升级为授权。任务取消后还需确认在途执行与产物状态。

### 5. 进展与漏洞怎样阅读？

PDF第150–151页展示研究进展与安全事件线索。新闻案例不等于普遍能力评估，漏洞演示也应检查实验环境、权限与复现条件；这里不将未独立核实的日期或产品事件写成当前事实。

防御性重点是最小权限、网络／文件隔离、外部内容不可信、敏感动作确认、审计与停止。不要因为“Agent合作”就让任何成员获得其余成员全部凭据或允许外部消息触发任意命令。

### 6. 最小可行系统常更好

先看单Agent加明确工具是否足够，再考虑分工。若固定流程能完成，优先减少状态和通信复杂度。增加成员应有可测收益，而不是把数量本身当质量指标。

<details><summary>三份一致的报告是否就能替代引用核查？</summary><p>不能，它们可能共享错误来源或模型偏差，需要独立证据与检查。</p></details>

## 第六讲复习：信息、行动与控制分层检查

### 1. 一张流程图回顾

<div class="flow"><span class="chip">用户目标与约束</span><span class="arrow">→</span><span class="chip">检索／澄清</span><span class="arrow">→</span><span class="chip">模型提议动作</span><span class="arrow">→ 授权执行 →</span><span class="chip">观察、验证与停止</span></div>

贯穿全讲的关键不是“模型会调用函数”这一点，而是信息从哪里来、动作由谁批准、结果由谁验证、状态怎样保留。

### 2. 各层分别验收

| 层 | 应检查 | 不能只用什么代替 |
| --- | --- | --- |
| 候选检索 | 相关证据覆盖与权限 | 生成回答看起来流畅 |
| 重排 | 前列相关性与指标 | 余弦分数很高 |
| 生成 | 证据忠实、引用与未知边界 | RAG命中一个chunk |
| 工具 | 名称、参数、权限、错误与副作用 | JSON能解析 |
| Harness | 预算、停止、确认、审计与隔离 | 模型说自己会安全 |
| 记忆 | 来源、时效、范围、可更正／删除 | 口头说“我记住了” |
| 多Agent | 分工、独立证据、写入隔离 | 数量多／多数票 |
