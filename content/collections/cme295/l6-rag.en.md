## 1. Why can the model not be given everything?

PDF pages 10–20 give three motives: the window is limited; irrelevant material in a long input can hurt performance; and input tokens cost money.

Needle-in-a-haystack tests retrieval ability by varying where a fact sits and how long the input is; it does not mean one score covers every long-document understanding task, nor that a single historical chart proves every model degrades identically.

RAG = Retrieval-Augmented Generation: retrieve relevant passages, augment the prompt, then generate an answer. What usually updates is the knowledge base and this request’s context, not the model’s weights.

## 2. One complete run

<div class="flow"><span class="chip">question</span><span class="arrow">→ retrieve material →</span><span class="chip">question + evidence</span><span class="arrow">→ generate →</span><span class="chip">answer with sources</span></div>

Teaching question: “Where is Cuddly usually?” The material says “Cuddly spends most of its time around books”. The model may answer “the material only says it is often near books”, and must not upgrade that to “it is definitely in some library right now”.

Retrieved material itself may be stale, wrong or contain malicious instructions. RAG makes evidence available; it does not guarantee the generation is faithful to it. Distinguish direct statements, inference and unknowns, and keep pointers to sources.

## 3. How is a knowledge base built?

PDF pages 22–25: collect documents → cut into chunks → encode embeddings → store text, vectors and metadata.

Useful metadata includes document ID, version, page or paragraph, update time and access permission. Permission checks cannot live only at the display stage: retrieval and reranking must also keep unauthorised content out of the model and the logs.

## 4. Chunk size and overlap

A chunk that is too small loses context; one that is too large dilutes the topic and raises input cost. Fixed-length, heading or sentence-based, and structure-aware chunking each trade off differently.

Teaching example: length 1000 tokens, chunk 400, overlap 100, stride 300, stopping once the end is covered, giving intervals [0,400), [300,700), [600,1000) — 3 chunks and 1200 stored tokens. Without overlap the 3 chunks total 1000 tokens, so the 200 extra come from the two overlaps.

Overlap improves coverage at boundaries but does not guarantee any single fact stays whole; it also enlarges the index and duplicates evidence, so deduplication after retrieval may be needed. The slides’ “about 10%” is a heuristic, not a universal optimum.

## 5. Embedding shape and storage

With N chunks of d dimensions, the document matrix E is N×d and the query vector q is d-dimensional. The inner product Eq gives N scores; cosine also needs norm normalisation.

Teaching example: N=10000, d=768, FP32 at 4 bytes per entry gives 30,720,000 bytes = 30.72 MB, about 29.30 MiB. Text, index structures, permission metadata and database overhead are excluded.

Larger dimensions are not necessarily better retrieval; the encoder model, training objective, language and chunking matter more. Query and documents must share a compatible embedding space and the matching query/document configuration — “same number of dimensions” is not enough. Changing the model usually means rebuilding the vector index.

## 6. How do updates affect answers?

After a knowledge-base update, track deletion of old chunks, version replacement and index refresh. The model sees whatever version this retrieval selected; “the database has a new document” does not mean every request already received it.

Hypothetical material generated by techniques such as HyDE cannot be used as source evidence; the next page separates its role as a retrieval bridge from that of real documents.
