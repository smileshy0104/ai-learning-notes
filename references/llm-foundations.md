## 路线 0：基础前置——从统计语言模型到词向量与 RNN

> 先理解模型为什么需要表示、记忆和上下文，这是 Transformer 出现的前置知识。

### 1.1 从简单到复杂：N-gram 模型

**核心思想**：预测下一个词出现的概率

想象你在玩「文字接龙」游戏。传统的 N-gram 模型就像是通过「死记硬背」历史上见过的词组合来猜测下一个词。

#### （1）先看一个最小例子

- 语料库：`datawhale agent learns`, `datawhale agent works`
- 问题：预测 `datawhale agent` 后面最可能出现什么词？
- 答案：通过统计发现，`learns` 和 `works` 各出现 1 次，概率都是 50%

这个例子只有两个句子，看不出计算过程。下面用一个稍大的语料把每一步算清楚。

#### （2）形式化：条件概率与链式法则

N-gram 模型要回答的是一个**条件概率**：

```
P(w_t | w_1, w_2, ..., w_{t-1})      —— 给定前面所有词，下一个词是什么？
```

**链式法则**：一个句子的概率，等于每个词在它前面所有词条件下的**条件概率连乘**。对于由 $w_1,w_2,...,w_m$ 构成的句子 S：

```
P(S) = P(w_1) · P(w_2|w_1) · P(w_3|w_1,w_2) · ... · P(w_m|w_1,...,w_{m-1})
```

直接算这个公式几乎不可能——像 `P(w_m | w_1...w_{m-1})` 这样的条件概率太难从语料库估计，因为词序列 `w_1...w_{m-1}` 可能从未在训练数据中出现过。

于是引入**马尔可夫假设**：

> **不必回溯一个词的全部历史，只依赖前 n-1 个词。**

于是：

```
P(w_t | w_1...w_{t-1})  ≈  P(w_t | w_{t-n+1} ... w_{t-1})
```

- **n=1（unigram）**：`P(w_t)` —— 不看上下文，只看词频
- **n=2（bigram）**：`P(w_i | w_{i-1})` —— **只看前一个词**
- **n=3（trigram）**：`P(w_i | w_{i-2}, w_{i-1})` —— **只看前两个词**

**一句话的联合概率**则由链式法则拆成多个 n-gram 相乘：

```
P(w_1, w_2, ..., w_m) = Π P(w_i | w_{i-n+1} ... w_{i-1})
```

工程上几乎总是取对数相加（避免多个小数相乘下溢）：

```
log P(sentence) = Σ log P(w_i | 前文)
```

#### （3）最大似然估计（MLE）：数一数就完了

N-gram 的概率估计极其朴素——**数频次，做除法**：

```
              C(w_{t-n+1} ... w_{t-1}, w_t)          「这个 n-gram 出现的次数」
P(w_t | 前文) = ───────────────────────────  =  ─────────────────────────────
                C(w_{t-n+1} ... w_{t-1})          「前文出现的次数」
```

#### （4）完整算例：官方原书例子（`datawhale agent` 语料）

这是 HelloAgents 原书 3.1.1 节的例子，也是本文开头那个“最小例子”的完整算法。

**语料**（仅两句话，共 6 个词）：

```
datawhale agent learns
datawhale agent works
```

**目标**：用 Bigram 模型估算句子 `datawhale agent learns` 的概率。

**第一步：算第一个词的概率** `P(datawhale)`

```
P(datawhale) = Count(datawhale) / 总词数 = 2 / 6 ≈ 0.333
```

**第二步：算条件概率** `P(agent | datawhale)`

```
P(agent|datawhale) = Count(datawhale agent) / Count(datawhale) = 2 / 2 = 1.000
```

**第三步：算条件概率** `P(learns | agent)`

```
P(learns|agent) = Count(agent learns) / Count(agent) = 1 / 2 = 0.500
```

**最后：连乘**

```
P(datawhale agent learns) ≈ P(datawhale) × P(agent|datawhale) × P(learns|agent)
                          ≈ 0.333 × 1.000 × 0.500
                          ≈ 0.167
```

**可运行代码**：

```python
import collections

corpus = "datawhale agent learns datawhale agent works"
tokens = corpus.split()
total_tokens = len(tokens)

# 第一步: P(datawhale)
count_datawhale = tokens.count('datawhale')
p_datawhale = count_datawhale / total_tokens
print(f"第一步: P(datawhale) = {count_datawhale}/{total_tokens} = {p_datawhale:.3f}")

# 第二步: P(agent|datawhale)
bigram_counts = collections.Counter(zip(tokens, tokens[1:]))
count_datawhale_agent = bigram_counts[('datawhale', 'agent')]
p_agent_given_datawhale = count_datawhale_agent / count_datawhale
print(f"第二步: P(agent|datawhale) = {count_datawhale_agent}/{count_datawhale} = {p_agent_given_datawhale:.3f}")

# 第三步: P(learns|agent)
count_agent_learns = bigram_counts[('agent', 'learns')]
count_agent = tokens.count('agent')
p_learns_given_agent = count_agent_learns / count_agent
print(f"第三步: P(learns|agent) = {count_agent_learns}/{count_agent} = {p_learns_given_agent:.3f}")

# 连乘
p_sentence = p_datawhale * p_agent_given_datawhale * p_learns_given_agent
print(f"最后: P('datawhale agent learns') ≈ {p_sentence:.3f}")

运行命令：  python3 N-gram.py
```

输出：

```
第一步: P(datawhale) = 2/6 = 0.333
第二步: P(agent|datawhale) = 2/2 = 1.000
第三步: P(learns|agent) = 1/2 = 0.500
最后: P('datawhale agent learns') ≈ 0.167
```

> 💡 **注意第一步的细节**：`P(datawhale)` 用的是**词频**（unigram），而后面两项用的是**条件概率**（bigram）。这是链式法则的自然结果——第一个词没有前文可依赖。如果严格用 bigram，应该加上 `<s>` 句首标记，即 `P(datawhale|<s>)`。原书这个例子为了讲解简洁省略了句首标记。

#### （5）N-gram 的两个致命缺陷

这是官方原文的总结（只有两条，不是三条）：

**1. 数据稀疏性（Sparsity）**

如果一个词序列从未在语料库中出现，其概率估计就为 **0**，这显然不合理。虽然可以通过**平滑（Smoothing）**技术缓解，但**无法根除**。

> 💡 一句话理解平滑：把概率质量**从"见过的组合"匀一点给"没见过的组合"，避免整句概率归零**。但匀出去的代价是见过组合的概率变低，所以只能缓解、不能根治。

**2. 泛化能力差**

模型无法理解词与词之间的**语义相似性**。

原文的例子很到位：即使模型在语料库中见过很多次 `agent learns`，它也无法把这个知识泛化到语义相似的词上。当我们计算 `robot learns` 的概率时，如果 `robot` 这个词从未出现过，或者 `robot learns` 这个组合从未出现过，**模型算出的概率就是零**。

> 🎯 **模型无法理解 `agent` 和 `robot` 在语义上是相似的**——这正是神经网络语言模型要解决的问题，也是 1.2 节的起点。

> ⚠️ 另外还有**参数爆炸**问题（词表 10 万时，3-gram 理论上有 10^15 个格子，根本存不下），这是 1.2 节 NNLM 要解决的第二个动机。

### 1.2 神经语言模型（NLM/NNLM）：从"查表"到"算出来"

**要解决的问题**：N-gram 的两个致命缺陷——**数据稀疏**（没见过的组合概率为 0）与**泛化能力差**（不懂 `agent` 和 `robot` 相似）。顺带也解决了参数爆炸：词表 10 万时 3-gram 有 10^15 个格子，根本存不下。

**NNLM 的突破**（Bengio 等，2003，**Neural Network Language Model**）：

1. **先查表**：给**每个词分配一个稠密向量（几十到几百维）**，这就是"词嵌入"的**起源**——它最初只是神经网络的副产品
2. **再算概率**：用**前馈神经网络根据前 n-1 个词预测下一个词**
3. **关键收益**：相似词自动**获得相似向量**，因此**没见过的词组合也能算出合理概率**，直接**缓解了数据稀疏问题**

**这一代的定位：任务独立的特征提取器**

这是理解整条演进线的关键。所谓"任务独立"，是指：

- 词向量本身**不完成任何任务**，只作为下游分类器、序列标注模型的**输入特征**
- 因此同一个词向量可以喂给情感分析、命名实体识别等任意任务，模型不需要重训
- 代价是：词向量是**静态**的（Static Word Representations）——**`bank` 在"河岸"和"银行"两个句子里，向量完全相同**

**从静态到动态，正是下一次跃迁的动机**：

|          | 静态词表示（上下文无关）  | 上下文相关表示              |
| -------- | ------------------------- | --------------------------- |
| 代表     | Word2Vec、GloVe、FastText | ELMo、BERT、GPT             |
| 一词多义 | 无法区分                  | **随语境动态变化**          |
| 使用方式 | **作为特征喂给下游模型**  | **预训练 + 微调，直接迁移** |
| 所属代际 | 神经语言模型（1.3~1.4）   | 预训练语言模型（1.5）       |

**「静态」到底意味着什么**

这三个方法有个**共同的、致命的**特征：**一个词只对应一个向量，与上下文无关**。

```
「他在河岸散步」   → bank 的向量 = [0.21, -0.83, ...]
「他去银行取钱」   → bank 的向量 = [0.21, -0.83, ...]   ← 完全相同
```

`bank`（河岸/银行）、`apple`（苹果/苹果公司）、`table`（桌子/表格）、`java`（爪哇岛/编程语言）全部无法区分。

**为什么这是致命的**：下游模型拿到的输入特征里，**根本没有区分歧义的信息**。哪怕下游模型再强，也无法从同一个向量里还原出两种含义——**信息在第一步就已经丢了**。

**为什么这是「跃迁」而不是「优化」**

**静态向量**的两个问题**无法靠「继续优化 Word2Vec」解决**，必须换范式：

1. **信息瓶颈**：要区分歧义，模型必须**看到整个句子**再决定词向量。而 Word2Vec / GloVe / FastText 的训练目标（局部窗口共现）从设计上就只让模型看几个词。**目标函数错了，调超参数没用。**
2. **使用方式受限**：静态向量只能当**固定特征（重要）**喂给下游模型（feature-based），每个任务还要单独训一个分类器；而「**上下文相关表示**」可以**预训练 + 微调**（fine-tuning），一套参数适配所有任务。

所以完整的逻辑链（重点）是：

```
静态向量 → 一词多义无法区分 → 下游模型信息不足
         → 想解决必须「先看整句再决定词向量」
         → 必须换训练目标（从「局部共现」到「整句建模」）
         → 必须换架构（从浅层网络到双向 Transformer/LSTM）
         → 这就是 ELMo / BERT / 预训练语言模型
```

> 🎯 **一句话**：「静态 → 动态」不是一个渐进优化，而是**范式切换**——这才是它被称为「跃迁动机」的原因。

### 1.3 词嵌入方法：把词变成向量

#### （1）到底什么是「词嵌入」

**一句话定义**：词嵌入（Word Embedding）= **把离散的词映射为连续稠密向量**的过程。

**为什么叫「嵌入」？**

因为这一步的本质，是把一个**离散的符号空间**「嵌入」到一个**连续的向量空间**里：

```
词表（离散）              向量空间（连续）
┌─────────┐              ┌─────────────────────────┐
│ agent   │──映射──→      [ 0.21, -0.83,  0.47, ...]
│ robot   │──映射──→      [ 0.19, -0.79,  0.52, ...]   ← 靠得很近
│ apple   │──映射──→      [-0.62,  0.34, -0.11, ...]   ← 离得很远
└─────────┘              └─────────────────────────┘
```

**三个关键词拆开看**：

| 关键词                 | 含义                          | 对比旧方法（One-hot）                                                   |
| ---------------------- | ----------------------------- | ----------------------------------------------------------------------- |
| **稠密（Dense）**      | 每一维都有实数值（如 300 维） | One-hot 极度稀疏：词表 10 万 → 每个词一个 10 万维向量，只有一个位置是 1 |
| **连续（Continuous）** | **取值是连续实数，不是 0/1**  | One-hot 只能表示「是/不是」，无法表示「有多像」                         |
| **低维（Low-dim）**    | 通常 50~4096 维               | One-hot 维度 = 词表大小                                                 |

**One-hot 的两个致命问题**（为什么必须换成词嵌入）：

```
One-hot 编码：
agent = [0, 0, 1, 0, 0, 0, ..., 0]   （10 万维，只有第 3 位是 1）
robot = [0, 0, 0, 1, 0, 0, ..., 0]   （10 万维，只有第 4 位是 1）

任意两个不同词的余弦相似度 = 0
→ agent 和 robot 的「距离」 == agent 和 apple 的「距离」
→ 模型无法知道 agent 和 robot 更相似（重点）
```

> 🎯 **这就是词嵌入真正解决的核心问题**：它让「语义相似」变成**可计算的数值关系**。一旦词变成向量，相似度、类比、聚类这些数学工具就全部可用了。

#### （2）词向量是怎么学出来的

这里有个很反直觉的事实：**没有人去定义「相似」是什么意思，词向量是「副产物」。**

**核心假设：分布式假设（Distributional Hypothesis）**

> 一个词的含义，由它经常出现的**上下文**决定。
> —— J.R. Firth, 1957："You shall know a word by the company it keeps."

具体来说：如果 `agent` 和 `robot` 经常出现在相似的上下文里（如 `__ learns`、`__ works`、`the __ is`），那么它们就应该有相似的向量。

**学习机制**：设一个「猜上下文」的任务，模型为了猜得更准，**被迫把语义相近的词调整到相近的位置**。

```
任务：根据 agent 猜上下文 → 想猜出 learns / works
任务：根据 robot 猜上下文 → 也想猜出 learns / works

为了在两个任务上都猜对：
  agent 的向量必须和 robot 的向量相似
  ↓
  模型自动学出了「agent ≈ robot」这个语义关系
```

> 💡 **关键理解**：词向量不是被「设计」出来的，而是被「任务逼」出来的。我们只定义了「猜上下文」这个任务，语义结构是模型为了完成任务而**自发形成**的。

#### （3）演进脉络：四代方法

| 代际                      | 代表                                  | 时间      | 核心思路                   | 主要局限                           |
| ------------------------- | ------------------------------------- | --------- | -------------------------- | ---------------------------------- |
| **1. 统计共现**           | LSA / HAL                             | 1990s     | 对共现矩阵做 SVD 降维      | 计算贵、无法处理新词               |
| **2. 浅层神经网络**       | NNLM                                  | 2003      | 前馈网络预测下一个词       | 训练慢，词向量是副产物             |
| **3. 专用词向量（重要）** | **Word2Vec**、**GloVe**、**FastText** | 2013-2016 | 专为学词向量设计的高效算法 | **静态**：一词一向量，无法区分歧义 |
| **4. 上下文相关（重要）** | ELMo、BERT、GPT                       | 2018+     | **向量随语境动态变化**     | 计算量大，需**预训练+微调**        |

> 📌 **第 3 代是本节重点**——它把词向量从「副产品」变成了「产品」，也是工业界至今仍在推荐系统、文本聚类等场景大量使用的一代。

#### （4）怎么衡量「靠得近」：余弦相似度

有了向量，就需要一个工具衡量两个词有多像。最常用的是**余弦相似度**，它看的是两个向量**方向的夹角**，而不是长度：

```
similarity(a, b) = cos(θ) = (a · b) / (|a| × |b|)
```

| 余弦值 | 夹角 | 含义                   |
| ------ | ---- | ---------------------- |
| 1      | 0°   | 方向完全相同，完全相关 |
| 0      | 90°  | 正交，毫无关系         |
| -1     | 180° | 方向相反，完全负相关   |

> 💡 **为什么用余弦而不是欧氏距离？** 因为余弦只看方向、忽略长度。一个词在长文中出现频繁、在短文中出现少，向量长度会差很多，但它们表达的语义关系可能一致。余弦能屏蔽这种「频次干扰」。

**语义运算演示**（官方原文 3.1.1 节）：

```python
import numpy as np

# 假设我们已经学习到了简化的二维词向量
embeddings = {
    "king": np.array([0.9, 0.8]),
    "queen": np.array([0.9, 0.2]),
    "man": np.array([0.7, 0.9]),
    "woman": np.array([0.7, 0.3])
}

def cosine_similarity(vec1, vec2):
    dot_product = np.dot(vec1, vec2)
    norm_product = np.linalg.norm(vec1) * np.linalg.norm(vec2)
    return dot_product / norm_product

# king - man + woman
result_vec = embeddings["king"] - embeddings["man"] + embeddings["woman"]

# 计算结果向量与 "queen" 的相似度
sim = cosine_similarity(result_vec, embeddings["queen"])

print(f"king - man + woman 的结果向量: {result_vec}")
print(f"该结果与 'queen' 的相似度: {sim:.4f}")

运行命令：python3 Norm.py 
```

官方输出：

```
king - man + woman 的结果向量: [0.9 0.2]
该结果与 'queen' 的相似度: 1.0000
```

> 📌 **注意这组向量是人为构造的**：`king - man + woman = [0.9-0.7+0.7, 0.8-0.9+0.3] = [0.9, 0.2]`，正好等于 `queen`。这是为了演示「语义平移」思想而刻意设计的——真实训练出来的词向量不会这么精确，相似度通常在 0.7~0.9 之间。

**为什么这个例子重要**：它说明词嵌入不只是「把词变成数字」，而是**把语义关系变成了可运算的向量关系**。

```
king - man + woman ≈ queen         → 性别关系可以被「加减」出来
paris - france + italy ≈ rome      → 首都关系也可以
walking - walk + swim ≈ swimming   → 时态关系也可以
```

这就是「语义平移」（semantic arithmetic）—— 向量的**差值**编码了语义关系本身。

#### （5）Word2Vec（2013，Google / Mikolov）—— 预测派

**核心思路：用「猜词」学向量。**

训练一个**极浅**的神经网络（只有一层隐藏层），任务就是猜词。两种猜法：

| 架构          | 输入 → 输出     | 举例                         | 特点                         |
| ------------- | --------------- | ---------------------------- | ---------------------------- |
| **CBOW**      | 上下文 → 中心词 | 输入 `the ? sat`，猜 `cat`   | 训练快，对高频词更好         |
| **Skip-gram** | 中心词 → 上下文 | 输入 `cat`，猜 `the` / `sat` | 训练慢，对低频词和生僻词更好 |

**网络结构**（只有三层）：

```
输入层（上下文词的 one-hot）
      ↓  乘以词向量矩阵 W（这才是我们要的东西）
隐藏层（稠密向量，无激活函数）
      ↓  乘以输出矩阵 W'
输出层（词表大小的 softmax 概率）
```

> 🎯 **关键洞察**：训练完成后，**那个神经网络直接扔掉**，只留下中间的**词向量矩阵 W**。网络只是「学习工具」，**向量才是产品（重要）**。

**加速技巧：Negative Sampling（负采样）**

原始做法要对全词表（10 万+）做 softmax，太贵。负采样的思路：

```
不学「从 10 万个词里挑对那一个」
而学「判断这一对词是不是真的相邻」（二分类）

正样本：真实相邻的词对（agent, learns）→ 标签 1
负样本：随机抽 5~15 个不相关词     → 标签 0
```

把 10 万类分类问题变成几个二分类问题，训练速度提升几个数量级。

**局限**：只看**局部窗口**内的共现，完全不知道全局统计信息。

#### （6）GloVe（2014，Stanford / Pennington）—— 计数派

**核心思路：用「计数 + 矩阵分解」学向量。**

1. 扫全语料，构建**全局共现矩阵** `X`，其中 `X_ij` = 词 i 与词 j 在窗口内共现的次数
2. 目标是让两个词的向量点积 ≈ 共现次数的对数：

```
w_i · w_j + b_i + b_j ≈ log(X_ij)
```

**为什么要取 log？** 因为共现次数的分布极度长尾（常见词对几百万次，罕见词对 1 次）。取对数把「次数差异」压缩成「量级差异」，更接近语义重要性的真实比例。

**它同时继承了两派优点**：

| 来源           | 继承了什么             |
| -------------- | ---------------------- |
| LSA / 矩阵分解 | 利用**全局**统计信息   |
| Word2Vec       | 用**局部窗口**定义共现 |

一句话对比：**Word2Vec 是「预测派」，GloVe 是「计数派」。**

#### （7）FastText（2016，Facebook / Bojanowski）—— 子词派

**核心创新：把词拆成子词（subword）。**

不再把 `where` 当成一个整体，而是拆成字符 n-gram：

```
where → <wh, whe, her, ere, re>，再加上整体 <where>
词向量 = 所有这些 n-gram 向量之和
```

**三个好处**：

1. **彻底解决 OOV**：没见过的词 `whereabouts`，也能用 `where` 的 n-gram 拼出一个合理向量
2. **形态丰富语言友好**：土耳其语、芬兰语这类一个词根变几十种形式的语言
3. **拼写错误鲁棒**：`aple` 和 `apple` 共享大量 n-gram，向量不会差太远

**代价**：要存所有 n-gram 的向量，**存储和内存开销大**。

> 📌 **FastText 与 3.3 节的 BPE 有思想上的亲缘关系**：都是「用更小的单位组合出任意词」，区别在于 FastText 用于**词向量**，BPE 用于**分词**。

#### （8）三者对比

|                | Word2Vec         | GloVe            | FastText            |
| -------------- | ---------------- | ---------------- | ------------------- |
| 年份 / 出处    | 2013 / Google    | 2014 / Stanford  | 2016 / Facebook     |
| 学习方式       | 预测（浅层网络） | 计数 + 矩阵分解  | 预测 + 子词         |
| 看局部还是全局 | 局部窗口         | **全局**共现矩阵 | 局部窗口            |
| OOV 处理       | ❌ 无能为力       | ❌ 无能为力       | ✅ **子词组合**      |
| 存储开销       | 小               | 小               | **大**（存 n-gram） |
| 一句话定位     | 开创性，最简单   | 统计上更优雅     | 工程上最鲁棒        |

**选型建议**：

- 通用场景、追求简单 → **Word2Vec**
- 语料大、追求统计严谨 → **GloVe**
- 有大量生僻词 / 拼写变体 / 形态丰富语言 → **FastText**
- **但绝大多数现代场景**：直接**用预训练好的（BERT / Sentence-BERT）**，不必自己训

> ⚠️ **容易混淆的一点**：Word2Vec、GloVe 严格来说不是「语言模型」，而是**词表示学习方法**——它们不预测下一个词，而是用局部窗口内的共现关系学出向量。它们与 NNLM 同属「神经语言模型」这一代，是因为共同完成了从「离散符号」到「稠密向量」的转换，并同样只提供**任务独立的特征**。

### 1.4 RNN（循环神经网络） 和 LSTM（长短时记忆网络-改进版循环神经网络）：有记忆的模型

**核心特点**：为网络增加“记忆”能力，**引入"隐藏状态"作为短期记忆**

- **RNN**：像接力赛，**每个时刻的信息传递给下一刻**，这个循环往复的过程，使得信息可以在序列中不断向后传递。

  - **长期依赖问题 (Long-term Dependency Problem)**：对于 RNN 而言，序列的长度就是网络的深度。当序列很长时，梯度在从后向前传播的过程中会经过多次连乘，这会导致梯度值快速趋向于零（**梯度消失**）或变得极大（**梯度爆炸**）
  - 梯度消失使得模型无法有效学习到序列早期信息对后期输出的影响，即**难以捕捉长距离的依赖关系**。

- **LSTM**：LSTM 是一种特殊的 RNN，其核心创新在于引入了**细胞状态 (Cell State)** 和一套精密的**门控机制 (Gating Mechanism)** ，**通过"门控机制"解决长期依赖问题**

- **细胞状态**可以看作是一条独立于隐藏状态的信息通路，允许信息在时间步之间更顺畅地传递。

- **门控机制**则是由几个小型神经网络构成，它们可以学习如何有选择地让信息通过，从而**控制细胞状态中信息的增加与移除**。

  - **遗忘门**（Forget Gate）：决定丢弃什么
  - **输入门**（Input Gate）：决定记住什么
  - **输出门**（Output Gate）：决定输出什么

- **GRU**：LSTM 的简化版，只有两个门（更新门和重置门），参数更少

**共同缺点**：

1. 必须按顺序处理，无法并行计算
2. 长序列训练慢，难以捕捉超长距离依赖
3. 信息瓶颈：所有信息都要压缩到固定大小的隐藏状态

## 路线 1：Transformer 与预训练基座

> 先理解 Transformer 的零件，再理解预训练语言模型如何把架构变成可迁移的基座。

### 1.5 预训练语言模型：可迁移的 NLP（Natural Language Processing，自然语言处理） 任务求解器

> 📌 本节内容是对 Datawhale 原书第三章的补充（原书从 RNN 直接进入 Transformer 架构）。补充的理由：**1.4 节的 RNN/LSTM 和第二章的 Transformer 之间，缺了「预训练 + 微调」这一环**——正是这一环让 Transformer 从「一个更好的架构」变成「现代大模型的起点」。

#### （1）解决什么问题：一任务一模型的时代

1.4 节结束时，做一个 NLP 应用的流程是这样的：

```
情感分析    → 标注 1 万条 → 训练一个 LSTM → 得到一个模型
命名实体识别 → 标注 1 万条 → 训练一个 LSTM → 得到另一个模型
问答系统    → 标注 1 万条 → 训练一个 LSTM → 又得到另一个模型
```

**三个致命问题**：

| 问题                     | 后果                                        |
| ------------------------ | ------------------------------------------- |
| **每个任务都要标注数据** | 成本高，小语种/垂直领域几乎无解             |
| **每个任务一个模型**     | 存储、部署、维护成本线性增长                |
| **语言知识无法复用**     | 情感分析模型学到的「中文语法」不能给 NER 用 |

> 🎯 **这就是「可迁移」三个字的分量**：预训练语言模型让「学语言」和「学任务」变成两件可以分开的事。

#### （2）核心思想：两阶段范式（重要）

```
阶段一：预训练（Pre-training）
  数据：海量无标注文本（维基百科、书籍、网页，几十 GB 到几 TB）
  目标：自监督学习（不需要人工标注）
  产出：一个「懂语言」的通用基座
         ↓
阶段二：微调（Fine-tuning）
  数据：少量标注数据（几千到几万条）
  目标：适配具体任务
  产出：一个任务专用模型
```

这相当于把 NLP 从「手工作坊」变成「基座 + 适配器」：

```
旧范式：每个任务从头造轮子
新范式（更好理解）：造一个好轮子（基座），然后换不同的轮胎（微调）
```

**为什么这样更省？** 因为「学语言」这件事只需要做一次，而它恰恰是最贵的（需要海量数据 + 大量算力）。「学任务」相对便宜，几千条标注就够。

#### （3）关键创新：上下文相关表示

这是 1.2 节末尾埋下的伏笔终于兑现。

|                       | 静态向量（1.3 节）          | 上下文向量（本节）           |
| --------------------- | --------------------------- | ---------------------------- |
| 代表                  | Word2Vec / GloVe / FastText | **ELMo / BERT / GPT**        |
| `bank` 在「河岸」句中 | 向量 A                      | 向量 A₁（偏向河岸语义）      |
| `bank` 在「银行」句中 | 向量 A（**完全相同**）      | 向量 A₂（偏向金融机构语义）  |
| 一词多义              | **❌ 无法区分**              | ✅ **随语境动态变化（重点）** |

**关键区别在于「什么时候算向量」**：

```
静态方法：查表  →  bank 永远对应同一个向量（训练完就固定了）
动态方法：计算  →  每次输入句子，都现场跑一遍网络，算出当前语境下的向量
```

> 💡 **一句话**：**静态向量是「查出来的」，动态向量是「算出来的」**。
> 这就是为什么 BERT 类模型推理更慢——它**每次都要跑一遍「前向传播」**。

#### （4）四条技术路线

**路线一：ELMo（2018，双向 LSTM）—— 过渡方案**

- 用**两个方向的 LSTM**（正向 + 反向）分别编码，再把两层隐状态拼接
- 严格说不是「真双向」：正向和反向是**各自独立训练**的，只是最后拼起来
- 历史意义：第一次证明「上下文相关表示」在多项任务上大幅超过静态词向量
- 局限：仍受 LSTM 顺序计算限制，无法并行

**路线二：BERT（2018，双向 Transformer Encoder）—— 理解派**

核心是**两个预训练任务**：

| 任务                    | 做法                                                                              | 作用                                          |
| ----------------------- | --------------------------------------------------------------------------------- | --------------------------------------------- |
| **MLM**（掩码语言模型） | 随机遮住 15% 的词，让模型猜。其中 80% 换成 `[MASK]`、10% 换成随机词、10% 保持不变 | 学到**双向**语义                              |
| **NSP**（下一句预测）   | 给两个句子，判断 B 是不是 A 的下一句                                              | 学到**句间关系**（后被 RoBERTa 证明用处不大） |

> 🔍 **为什么是 80/10/10 而不是全用 `[MASK]`？** 因为下游任务里根本没有 `[MASK]` 这个符号。如果训练时 100% 用 `[MASK]`，模型会学到一个只在这种特殊符号下有效的模式，造成**预训练-微调不一致**。掺入随机词和原词，是为了让模型对「任何位置的任何词都可能被替换」保持鲁棒。

**路线三：GPT-1/2（2018-2019，单向 Transformer Decoder）—— 生成派**

- 训练目标只有一个：**预测下一个词**（自回归）
- GPT-1 证明了「预训练 + 微调」可行
- GPT-2 发现：**不微调，只靠提示（prompt）也能做任务**——这是通往 1.7 节的伏笔

**路线四：T5 / BART（2019-2020）—— 混合派**

- 保留完整的 Encoder-Decoder 结构
- T5 把所有任务都改写成「文本到文本」：`translate English to German: ... → ...`
- 这个「统一格式」的思想，是后来大模型「万物皆可 prompt」的先声

#### （5）四条路线对比

|                  | ELMo               | BERT                       | GPT-1/2                 | T5 / BART                   |
| ---------------- | ------------------ | -------------------------- | ----------------------- | --------------------------- |
| 年份             | 2018               | 2018                       | 2018-2019               | 2019-2020                   |
| **架构（重要）** | 双向 LSTM          | Transformer **Encoder**    | Transformer **Decoder** | **Encoder-Decoder**         |
| 注意力           | 伪双向（两向拼接） | 真双向                     | 单向（因果掩码）        | 编码双向 + 解码单向         |
| 预训练目标       | 双向语言模型       | MLM + NSP                  | 自回归                  | Span 掩码 / 去噪            |
| 擅长             | 理解               | **理解**（分类/抽取/检索） | **生成**（续写/对话）   | **序列到序列（翻译/摘要）** |
| 能否直接生成     | ❌                  | ❌                          | ✅                       | ✅                           |

> 💡 **这张表最关键的一行是「能否直接生成」**：BERT 训练时能看到「答案」，所以不能用于生成；GPT 训练时只能看左边，所以天然会生成。这个分岔直接决定了 2.3 节的架构分野，也决定了 2021 年之后为什么是 Decoder-Only 胜出。

#### （6）「可迁移」到底体现在哪

微调有两种方式，这是理解「**可迁移**」的关键：

|      | Feature-based（特征提取）                              | Fine-tuning（微调）                              |
| ---- | ------------------------------------------------------ | ------------------------------------------------ |
| 做法 | 冻结预训练模型，把它输出的向量当**特征**喂给下游分类器 | 解冻全部（或部分）参数，**连同下游任务一起训练** |
| 类比 | **预训练模型是「照相机」，只拍照不改造**               | **预训练模型是「黏土」，按任务重新捏**           |
| 代表 | ELMo 的常见用法                                        | BERT 的标准用法                                  |
| 成本 | 低（只训一个小分类器）                                 | 高（要反传整个大模型）                           |
| 效果 | 较好                                                   | **更好**（这也是 BERT 击败 ELMo 的原因之一）     |

**「可迁移」的三个层次**：

1. **跨任务迁移**：一个基座 → 分类、抽取、问答、句对匹配……只需换最后的输出层
2. **跨领域迁移**：通用语料预训练 → 医疗/法律/金融语料微调
3. **跨语言迁移**：多语言预训练（mBERT）→ 低资源语言也能受益

#### （7）这一代的局限

| 局限                          | 具体表现                                                     | 后来怎么解决                                  |
| ----------------------------- | ------------------------------------------------------------ | --------------------------------------------- |
| **微调成本高**                | 每个任务要存一份完整模型副本（BERT-base 1.1 亿参数 ≈ 440MB） | LoRA / Adapter 等参数**高效微调（PEFT）**     |
| **泛化靠「专」**              | 一个微调模型只会一个任务，换个任务就要重训                   | **提示学习（prompt-based）**，见 1.7 节       |
| **规模未到临界点**            | 参数量普遍在亿级，尚未出现涌现能力                           | **扩大规模到千亿级**（GPT-3）                 |
| **MLM 造成预训练-微调不一致** | 训练时有 `[MASK]`，实际使用时没有                            | RoBERTa 移除 NSP、动态 mask；后续用自回归目标 |

**这四个局限，正好构成了向下一代（大规模语言模型）跳转的完整动机**：

```
微调成本高  → 想「不微调也能用」 → 提示学习
泛化靠专    → 想「一个模型做所有任务」 → 通用求解器
规模不够    → 想「继续扩大」 → 千亿参数
```

#### （8）这一代的历史地位

```
统计语言模型（N-gram）       → 会背词组合
神经语言模型（NNLM/词向量）  → 会表示词
预训练语言模型（BERT/GPT）   → 会理解语言，能迁移到任务   ← 本节
大规模语言模型（GPT-3/4）    → 一个模型做所有任务
```

> 🎯 **一句话总结这一代**：它第一次把 NLP 从「每个任务单独造模型」变成了「**造一次基座，适配所有任务**」。虽然这个范式后来被「提示学习」部分取代，但「**预训练**」这个**思想保留了下来**，并成为所有现代大模型的基础。

### 2.1 为什么 Transformer 这么重要？

**先看它解决了 RNN（循环神经网络） 的什么问题**（承接 1.4 节）：

|                | RNN / LSTM                                     | Transformer                          |
| -------------- | ---------------------------------------------- | ------------------------------------ |
| **计算方式**   | 必须按时间步串行：**第 t 步要等第 t-1 步算完** | **全部位置并行**计算                 |
| **长距离依赖** | 信息要逐步传递，远了就衰减（**梯度消失**）     | 任意两个位置**直接相连**，距离恒为 1 |
| **训练速度**   | 慢，且序列越长越慢                             | 快，可充分利用 GPU 并行能力          |
| **可扩展性**   | 受串行限制，难以扩到超大规模                   | **可以堆到上百层、千亿参数**         |

**四大优势**：

1. **并行计算**：可以同时处理整个句子，**训练效率提升数十倍**
2. **捕捉长距离依赖**：通过注意力机制，理论上**可以关注任意距离的词**
3. **可扩展性强**：**适合构建超大规模模型**（从百万到千亿参数）
4. **可解释性更好**：注意力权重可以可视化，了解模型关注什么

> 💡 **一个数字对比**：RNN 处理长度 1000 的序列，需要 1000 个串行步骤；Transformer 只需要 1 步（虽然每步计算量大）。**在 GPU 上，「并行的大计算」远快于「串行的小计算」**——这是 Transformer 能赢的硬件基础。

> ⚠️ **代价也要知道**：注意力的计算复杂度是 **O(n²)**（n = 序列长度）——每个词都要和其他所有词算一次。这就是为什么长上下文成本高（见 5.3 节「上下文长度限制」）。

### 2.2 核心组件解析

#### （1）编码器-解码器架构

```
编码器（Encoder）：理解输入句子
         ↓
解码器（Decoder）：生成目标句子
```

#### （2）注意力机制到底是什么

在讲自注意力之前，先把「注意力」这个通用概念说清楚——**它是整个 Transformer 的灵魂，也是名字的由来**。

**（a）直觉来源：人是怎么看东西的**

你扫一眼下面这句话，会不自觉地做一件事：

```
小明把书放在桌子上，然后他去吃饭了，因为他饿了。
                                  ↑
                              「他」指谁？
```

你会**自动把注意力集中在「小明」上**，而不是平均分配每个字。人类的注意力是**有选择、有权重**的——重要的地方看得多，不重要的地方一扫而过。

**注意力机制就是把这件事数学化**：给每个位置分配一个「关注权重」，权重高的地方信息保留得多，权重低的地方几乎被忽略。

**（b）一般框架：Q / K / V 三元组**

所有注意力机制都可以写成同一个框架——**用 Query 去查 Key，取回 Value**：

| 角色           | 类比（图书馆）        | 含义                     |
| -------------- | --------------------- | ------------------------ |
| **Query（Q）** | 你的**检索需求**      | 我现在想找什么信息？     |
| **Key（K）**   | 每本书的**标签/索引** | 我能提供什么信息？       |
| **Value（V）** | 书里的**实际内容**    | 我实际包含的信息是什么？ |

**流程**：

```
① 用 Q 和所有 K 做点积 → 得到「匹配分数」（需求与标签的匹配度）
② 分数过 softmax      → 变成「注意力权重」（归一化成概率，和为 1）
③ 用权重加权求和 V     → 得到「输出」（按匹配度取回内容）
```

**（c）三种注意力形式**

同样是 Q/K/V 框架，**区别只在于 Q、K、V 从哪里来**：

| 类型                                      | Q 来自     | K、V 来自                | 用在哪                     | 含义                         |
| ----------------------------------------- | ---------- | ------------------------ | -------------------------- | ---------------------------- |
| **自注意力**<br>Self-Attention            | 序列自己   | 序列自己                 | **Encoder / Decoder 内部** | **句子内部，词与词互相关注** |
| **掩码自注意力**<br>Masked Self-Attention | 序列自己   | 序列自己（**屏蔽未来**） | Decoder（GPT 类）          | 只能看已生成的部分           |
| **交叉注意力**<br>Cross-Attention         | **解码器** | **编码器输出**           | Encoder-Decoder（T5）      | 生成时参考输入               |

> 📌 **记住这个框架，后面所有变体都能套进去**：注意力不是「一种操作」，而是「**用查询去检索信息（重要）**」这个范式。后面的**多模态注意力、Agent 的记忆检索、RAG 的向量检索，本质都是同一套思想**。

**（d）一个具体例子：注意力在解决什么**

经典例子——**指代消解**：

```
The animal didn't cross the street because it was too tired
                                            ↑
                                        「it」指谁？
```

模型处理 `it` 这个词时，它的 Query 会和句中所有词的 Key 做匹配，得到一个权重分布（示意）：

```
The        score=  0.5  weight=0.0004
animal     score=  8.2  weight=0.9823  ██████████████████████████████████████████████
didn't     score=  0.3  weight=0.0004
cross      score=  0.4  weight=0.0004
the        score=  0.6  weight=0.0005
street     score=  0.9  weight=0.0007
because    score=  0.2  weight=0.0003
it         score=  2.1  weight=0.0022
was        score=  0.3  weight=0.0004
too        score=  0.4  weight=0.0004
tired      score=  3.8  weight=0.0121  █
```

> 🎯 **这就是注意力做的事**：`it` 有 **98.2%** 的注意力放在 `animal` 上——模型「明白」了 it 指的是 animal。这个权重不是人写的规则，是**训练出来的**。

**（e）手算一遍：3 个词的完整计算**

用极简例子（d_k=2）把公式从头算一遍，消除「公式恐惧」。

**第 0 步：先准备输入向量**

> ⚠️ **先说清楚：下面所有数字都是人为构造的，不是真实模型的输出。**
>
> 真实模型中：
>
> - **词向量**由训练得到，维度通常是 768 / 1024 / 4096，每个分量是 [-1, 1] 附近的**任意实数**（有正有负）
> - **投影矩阵 W_Q / W_K / W_V** 也是训练得到的稠密矩阵
> - 单个 token 在 GPT-3 上的注意力计算就是 **1200 万次乘法**，完全无法手算
>
> 所以教学例子必须简化。**这里简化了三处**，简化目的都是「让公式能被手工验证」：

| 简化项         | 真实情况             | 本例子                  | 为什么这样简化                               |
| -------------- | -------------------- | ----------------------- | -------------------------------------------- |
| **维度**       | d_model = 512~12288  | **2**                   | 二维向量能手算点积                           |
| **词向量取值** | 任意实数（有正有负） | `[1,0]`/`[0,1]`/`[1,1]` | 正交向量点积恰好为 0，能直观展示「完全无关」 |
| **投影矩阵**   | 训练得到的稠密矩阵   | **单位矩阵**            | 让 Q/K/V 直接等于 X，省掉一层矩阵乘法        |

**假设已经通过词嵌入（1.3 节）得到 3 个词向量，维度 d_model=2**：

```
X(The) = [1.0, 0.0]      ← 在「第1维」方向
X(cat) = [0.0, 1.0]      ← 在「第2维」方向（与 The 完全正交）
X(sat) = [1.0, 1.0]      ← 两个方向都有分量
```

**再假设三个投影矩阵都是单位矩阵**：

```
W_Q = W_K = W_V = [1 0]
                  [0 1]
```

于是：

```
Q = X · W_Q = X      →  q_The=[1,0],  q_cat=[0,1],  q_sat=[1,1]
K = X · W_K = X      →  k_The=[1,0],  k_cat=[0,1],  k_sat=[1,1]
V = X · W_V = X      →  v_The=[1,0],  v_cat=[0,1],  v_sat=[1,1]
```

> 📌 **关键点**：Q、K、V 是**同一批输入经过三个不同投影**得到的——这正是「**自**」注意力的含义（自己查自己）。真实模型中三个矩阵不同，所以 Q≠K≠V；这里为了简化都取了单位矩阵。

**这个简化会掩盖什么**（读完后要知道）：

| 真实特征                     | 本例子中的样子             | 差别的影响                                                       |
| ---------------------------- | -------------------------- | ---------------------------------------------------------------- |
| 点积分数**有正有负**         | 全是 0 或正数              | 真实中「负相关」的词会得到负分，softmax 后权重极低               |
| softmax 权重**差异可能极大** | 0.20 / 0.40 / 0.40，较平均 | 真实中常见 0.99 / 0.001 / ... 这种悬殊分布（见前面指代消解例子） |
| d_k 很大，缩放**效果显著**   | d_k=2，÷√2 只缩小 1.41 倍  | 真实 d_k=64 时 ÷8，d_k=128 时 ÷11.3，缩放作用大得多              |

**第一步：算匹配分数（Q · K，即点积）**

点积的定义：`[a₁,a₂] · [b₁,b₂] = a₁b₁ + a₂b₂`

现在以 `cat` 这个词的输出为例（它的 Query 是 `q_cat = [0, 1]`），让它和**所有**词的 Key 做点积：

```
q_cat · k_The = [0,1]·[1,0] = 0×1 + 1×0 = 0.00
q_cat · k_cat = [0,1]·[0,1] = 0×0 + 1×1 = 1.00
q_cat · k_sat = [0,1]·[1,1] = 0×1 + 1×1 = 1.00
```

**怎么理解这三个数**：

- `q_cat · k_cat = 1.00` —— `cat` 和自己方向一致，匹配度最高
- `q_cat · k_sat = 1.00` —— `sat` 的向量是 `[1,1]`，在 `cat` 的方向（第二维）上也有分量，所以也匹配
- `q_cat · k_The = 0.00` —— `The` 是 `[1,0]`，和 `cat` 的 `[0,1]` **完全正交**，毫不相关

> 💡 **这就是「点积衡量相关性」的几何含义**：两个向量方向越一致，点积越大；垂直（正交）时点积为 0。所以点积天然适合当「匹配分数」。

**如果是完整矩阵形式（看值大小）**（一次算出所有词的分数），就是 `QK^T`：

```
         k_The  k_cat  k_sat
q_The [  1.00   0.00   1.00 ]     ← The 关注 The(自己) 和 sat
q_cat [  0.00   1.00   1.00 ]     ← cat 关注 cat(自己) 和 sat
q_sat [  1.00   1.00   2.00 ]     ← sat 关注所有，最关注自己
```

> 🎯 **注意这个矩阵一般不对称**：本例中 `q_cat · k_sat = 1` 且 `q_sat · k_cat = 1` 碰巧相等，但一般情况**不相等**——因为 Q 和 K 用的是不同投影矩阵，**「cat 觉得 sat 重要」和「sat 觉得 cat 重要」是两件事**，各算各的。

**对比一下：真实数据算出来是什么样**

如果把词向量换成 4 维的随机实数（模拟真实分布，分量有正有负）：

```
X(The)    = [ 0.28, -0.95, -0.45, -0.55]
X(animal) = [ 0.47,  0.35,  0.78, -0.83]
X(was)    = [-0.16, -0.94, -0.56,  0.01]
X(too)    = [-0.95, -0.60,  0.30,  0.09]
X(tired)  = [-0.56,  0.18,  0.62, -0.99]
```

以 `tired` 为 Query，d_k=4：

| 步骤     | 结果                                                   |
| -------- | ------------------------------------------------------ |
| 原始点积 | `[-0.062, 1.105, -0.437, 0.521, 1.711]` ← **有正有负** |
| ÷√4 = ÷2 | `[-0.031, 0.553, -0.218, 0.260, 0.855]`                |
| softmax  | `[0.1354, 0.2427, 0.1123, 0.1812, 0.3285]` 和 = 1.0    |

> 💡 **对比看出差别**：真实数据的点积**有正有负**（`was` 是负分），权重分布也更分散。而前面那个 `[1,0]/[0,1]/[1,1]` 的例子全是非负数——这是为了展示「正交=0」这个几何性质而刻意设计的，**不代表真实分布**。

**第二步：缩放（除以 √d_k = √2 ≈ 1.414）**

```
The: 0.00 / 1.414 = 0.0000
cat: 1.00 / 1.414 = 0.7071
sat: 1.00 / 1.414 = 0.7071
```

**第三步：softmax 归一化（变成和为 1 的权重）**

**softmax 的公式**：

```
              exp(x_i)
softmax(x_i) = ─────────
               Σ exp(x_j)
                  j
```

用大白话说，**两步**：

1. 每个数取 `e 的多少次方`（`exp`，即 e^x）
2. 全部加起来，再各自除以这个总和（归一化）

**为什么要先取 exp？** 两个原因：

- **把负数变成正数**：概率不能为负，而点积分数可以是负的
- **放大差距**：`exp` 是单调递增的凸函数，大数被放得更大（`exp(2)/exp(1) ≈ 2.7`），让模型更「果断」地选择

**手算过程**（输入是第二步缩放后的 `[0.0000, 0.7071, 0.7071]`）：

```
① 取 exp：
   exp(0.0000) = 1.000000
   exp(0.7071) = 2.028101
   exp(0.7071) = 2.028101

② 求和：
   1.000000 + 2.028101 + 2.028101 = 5.056202

③ 各自除以总和：
   The: 1.000000 / 5.056202 = 0.197777  ≈ 0.1978
   cat: 2.028101 / 5.056202 = 0.401112  ≈ 0.4011
   sat: 2.028101 / 5.056202 = 0.401112  ≈ 0.4011

④ 校验：
   0.197777 + 0.401112 + 0.401112 = 1.000001 ≈ 1 ✓
```

**可运行代码**（三行）：

```python
import math

def softmax(xs):
    exps = [math.exp(x) for x in xs]   # ① 取 exp
    total = sum(exps)                   # ② 求和
    return [e / total for e in exps]    # ③ 归一化

print(softmax([0.0, 0.7071, 0.7071]))
# [0.1977767..., 0.4011116..., 0.4011116...]
```

> 💡 **注意一个实现细节**：真实代码里通常写成 `exp(x - max(x))` 而不是 `exp(x)`。因为 `exp(1000)` 会溢出成 `inf`。减去最大值不改变 softmax 结果（分子分母同乘一个常数约掉了），但能防止溢出。**这也是为什么 softmax 具有「平移不变性」：所有输入同时加一个常数，输出不变。**

> 🎯 **softmax 这个名字的由来**：它是 `argmax`（取最大值）的「软化版」——`argmax` 会输出 `[0, 0, 1]`（硬选择），softmax 输出 `[0.20, 0.40, 0.40]`（软分配）。**「soft」= 软，「max」= 取最大**：保留了「大的更大」的倾向，但不像 argmax 那样非黑即白。这让梯度可以回传（argmax 不可导，softmax 可导）。

**第四步：用权重加权求和 Value**

```
output = 0.1978 × V(The) + 0.4011 × V(cat) + 0.4011 × V(sat)
       = 0.1978 × [0.2, 0.1] + 0.4011 × [0.9, 0.3] + 0.4011 × [0.4, 0.8]
       = [0.561, 0.461]
```

> 💡 **关键理解**：`cat` 这个词的新表示 `[0.561, 0.461]`，**不再是它自己的向量，而是「按关注度混合了整句信息」的结果**。这就是为什么说「注意力让每个词都获得了上下文」——每个词的输出都包含了它认为重要的其他词的信息。

**（f）注意力权重长什么样**

实际模型中，注意力权重是一个 `n × n` 的矩阵（n = 序列长度）。**每一行是一个 softmax 的结果，所以每行加起来必定等于 1。**

> ⚠️ **下面这个矩阵同样是人为构造的示意图**，不是任何真实模型的输出。真实的注意力矩阵来自训练，而且不同层、不同头会呈现完全不同的模式（有的头关注相邻词，有的头关注句法依存，有的头几乎只关注自己）。这里只是为了展示「长什么样」而手工编排的。

```
              被关注的词
          The   cat   sat   on    the   mat
  The   [0.85  0.10  0.00  0.00  0.05  0.00]   ← 关注自己
查询 cat [0.15  0.45  0.25  0.05  0.05  0.05]   ← 关注自己 + sat（主谓）
  sat   [0.05  0.50  0.20  0.15  0.05  0.05]   ← 关注 cat（主语）
  on    [0.00  0.05  0.55  0.15  0.05  0.20]   ← 关注 sat（动词）+ mat
  the   [0.05  0.00  0.00  0.15  0.70  0.10]   ← 关注自己 + mat
  mat   [0.00  0.05  0.05  0.30  0.45  0.15]   ← 关注 on + the
```

**怎么读这张表**：

- **行** = 「谁在看」（Query 的角色）
- **列** = 「被看的是谁」（Key 的角色）
- **单元格** = 关注权重，**每行加起来 = 1.00**
- 例如第 3 行 `sat` 那行：`[0.05, 0.50, 0.20, 0.15, 0.05, 0.05]`，最大的是 `cat` 列（0.50）——说明 `sat` 主要关注 `cat`，符合「sat 的主语是 cat」这个语法事实

**能看出的规律**（示意）：

| 现象               | 体现在矩阵里                                        |
| ------------------ | --------------------------------------------------- |
| 动词关注主语       | `sat` 行在 `cat` 列权重最高（0.50）                 |
| 介词关注前面的动词 | `on` 行在 `sat` 列权重最高（0.55）                  |
| 定冠词关注后接名词 | `the` 行在 `mat` 列权重较高（0.10，相对其他远处词） |
| 虚词倾向关注自己   | `The` 行自己那列 0.85                               |

> 📌 **这也是 Transformer「可解释性更好」的来源**：可以直接看到模型在处理某个词时关注了哪些位置。

> ⚠️ **但要注意两件事**：
>
> 1. **注意力权重 ≠ 因果解释**。高权重不一定代表「因为看了这里才这样输出」——学界对此仍有争议（可参考 Jain & Wallace 2019 对注意力可解释性的质疑）。注意力更像是「信息路由」，不是「决策理由」。
> 2. **真实模型有多个头**。上面只是一张单头的示意。实际 GPT-3 每层有 96 个头，多头叠加后的模式远比这复杂，通常需要专门的工具（如 BertViz）才能可视化。

#### （3）自注意力机制（Self-Attention）

**用人话说**：在处理每个词时，**让模型看看整个句子中哪些词最重要**。

**工作流程**：

1. **线性变换**：每个词的嵌入向量通过三个权重矩阵**生成 Query（查询）、Key（键）、Value（值）**
2. **计算相关性**：用 **Query 和所有 Key 做点积，得到注意力分数**
3. **缩放与归一化**：除以 **√d_k 防止梯度消失**，再**用 softmax 归一化为概率分布**
4. **加权求和**：用**注意力权重对 Value 加权求和，得到包含上下文信息的新表示**

**公式**（理解思想即可）：

```
Attention(Q,K,V) = softmax(QK^T / √d_k) × V
```

**为什么要除以 √d_k？**
当维度 d_k 很大时，点积结果会很大，导致 softmax 梯度很小。**缩放可以稳定训练**。

**直观理解**：

- Query：我想找什么信息？
- Key：我能提供什么信息？
- Value：我实际包含的信息是什么？

#### （4）多头注意力（Multi-Head Attention）

**类比**：像雇佣**多个专家从不同角度分析问题**

- **单头**：只**关注一种关系**（如主谓关系）
- **多头**：同时**关注多种关系**（主谓、时态、指代、语义等）

**工作原理**：

1. 将 Q、K、V 分成 h 个头（通常 h=8 或 h=16）
2. 每个头独立计算注意力
3. 将所有头的输出拼接起来
4. 通过一个线性层融合信息

**优势**：

- 增强模型的表达能力
- 不同头可以学习不同的语言现象
- 类似于 CNN 中的多通道

#### （5）位置编码（Positional Encoding）

**问题**：注意力机制本身不知道词的顺序（"我爱你" 和 "你爱我" 会得到相同的表示）

**解决方案**：给每个位置的词**加上一个"位置向量"**

**两种方法**：

1. **固定位置编码**（原始 Transformer）：用正弦和余弦函数生成
   - 优点：可以处理任意长度的序列
   - 公式：PE(pos, 2i) = sin(pos/10000^(2i/d))
2. **可学习位置编码**（BERT、GPT）：作为参数训练
   - 优点：更灵活，可以学习到更复杂的位置关系
   - 缺点：受限于训练时的最大长度

**正弦/余弦公式**（原论文）：

```
PE(pos, 2i)   = sin( pos / 10000^(2i/d_model) )
PE(pos, 2i+1) = cos( pos / 10000^(2i/d_model) )
```

其中 `pos` 是词元位置（0,1,2...），`i` 是维度索引（0 到 d_model/2），`d_model` 是词嵌入维度。

> 💡 **为什么用正弦函数而不是直接用位置编号 0,1,2,3...？**
>
> 因为位置编号是无界的（序列可以无限长），但向量必须有界。正弦函数的取值在 [-1,1] 之间，且不同频率的正弦波组合能唯一编码每个位置。更妙的是：**任意两个位置的编码差值只与它们的距离有关，与绝对位置无关**——这让模型能学到「相对位置」的概念。

**现代主流替代方案**：RoPE（旋转位置编码，LLaMA/Qwen 使用）、ALiBi（线性偏置，BLOOM 使用）。它们对长文本外推更好，详见第十二章「前沿趋势」。

#### （6）前馈神经网络（FFN）

每个 Encoder / Decoder 层里，**多头注意力之后**都跟着一个**逐位置前馈网络（Position-wise Feed-Forward Network）**。

**分工**：

- **注意力层**：从**整个序列中「动态地聚合」相关信息**
- **前馈网络**：从**聚合后的信息中「提取更高阶的特征」**

**为什么叫「逐位置」**：它独立作用于序列中的**每一个**词元向量——长度为 `seq_len` 的序列，FFN 会被调用 `seq_len` 次，每次处理一个词元。**但所有位置共享同一组权重**，这既保持了独立加工能力，又大幅减少了参数量。

**结构**（两个线性变换 + 一个 ReLU）：

```
FFN(x) = max(0, x·W₁ + b₁) · W₂ + b₂
```

**关键设计：先扩大再缩小**

```
d_model (如 512)  →  d_ff (如 2048，即 4×d_model)  →  d_model (512)
                        ↑
                   中间层扩到 4 倍
```

这种「先扩大再缩小」的模式，被认为有助于模型学习更丰富的特征表示。

```python
class PositionWiseFeedForward(nn.Module):
    """位置前馈网络模块"""
    def __init__(self, d_model, d_ff, dropout=0.1):
        super().__init__()
        self.linear1 = nn.Linear(d_model, d_ff)   # 扩大 4 倍
        self.linear2 = nn.Linear(d_ff, d_model)   # 缩回原维度
        self.dropout = nn.Dropout(dropout)
        self.relu = nn.ReLU()

    def forward(self, x):
        # x 形状: (batch_size, seq_len, d_model)
        x = self.linear1(x)
        x = self.relu(x)
        x = self.dropout(x)
        x = self.linear2(x)
        return x   # 形状: (batch_size, seq_len, d_model)
```

> 🎯 **一个常被忽略的事实**：在大模型里，**FFN 的参数量通常占总参数的 2/3**（注意力层只占 1/3）。所以「模型变大」很多时候是在变大 FFN 的中间维度，而不是注意力头数。

#### （7）残差连接与层归一化（Add & Norm）

Transformer 的每个子模块（**多头注意力、前馈网络**）外面都包着一层 `Add & Norm`。**没有它，Transformer 根本训不起来**。

```
        输入 x
          │
    ┌─────┴─────┐
    │           │
    │   子模块   │  ← 如多头注意力 / FFN
    │           │
    └─────┬─────┘
          │
      x + 输出      ← ① 残差连接（Add）
          │
      LayerNorm     ← ② 层归一化（Norm）
          │
        输出
```

**① 残差连接（Add）：`Output = x + Sublayer(x)`**

把子模块的输入 `x` 直接加到它的输出上。

**解决什么问题**：深度网络的**梯度消失**。反向传播时，梯度可以绕过子模块**直接向前传播**（因为 `d(x + f(x))/dx = 1 + f'(x)`，那个常数 1 保证了梯度至少有一条畅通的路）。这让堆几十上百层成为可能。

> 💡 **一句话**：**残差连接是「深度」的许可证**。没有它，Transformer 堆到 6 层就开始退化；有了它，堆到 100 层也能训。

**② 层归一化（Norm）：让每个样本的特征均值为 0、方差为 1**

**解决什么问题**：**内部协变量偏移**（Internal Covariate Shift）——深层网络中，每层输入的分布会随着前面层参数的更新而不断变化，导致训练不稳定。

归一化让每层的输入分布保持稳定，从而**加速收敛、提高稳定性**。

**两种常见的排列顺序**（了解即可）：

| 方式          | 结构                         | 使用者                     |
| ------------- | ---------------------------- | -------------------------- |
| **Post-Norm** | `LayerNorm(x + Sublayer(x))` | 原始 Transformer、BERT     |
| **Pre-Norm**  | `x + Sublayer(LayerNorm(x))` | GPT 系列、LLaMA 等现代模型 |

> 📌 **为什么现代模型几乎都用 Pre-Norm**：Pre-Norm 把归一化放在子模块**之前**，使得残差通路上完全没有归一化操作——**梯度可以「无损」直达底层**，因此训练更稳定，不需要漫长的 warmup。代价是表达能力略弱，但换来的是可以堆更多层。

### 2.3 三种主流架构对比

#### （1）先用人话讲清楚：三种架构是三种"性格"

抛开术语，这三种架构的区别可以用**三个职业**来理解：

| 架构                | 一句话   | 类比                                                   |
| ------------------- | -------- | ------------------------------------------------------ |
| **Encoder-Only**    | 只读不写 | **阅读理解考生**：读完文章能**回答问题**，但不会写作文 |
| **Decoder-Only**    | 只写不读 | **接龙选手**：只能**顺着往下说**，但什么都能接着说     |
| **Encoder-Decoder** | 先读后写 | **翻译官**：**先完整听懂一句话，再翻译成另一种语言**   |

**换一个更具体的说法**：

```
Encoder-Only（BERT）
  "我给你一篇文章，你告诉我它讲什么"
  → 擅长「理解」，不擅长「创作」

Decoder-Only（GPT）
  "我给你一个开头，你接着往下写"
  → 擅长「创作」，理解也能兼顾（把理解当成一种"写"）

Encoder-Decoder（T5）
  "我给你一句话，你换成另一种形式还给我"
  → 专门干「转换」这件事：翻译、摘要、改写
```

#### （2）同一个任务，三种架构怎么做

用「判断这句话是正面还是负面」来演示（输入：`这个产品太棒了`）：

**Encoder-Only（BERT）**：把整句读进去，直接输出一个分类结果

```
输入：这个产品太棒了
       ↓ 双向读完整句（能看到"太棒了"和"这个产品"）
     [分类头]
       ↓
输出：正面（概率 0.97）
```

**Decoder-Only（GPT）**：把分类**当成一次续写**

```
输入：请判断情感：这个产品太棒了
      情感是：
       ↓ 从左往右生成
输出：正面
```

> 💡 注意：GPT 不是"理解后分类"，而是"**接着写出**『正面』这个词"。**这就是为什么它什么任务都能做——因为它把一切任务都改写成了「续写」。**

**Encoder-Decoder（T5）**：输入一段、输出另一段

```
输入：sentiment: 这个产品太棒了
       ↓ 编码器读完整句 → 解码器生成结果
输出：positive
```

> 🎯 **关键洞察**：三种架构都能完成这个任务，但**"怎么做"完全不同**。BERT 是"读懂再判断"，GPT 是"顺着写出来"，T5 是"格式转换"。

#### （3）能做什么、不能做什么

这是最实用的一张表：

| 任务                       | Encoder-Only<br>(BERT) | Decoder-Only<br>(GPT) | Encoder-Decoder<br>(T5) |
| -------------------------- |:----------------------:|:---------------------:|:-----------------------:|
| **文本分类**（情感、意图） | ✅ **最好**             | ⚠️ 能做，绕了一圈      | ✅ 好                    |
| **信息抽取**（人名、实体） | ✅ **最好**             | ⚠️ 能做                | ✅ 好                    |
| **文本检索**（语义搜索）   | ✅ **最好**             | ⚠️ 不擅长              | ✅ 好                    |
| **对话聊天**               | ❌ 不能                 | ✅ **最好**            | ⚠️ 能做                  |
| **写作续写**               | ❌ 不能                 | ✅ **最好**            | ⚠️ 能做                  |
| **代码生成**               | ❌ 不能                 | ✅ **最好**            | ⚠️ 能做                  |
| **翻译**                   | ❌ 不能                 | ⚠️ 能做                | ✅ **最好**              |
| **摘要**                   | ⚠️ 只能做"抽取式"       | ✅ 好                  | ✅ **最好**              |

**记住这个规律**：

- **只需要"判断"的** → Encoder-Only 最省成本（它不用生成，速度快）
- **需要"创作"的** → Decoder-Only
- **需要"整段换整段"的** → Encoder-Decoder

> 📌 **但现实中**：今天的 GPT-4 / Claude / Qwen 已经强到**用 Decoder-Only 就能做好几乎所有任务**，所以这张表的"最好"更多是**理论上的性价比**，而不是"别的做不了"。这也是 Decoder-Only 胜出的现实原因之一。

#### （4）Encoder-Only（编码器）：阅读理解专家

**代表模型**：BERT、RoBERTa、ALBERT

**结构特点**：只用 Transformer 的编码器部分，**双向注意力**——每个词都能看到左边和右边的所有词。

**为什么双向？** 因为它的任务是「理解」。理解一句话时，你当然希望前后文都能看：

```
"苹果公司发布了新产品"
      ↑ 判断"苹果"是水果还是公司，要看后面的"公司"和"发布"
```

**优点**：

- 双向上下文，语言理解效果好
- 不用生成，**推理速度快**（一次前向就出结果）
- 输出的是固定向量，方便接下游任务

**缺点**：

- 使用 `[MASK]` 特殊符号，导致**预训练-微调不一致**（训练时有 mask，实际使用时没有）
- 假设所有被 mask 的 token **相互独立**，忽略了它们之间的关联
- **不天然适合生成**（训练时看得到答案，见 1.7 节的详细解释）

**今天还用吗？** 用，但场景很窄：

- 语义检索 / 向量数据库（Sentence-BERT 系列）
- 需要极低延迟的分类、打标签
- 对成本敏感的批量处理

#### （5）Decoder-Only（解码器）：接龙冠军

**代表模型**：GPT 系列、LLaMA、Qwen、DeepSeek

**结构特点**：只用 Transformer 的解码器部分，**单向注意力**——每个词只能看到它左边的词。

**核心思想**：只保留解码器，专注于"预测下一个词"

**关键机制**：因果掩码注意力（Causal/Masked Attention）

- 保证预测第 t 个词时，只能看到前 t-1 个词
- 就像考试时把后面的答案遮住
- 通过上三角掩码矩阵实现

**优势**：

- 结构简单，易于扩展到巨大规模（千亿参数）
- 天然适合生成任务（对话、写作、代码）
- 训练目标统一（语言建模）
- 可以通过 Prompt 完成各种任务（零样本学习）

**缺点（需要知道的另一面）**：

- **单向建模**：难以同时利用双向上下文，理解类任务（如分类、抽取）不如编码器模型
- **信息利用效率低**：每个 token 只见过它左边的上下文，同样的数据量学到的东西比双向模型少
- **本质是"概率续写"**：不区分"真实"与"常见"，这也是幻觉的根源之一

**为什么成为主流？**（这是全章最重要的一个"为什么"）

| 原因                 | 通俗解释                                              |
| -------------------- | ----------------------------------------------------- |
| **一个模型干所有事** | 不用为每个任务换架构，省了工程复杂度                  |
| **训练信号最密集**   | 每个位置都是监督信号，同样的数据学得最充分            |
| **训练和使用一致**   | 训练时怎么学，推理时就怎么用，没有"gap"               |
| **规模最容易扩**     | 结构简单，堆层数、加参数都很直接                      |
| **能吃到规模红利**   | 涌现能力（In-Context Learning、思维链）在它身上最明显 |

> 🎯 **一句话总结**：**它不是因为"更强"而赢，而是因为"更统一"而赢**。统一意味着一个模型、一套训练流程、一套部署方案——**工程上的简洁性最终战胜了理论上的最优性**。

#### （6）Encoder-Decoder（编码器-解码器）：翻译官

**代表模型**：T5、BART

**结构特点**：完整的 Transformer——编码器**双向**读输入，解码器**单向**生成输出，中间用**交叉注意力**连接（见 2.4 节）。

**为什么需要"两段"？** 因为有些任务天然是"输入"和"输出"两种不同的东西：

```
输入（中文）→ 输出（英文）        ← 翻译
输入（长文）→ 输出（摘要）        ← 摘要
输入（问题）→ 输出（答案）        ← 问答
```

**优点**：

- **理解**和**生成**各自用最合适的结构
- 交叉注意力让解码器能"有选择地参考"输入
- 适合明确的"输入→输出"映射任务

**缺点**：

- 结构复杂，参数多，训练和部署成本高
- 需要维护两套组件
- 泛化到"任意任务"不如 Decoder-Only 灵活

**今天还用吗？** 用得少了，但没消失：

- 专门的翻译模型（如某些商业翻译引擎）
- 语音识别（Whisper 就是 Encoder-Decoder）
- 需要严格控制"输出必须基于输入"的场景

#### （7）三者终极对比

| 维度         | Encoder-Only      | Decoder-Only            | Encoder-Decoder     |
| ------------ | ----------------- | ----------------------- | ------------------- |
| **一句话**   | 只读不写          | 只写不读                | 先读后写            |
| **类比**     | 阅读理解考生      | 接龙选手                | 翻译官              |
| **代表**     | BERT、RoBERTa     | GPT、LLaMA、Qwen        | T5、BART            |
| **注意力**   | 双向              | 单向（因果掩码）        | 编码双向 + 解码单向 |
| **训练目标** | 去噪自编码（MLM） | 自回归生成              | 序列到序列          |
| **擅长**     | 理解、判断、检索  | 生成、对话、代码        | 翻译、摘要          |
| **能否生成** | ❌                 | ✅                       | ✅                   |
| **推理速度** | 快                | 慢（要逐个 token 生成） | 中                  |
| **主流程度** | ⚠️ 特定场景        | ✅ **绝对主流**          | ⚠️ 特定场景          |

#### （8）为什么最后是 Decoder-Only 赢了

这不是技术优劣的简单比较，而是**三个层面**的胜利：

**① 训练层面：信号密度**

|                              | BERT                | GPT                      |
| ---------------------------- | ------------------- | ------------------------ |
| 一句话有几个位置产生监督信号 | 只有被 mask 的 ~15% | **100%（每个位置都是）** |
| 同样数据学到的信息量         | 少                  | **多**                   |

**② 使用层面：任务统一**

```
BERT 时代：
  情感分析 → 训一个 BERT
  实体识别 → 又训一个 BERT
  问答系统 → 再训一个 BERT
  （每个任务一个模型 + 一份标注数据）

GPT 时代：
  所有任务 → 改 Prompt → 同一个模型
```

**③ 工程层面：规模化**

Decoder-Only 结构简单，**同样的工程量能堆出更大的模型**。而规模又带来了涌现能力——**形成正循环**。

> 📜 **产业史小注**：约 2021 年之前，编码器与编解码模型的衍生版本不断出现，学界称这一时期为 **"BERTology"**；2021 年之后，解码器模型飞速发展，进入 "Next-Level" 的生成式大模型时代。这个转向不是因为 BERT 不好，而是因为**生成比判别更接近通用任务**。

> 🎯 **最后一句总结**：**Encoder-Only 解决了"理解"，Encoder-Decoder 解决了"转换"，而 Decoder-Only 用"生成"这一个动作，把前两者的活儿都干了。**

### 2.4 完整数据流：一个句子如何穿过 Transformer

把前面所有组件串起来，看一遍完整流程。以「翻译」任务为例：

```
输入："The house is wonderful"
                │
        ┌───────▼────────┐
        │  ① 词嵌入        │  每个词 → 一个稠密向量（1.3 节）
        └───────┬────────┘
                │
        ┌───────▼────────┐
        │  ② 位置编码      │  加上位置信息，让模型知道顺序
        └───────┬────────┘
                │
    ╔═══════════▼═══════════════════╗
    ║   编码器（Encoder）× N 层      ║
    ║  ┌──────────────────────────┐  ║
    ║  │ ③ 多头自注意力            │  ║
    ║  │   ↓ Add & Norm           │  ║
    ║  │ ④ 前馈网络 FFN            │  ║
    ║  │   ↓ Add & Norm           │  ║
    ║  └──────────────────────────┘  ║
    ║   输出：每个词的「上下文表示」   ║
    ╚═══════════╤═══════════════════╝
                │  （这份记忆被传给解码器）
    ╔═══════════▼═══════════════════╗
    ║   解码器（Decoder）× N 层      ║
    ║  ┌──────────────────────────┐  ║
    ║  │ ⑤ 掩码多头自注意力         │  ║  ← 只看已生成的部分
    ║  │   ↓ Add & Norm           │  ║
    ║  │ ⑥ 交叉注意力（Cross-Attn） │  ║  ← 查询编码器的输出
    ║  │   ↓ Add & Norm           │  ║
    ║  │ ⑦ 前馈网络 FFN            │  ║
    ║  │   ↓ Add & Norm           │  ║
    ║  └──────────────────────────┘  ║
    ╚═══════════╤═══════════════════╝
                │
        ┌───────▼────────┐
        │  ⑧ 线性层 + Softmax│  映射到词表，得到每个词的概率
        └───────┬────────┘
                │
        输出："Das Haus ist wunderschön"
```

**每一步在做什么**：

| 步骤 | 组件           | 作用                           | 对应小节  |
| ---- | -------------- | ------------------------------ | --------- |
| ①    | 词嵌入         | 离散的词 → 稠密向量            | 1.3       |
| ②    | 位置编码       | 注入顺序信息                   | 2.2(4)    |
| ③    | 多头自注意力   | 让每个词看到全句其他词         | 2.2(2)(3) |
| ④    | 前馈网络       | 提取高阶特征                   | 2.2(5)    |
| ⑤    | 掩码自注意力   | 只看已生成部分（因果掩码）     | 2.3(2)    |
| ⑥    | **交叉注意力** | 解码器「查询」编码器的理解结果 | 见下      |
| ⑦    | 前馈网络       | 提取高阶特征                   | 2.2(5)    |
| ⑧    | 线性 + Softmax | 输出词表上的概率分布           | —         |

**⑥ 交叉注意力（Cross-Attention）是什么**

这是 Encoder-Decoder 架构独有的机制，也是它区别于 Decoder-Only 的关键：

|           | 自注意力（Self-Attention）     | 交叉注意力（Cross-Attention）              |
| --------- | ------------------------------ | ------------------------------------------ |
| Q 来自    | 自己                           | **解码器**                                 |
| K、V 来自 | 自己                           | **编码器输出**                             |
| 含义      | 「我这个句子内部，谁和谁相关」 | 「我当前要生成的内容，该参考输入的哪部分」 |

用翻译来理解：解码器要生成「Haus」，它通过交叉注意力去「查询」编码器——**编码器里哪几个词（The / house）对当前这个输出最重要？**

> 📌 **Decoder-Only 没有交叉注意力**，因为它没有编码器。它把「理解输入」和「生成输出」合并成同一件事——输入也是序列的一部分，直接接在自注意力里。**这个简化是 GPT 能统一所有任务的结构基础。**

> 🎯 **回到 2.3 的三分法**：三种架构的差别，本质就是「保留了上面流程的哪几块」：
>
> - **Encoder-Only（BERT）**：只留 ①②③④，双向理解，不生成
> - **Decoder-Only（GPT）**：只留 ①⑤⑦⑧，单向生成，不需要理解阶段
> - **Encoder-Decoder（T5）**：全部保留，先理解再生成

### 2.5 参数量怎么算：为什么说注意力只占三分之一

这是理解「大模型到底大在哪」的关键，也是面试常考点。

**单层 Transformer 的参数量**（以 d_model = d、层数 = 1 为例）：

| 组件             | 参数构成                  | 参数量     |
| ---------------- | ------------------------- | ---------- |
| **自注意力**     | W_Q、W_K、W_V、W_O 各 d×d | **4d²**    |
| **前馈网络 FFN** | 两个线性层 d→4d→d         | **8d²**    |
| **层归一化**     | 2 个 × 2d                 | 4d         |
| **合计**         |                           | **≈ 12d²** |

**结论：FFN 占 8/12 ≈ 67%，注意力占 4/12 ≈ 33%。**

**用真实模型验证**（GPT-3 175B，d_model=12288，96 层）：

```
每层 ≈ 12 × 12288² ≈ 1.81B
96 层 ≈ 174B
加上词嵌入（50257 × 12288 ≈ 0.62B）
总计 ≈ 175B ✓
```

> 💡 **这解释了几件事**：
>
> 1. **为什么「加宽」比「加头」有效**：加宽 d_model 会让 FFN 的 8d² 同步变大
> 2. **为什么 MoE 能省算力**：MoE 主要把 FFN 拆成多个专家，每次只激活少数几个——**因为 FFN 才是参数大头**
> 3. **为什么推理时 FFN 是计算瓶颈**：每个 token 都要过一遍巨大的 FFN

### 2.6 从 Transformer 到现代大模型：改了什么

原始 Transformer（2017）和今天的 GPT-4 / LLaMA 差别已经很大。主要改动：

| 组件           | 原始 Transformer（2017） | 现代大模型（2024+）          | 改动原因               |
| -------------- | ------------------------ | ---------------------------- | ---------------------- |
| **整体架构**   | Encoder-Decoder          | **Decoder-Only**             | 统一任务形式，简化结构 |
| **归一化位置** | Post-Norm                | **Pre-Norm**（RMSNorm）      | 训练更稳定，可堆更多层 |
| **归一化方法** | LayerNorm                | **RMSNorm**                  | 少算均值，速度更快     |
| **位置编码**   | 正弦/余弦（固定）        | **RoPE**（旋转位置编码）     | 长文本外推更好         |
| **激活函数**   | ReLU                     | **SwiGLU**                   | 效果更好               |
| **注意力**     | 标准 MHA                 | **GQA / MQA**（分组/多查询） | 大幅减少 KV cache 显存 |
| **FFN**        | 稠密                     | **MoE**（混合专家）          | 参数大但激活少         |
| **偏置项**     | 有 bias                  | 多数去掉 bias                | 略快、略稳             |

> 🎯 **一句话**：**骨架没变（还是注意力 + FFN + 残差 + 归一化），变的是每个零件的材料和装配方式。** 理解原始 Transformer 的每个组件，才能看懂现代模型的改进点在哪。

## 路线 2：规模化训练与通用能力

> 模型结构只是起点；训练循环、缩放规律和大规模预训练共同带来通用能力。

### 2.7 训练过程：模型是怎么学出来的

> 📌 前面讲了 Transformer 的「零件」，但没讲这些零件的**参数是怎么从数据里学到的**。这一节补上，因为文档里很多现象（为什么除以 √d_k、为什么用 Pre-Norm、为什么训练要 3 倍显存）都需要训练知识才能理解。

#### （1）一个训练循环的四个步骤

所有神经网络训练，本质上都是这四步的循环：

```
① 前向传播（Forward）    输入 → 逐层计算 → 得到预测
         ↓
② 算损失（Loss）         预测 vs 真实答案 → 差多少
         ↓
③ 反向传播（Backward）   算出「每个参数该往哪调」→ 梯度
         ↓
④ 更新参数（Update）     按梯度调整参数
         ↓
    重复千万次，直到损失降不下去
```

#### （2）前向传播：从输入到预测

**定义**：输入数据**沿着网络正向流动**，每层做一次变换，最终得到输出。

```
x → [层1] → h₁ → [层2] → h₂ → ... → [层N] → y（预测值）
```

**一个手算例子**（极简网络：2 个输入 → 1 个隐藏单元 → 1 个输出）：

假设：

```
输入   x = [1.0, 2.0]
权重   W₁ = [0.5, 0.3]      （隐藏层）
       W₂ = 2.0             （输出层）
目标值 t = 3.0               （正确答案）
```

**前向计算**：

```
① 加权求和：  z = 1.0×0.5 + 2.0×0.3 = 1.1
② 激活函数：  h = ReLU(1.1) = 1.1        ← ReLU(x)=max(0,x)，正数不变
③ 输出层：    y = h × W₂ = 1.1 × 2.0 = 2.2
④ 算损失：    L = (y - t)² / 2 = (2.2-3.0)²/2 = 0.32
```

**结论**：预测 2.2，正确答案 3.0，**差 0.8，损失 0.32**。接下来要调整参数让损失变小。

> 💡 **为什么要「/2」**：因为求导时 `(x²/2)' = x`，正好把 2 约掉，公式更简洁。这是工程习惯，不影响优化方向。

#### （3）损失函数：怎么量化「错得有多离谱」

上面用的 **MSE（均方误差）** 是回归任务的常用损失。**语言模型用的是交叉熵（Cross-Entropy）**：

```
L = -log P(正确词)
```

**为什么用交叉熵而不是 MSE？**

|                    | MSE                    | 交叉熵                                                                       |
| ------------------ | ---------------------- | ---------------------------------------------------------------------------- |
| 衡量什么           | 数值距离               | **概率分布的差异**                                                           |
| 适合               | 回归（预测房价、温度） | **分类**（预测下一个词）                                                     |
| 语言模型为什么用它 | —                      | 模型输出的是「词表上每个词的概率」，交叉熵直接衡量「给正确词的概率够不够高」 |

**具体到语言模型**：假设词表里正确答案是 `agent`，模型给它的概率是 0.7：

```
L = -log(0.7) = 0.357

如果模型给 agent 的概率只有 0.01：
L = -log(0.01) = 4.605     ← 损失大得多，惩罚更重
```

> 🎯 **这就是为什么语言模型的 Loss 通常报 2~4 这种数**——它是对数尺度。Loss 从 4 降到 2，意味着模型给正确答案的概率从 `e^-4 ≈ 1.8%` 提升到了 `e^-2 ≈ 13.5%`，**实际能力提升非常大**。

#### （4）反向传播：梯度是怎么算出来的

**核心问题**：损失 L 是所有参数共同作用的结果，怎么知道**每个参数**该往哪个方向调？

**答案：链式法则（求导版）**。

如果你有 `L = f(g(h(x)))`，那么：

```
dL/dx = dL/df × df/dg × dg/dh × dh/dx
```

**「反向」的含义**：从损失往回推，一层层算梯度。因为要先知道「输出层该怎么调」，才能推算「上一层该怎么调」。

**接着上面的手算例子**（目标：算 `dL/dW₂` 和 `dL/dW₁`）：

```
【第 1 步】损失对输出的梯度
  dL/dy = y - t = 2.2 - 3.0 = -0.80
  含义：y 增大 1，L 就减小 0.8 → y 应该增大

【第 2 步】输出对 W₂ 的梯度
  dL/dW₂ = dL/dy × h = -0.80 × 1.1 = -0.88

【第 3 步】损失对隐藏层的梯度
  dL/dh = dL/dy × W₂ = -0.80 × 2.0 = -1.60

【第 4 步】穿过 ReLU
  dL/dz = dL/dh × ReLU'(z) = -1.60 × 1 = -1.60
  （ReLU 的导数：z>0 时为 1，z<0 时为 0）

【第 5 步】隐藏层对 W₁ 的梯度
  dL/dW₁ = dL/dz × x = -1.60 × [1.0, 2.0] = [-1.60, -3.20]
```

**梯度的含义**：

- `dL/dW₂ = -0.88`：W₂ 增大，L 会减小。所以 **W₂ 应该增大**
- `dL/dW₁ = [-1.60, -3.20]`：W₁ 的两个分量都应该增大，第二个分量影响更大

> 💡 **为什么叫「反向」传播**：注意计算顺序是 `L → y → h → z → W₁`，**和 forward 的方向正好相反**。这不是巧合——因为链式法则要求从最外层开始逐层往里乘。

#### （5）参数更新：梯度下降

有了梯度，更新规则非常简单：

```
新参数 = 旧参数 - 学习率 × 梯度
W ← W - η × dL/dW
```

**为什么要减而不是加？** 因为梯度指向「损失增大最快的方向」，我们要**减小损失**，所以往反方向走——这就是「**梯度下降**」。

**接着算**（学习率 η = 0.01）：

```
W₂_new = 2.0 - 0.01 × (-0.88) = 2.0088
W₁_new = [0.5 - 0.01×(-1.60),  0.3 - 0.01×(-3.20)]
       = [0.5160, 0.3320]
```

**更新后再前向一次**：

```
z = 1.0×0.5160 + 2.0×0.3320 = 1.1800
h = 1.1800
y = 1.1800 × 2.0088 = 2.3704
L = (2.3704 - 3.0)²/2 = 0.1982

损失从 0.3200 降到 0.1982，下降 38.06% ✓
```

> 🎯 **这就是「学习」的全过程**：一次前向 + 一次反向 + 一次更新，损失就降了 38%。真实训练就是这个过程重复**几十万到几百万次**，只不过参数是千亿个而不是 3 个。

#### （6）学习率：最重要的超参数

| 学习率 η                   | 后果                                     |
| -------------------------- | ---------------------------------------- |
| **太大**（如 1.0）         | 一步迈过最优解，损失来回震荡甚至变成 NaN |
| **太小**（如 1e-8）        | 每步几乎不动，训练几天也没进展           |
| **合适**（如 1e-4 ~ 1e-3） | 稳定下降                                 |

**实际训练常用「学习率调度」**：

```
warmup（预热）        →  稳定期        →  衰减期
从 0 线性升到 1e-4      保持 1e-4        余弦衰减到 1e-5
```

> 📌 **为什么需要 warmup**：训练初期参数是随机的，梯度方向不可靠。如果一上来就用大学习率，可能一步把参数推到很糟的位置（甚至梯度爆炸）。**先小步走稳了再加速**，这就是 warmup 的作用。

#### （7）优化器：比朴素梯度下降更聪明

朴素梯度下降（SGD）只用当前梯度，容易震荡。实际训练几乎都用 **Adam / AdamW**：

| 优化器             | 核心改进                                                                                             |
| ------------------ | ---------------------------------------------------------------------------------------------------- |
| **SGD**            | 只用当前梯度：`W ← W - η·g`                                                                          |
| **SGD + Momentum** | 累积历史梯度，像小球滚下山有惯性                                                                     |
| **Adam**           | 同时用**一阶动量**（梯度的滑动平均）+ **二阶动量**（梯度平方的滑动平均），给每个参数**自适应学习率** |
| **AdamW**          | Adam + 正确的权重衰减（weight decay），大模型标配                                                    |

> 💡 **Adam 的关键贡献：每个参数有自己的学习率**。梯度一直很大的参数会自动减小步长，梯度一直很小的参数会自动加大步长。这让训练对超参数不敏感得多。

**这也是为什么训练显存是推理的 3 倍多**：

| 需要存的东西         | 大小                        |
| -------------------- | --------------------------- |
| 模型参数             | 1×                          |
| 梯度（每个参数一份） | 1×                          |
| Adam 一阶动量 m      | 1×                          |
| Adam 二阶动量 v      | 1×                          |
| **合计**             | **≈ 4×（混合精度下约 3×）** |

> 🎯 这就解释了 6.1 节那张表：为什么 Qwen2-72B 推理要 143G，微调要 156G——因为微调要多存梯度、动量、激活值。

#### （8）梯度消失与梯度爆炸

**问题根源：链式法则是连乘**。

假设一个 10 层的网络，每层梯度都是 0.5：

```
dL/dW₁ = 0.5 × 0.5 × 0.5 × ... × 0.5 = 0.5¹⁰ ≈ 0.00098   ← 几乎为 0，学不动
```

如果每层梯度都是 2：

```
2¹⁰ = 1024   ← 数值爆炸，训练崩溃
```

| 现象         | 原因            | 后果                   | 缓解方法                                  |
| ------------ | --------------- | ---------------------- | ----------------------------------------- |
| **梯度消失** | 连乘小于 1 的数 | 浅层学不动，深层白学   | 残差连接、归一化、ReLU 替代 sigmoid       |
| **梯度爆炸** | 连乘大于 1 的数 | 参数变成 NaN，训练崩溃 | **梯度裁剪**（gradient clipping）、归一化 |

**三种缓解手段的原理**：

**① 残差连接**（2.2 节讲过）

```
y = x + f(x)   →   dy/dx = 1 + f'(x)
```

那个 **常数 1** 保证了梯度至少有「一条直通的路」——不管 f'(x) 多小，梯度都不会归零。

**② 归一化（LayerNorm / RMSNorm）**

每层输出都归一化到固定分布，避免数值在层间累积放大或缩小。

**③ 梯度裁剪**

```python
# 如果梯度范数超过阈值，就等比缩小
if grad_norm > max_norm:      # 如 max_norm = 1.0
    grad = grad * (max_norm / grad_norm)
```

简单粗暴但极其有效，几乎所有大模型训练都用。

#### （9）一个最小可运行的训练循环

把上面所有内容串成代码：

```python
import torch
import torch.nn as nn

model = nn.Sequential(
    nn.Linear(2, 1),      # 简化版：2 维输入 → 1 维输出
    nn.ReLU(),
    nn.Linear(1, 1),
)
optimizer = torch.optim.AdamW(model.parameters(), lr=1e-3)
loss_fn = nn.MSELoss()

for step in range(1000):
    x = torch.randn(32, 2)          # ① 造一批数据（batch=32）
    t = (x[:, 0] * 2 + x[:, 1] * 3).unsqueeze(1)   # 真实关系：2x₁+3x₂

    y = model(x)                     # ② 前向传播
    loss = loss_fn(y, t)             # ③ 算损失

    optimizer.zero_grad()            # ④ 清空上一步的梯度（重要！）
    loss.backward()                  # ⑤ 反向传播，自动算梯度
    optimizer.step()                 # ⑥ 更新参数

    if step % 200 == 0:
        print(f"step {step:4d}  loss={loss.item():.6f}")
```

输出大致是：

```
step    0  loss=12.345678
step  200  loss=0.023456
step  400  loss=0.001234
step  600  loss=0.000089
step  800  loss=0.000012
```

> ⚠️ **`optimizer.zero_grad()` 为什么必须有**：PyTorch 的梯度默认是**累加**的。如果不清空，第二步的梯度会加上第一步的，等于用了错误的方向。这是新手最常见的 bug 之一。

#### （10）训练 vs 推理：为什么成本差这么多

|              | 训练（Training）     | 推理（Inference）    |
| ------------ | -------------------- | -------------------- |
| 前向传播     | ✅ 要                 | ✅ 要                 |
| 反向传播     | ✅ 要（贵）           | ❌ 不要               |
| 存梯度/动量  | ✅ 要                 | ❌ 不要               |
| 存激活值     | ✅ 要（反向传播要用） | ❌ 不要（可即时释放） |
| 显存占用     | **≈ 4× 模型大小**    | ≈ 1× 模型大小        |
| 是否更新参数 | ✅ 更新               | ❌ 冻结               |
| 典型耗时     | 几天到几个月         | 毫秒到秒             |

> 🎯 **一句话**：**推理只需要「算一遍」，训练需要「算一遍 + 往回推一遍 + 存一堆中间结果」**。这就是为什么微调比推理贵得多，也是为什么大多数人应该用 API 而不是自己训练。

### 5.1 缩放法则（Scaling Laws）

**前提：预训练的三要素**

在讲幂律关系之前，先明确预训练到底在烧什么。大模型预训练 = **算法 + 数据 + 算力**，三者缺一不可：

| 要素     | 内容                                      | 瓶颈表现                                        |
| -------- | ----------------------------------------- | ----------------------------------------------- |
| **算法** | Transformer 架构、优化器、并行策略        | 架构落后则同样算力训不出同等效果                |
| **数据** | 千亿到万亿 token 的文本、代码、图书、网页 | 数据不够则模型“学不饱”（Chinchilla 定律的核心） |
| **算力** | 千卡到万卡 GPU 集群，月级训练时间         | 算力不足则连实验都跑不起来                      |

> 📌 **一个常见误解**：以为大模型只是“堆参数”。实际上三要素中**数据往往是最先成为瓶颈的那个**——这也是 Chinchilla 定律能推翻“堆参数”思路的原因。

**核心发现**：模型性能（Loss）与三个因素呈幂律关系

**1. 参数量（N）**

```
L(N) ∝ N^(-α)  (α ≈ 0.076)
```

参数越多，性能越好，但收益递减

**2. 训练数据量（D）**

```
L(D) ∝ D^(-β)  (β ≈ 0.095)
```

数据越多，性能越好

**3. 计算资源（C）**

```
L(C) ∝ C^(-γ)
```

计算量越大，性能越好

**关键洞察**：

- 三个因素中，任何一个成为瓶颈都会限制性能
- 最优策略是平衡三者的投入

**Chinchilla 定律（2022）**：

- 传统做法：大模型 + 少数据（如 GPT-3：175B 参数，300B tokens）
- Chinchilla 发现：对于给定的计算预算，应该"中等模型 + 大数据"
- 公式：数据量应约为参数量的 20 倍，即 **D ≈ 20N**
  - 例：70B 参数配 1.4T tokens（70B × 20 = 1.4T）
  - 讲义口径："10B 模型用 200B tokens（1:20）"，与上式一致
- 实例：Chinchilla（70B 参数，1.4T tokens）性能超过 Gopher（280B 参数，300B tokens）

**涌现能力（Emergent Abilities）**：
当模型达到一定规模（通常 > 60B），会突然出现新能力：

- **上下文学习（In-Context Learning）**：从示例中学习，无需微调
- **链式思考（Chain-of-Thought）**：展示推理步骤
- **指令遵循（Instruction Following）**：理解并执行复杂指令
- **多步推理**：解决需要多步骤的问题
- **代码生成与理解**：编写和调试代码

**争议**：
有研究认为"涌现"可能是评估指标的产物，而非真正的相变

### 1.7 大规模语言模型：通用任务求解器

#### （0）解决的问题：微调范式的不可扩展性

1.5 节留下的三个局限，构成了向这一代跃迁的动机：

| 1.5 节的局限   | 后果                         | 这一代怎么解决                     |
| -------------- | ---------------------------- | ---------------------------------- |
| 微调成本高     | 每个任务要存一份完整模型副本 | **提示学习**：不改参数             |
| 泛化靠「专」   | 一个模型只会一个任务         | **通用求解器**：一个模型做所有任务 |
| 规模未到临界点 | 亿级参数，无涌现能力         | **扩到千亿**（GPT-3 175B）         |

**三条路径同时突破**：

| 维度         | 变化                        | 效果                           |
| ------------ | --------------------------- | ------------------------------ |
| **参数规模** | 亿级 → 千亿级（GPT-3 175B） | 容量足够装下世界知识           |
| **数据规模** | 十亿 → 万亿 token           | 覆盖多领域、多语言、多任务形式 |
| **使用方式** | 微调 → **提示（Prompt）**   | 不改一个参数就能换任务         |

> 📌 **这三条路径是「乘法关系」而非「加法关系」**：参数变大但数据不够 → 学不饱（Chinchilla 定律）；数据够但不会提示 → 用不起来；会提示但模型太小 → 没能力可激活（1.6 节的 10B 门槛）。**三者必须同时到位，才会出现「通用求解器」这个结果。**

#### （1）分水岭：两类模型到底差在哪

把 1.5 和 1.7 的差异集中到一张表，这是整章最值得记住的一张：

| 维度             | 预训练语言模型（中小模型）                | 大规模语言模型（生成式大模型）    |
| ---------------- | ----------------------------------------- | --------------------------------- |
| **典型模型**     | ELMo、BERT、GPT-1/2                       | GPT-3、ChatGPT、LLaMA             |
| **模型结构**     | RNN、Transformer                          | Transformer                       |
| **注意力机制**   | 双向、单向                                | 单向                              |
| **训练方式**     | **去噪自编码**（Denoising Auto-encoding） | **自回归生成**（Auto-regressive） |
| **擅长任务**     | 理解、判断                                | 生成                              |
| **模型规模**     | 约 **10B 以下**                           | 约 **10B - 100B 及以上**          |
| **下游应用方式** | 微调（Fine-tuning）                       | 微调 **& 提示学习**               |
| **涌现能力**     | 小数据领域迁移                            | 上下文学习、思维链提示            |

> 📌 表里「训练方式」这一行（去噪自编码 vs 自回归生成）是最本质的差异，**下面单独展开讲清楚**。

##### 深入理解：去噪自编码 vs 自回归生成

这两个术语听起来很学术，其实可以用一句话概括区别：

> **去噪自编码：把挖空的句子补回来。**
> **自回归生成：接着往下写。**

**（a）自回归生成（Auto-regressive）—— GPT 系**

**定义**：给定前文，预测下一个词；然后把预测出的词拼到前文后面，继续预测下一个。**一次一步，步步向前**。

```
训练时的样本（不需要人工标注，原文本身就是答案）：

输入：Datawhale Agent is
目标：a

输入：Datawhale Agent is a
目标：powerful

输入：Datawhale Agent is a powerful
目标：agent
```

**训练目标（数学形式）**：

```
L = -Σ log P(w_t | w_1, ..., w_{t-1})
     t
```

即：把一句话里每个位置都当成一次「预测下一个词」的训练，**一次前向传播就能算出所有位置的损失**（并行计算，但每个位置只看左边）。

**关键约束：因果掩码（Causal Mask）**

训练时整句话是一次性送进模型的，如果不加限制，预测第 t 个词时就会「偷看」到第 t+1 个词。因果掩码用一个上三角矩阵把「未来」位置的注意力分数设成 `-∞`，softmax 后变成 0：

```
        看得到的位置
        w1  w2  w3  w4
w1  [   ✓   ✗   ✗   ✗  ]      ✗ = -∞（被屏蔽）
w2  [   ✓   ✓   ✗   ✗  ]
w3  [   ✓   ✓   ✓   ✗  ]
w4  [   ✓   ✓   ✓   ✓  ]
```

> 🎯 **因果掩码是「训练方式」和「使用方式」一致性的保证**：训练时每个位置只能看左边，生成时也只有左边可用。**这个一致性是自回归模型能稳定工作的核心**。

**（b）去噪自编码（Denoising Auto-encoding）—— BERT 系**

**定义**：把句子里的某些词「挖掉」（替换成 `[MASK]`），让模型**根据上下文把原词还原出来**。

```
原始句子：Datawhale Agent is a powerful agent

挖空后：  Datawhale [MASK] is a [MASK] agent
                    ↓            ↓
模型要猜：        Agent       powerful
```

**训练目标（数学形式）**：

```
L = -Σ log P(w_masked | 上下文中的所有其他词)
   masked位置
```

注意：这里的条件不是「前面的词」，而是「**所有没被挖掉的词**」——左右都能看。

**关键特征：双向注意力（无掩码）**

```
        看得到的位置
        w1  w2  w3  w4
w1  [   ✓   ✓   ✓   ✓  ]      没有屏蔽，全都能看
w2  [   ✓   ✓   ✓   ✓  ]
w3  [   ✓   ✓   ✓   ✓  ]
w4  [   ✓   ✓   ✓   ✓  ]
```

> ⚠️ **这就是为什么 BERT 不能直接用来生成**：训练时它已经习惯了「看到右边」，而生成时右边根本不存在。让它生成就像**让一个习惯了看答案的人闭卷考试**——它没有学过「只有左边时该怎么办」。

**（c）为什么叫「去噪」自编码？**

这个名字来自它的思想源头：

```
自编码器（Auto-encoder）：输入 x → 编码 → 解码 → 还原 x
去噪自编码（Denoising） ：输入 x + 噪声 → 编码 → 解码 → 还原干净的 x
```

BERT 的 MLM 正是这个思路：**「挖空」就是「加噪声」，「猜回原词」就是「去噪」**。模型必须学会理解语义才能还原，因此学到了有用的语言表示。

**（d）一张表看清区别**

|                        | **去噪自编码**（BERT 系）          | **自回归生成**（GPT 系）         |
| ---------------------- | ---------------------------------- | -------------------------------- |
| **一句话概括**         | 把挖空的句子补回来                 | 接着往下写                       |
| **看得到多少上下文**   | **双向**（左右都能看）             | **单向**（只能看左边）           |
| **训练信号从哪来**     | 被 `[MASK]` 遮住的原词             | 序列中下一个真实的词             |
| **一次训练用几个位置** | 只有被 mask 的 ~15% 位置           | **所有位置**（每个位置都是样本） |
| **注意力掩码**         | 无（全连接）                       | 因果掩码（上三角）               |
| **训练与使用是否一致** | ❌ 不一致（训练有 mask，使用没有）  | ✅ 一致（都是只看左边）           |
| **擅长**               | 理解：分类、抽取、检索、句对匹配   | 生成：续写、对话、代码           |
| **能否直接生成**       | ❌ 不能（没见过「只有左边」的情形） | ✅ 天然可以                       |
| **训练效率**           | 低（每句只用 15% 的位置做监督）    | 高（每个位置都是监督信号）       |
| **代表**               | BERT、RoBERTa、ALBERT、ELECTRA     | GPT 系列、LLaMA、Qwen、DeepSeek  |

**（e）一个直觉类比**

|                | 类比                                                                                                             |
| -------------- | ---------------------------------------------------------------------------------------------------------------- |
| **去噪自编码** | **完形填空考试**：给你一段挖了空的文章，要求根据上下文填空。你能看到前后文，但你的任务是「还原」，不是「续写」。 |
| **自回归生成** | **文字接龙**：给你开头，你要一个词一个词往下写。你只能看到已经写出来的部分。                                     |

> 🎯 **为什么最后是自回归赢了？** 三个原因：
>
> 1. **训练信号更密集**：自回归每个位置都是监督信号，BERT 只有 15%。同样的数据，GPT 学得更充分。
> 2. **训练和使用天然一致**：GPT 训练时怎么学，推理时就怎么用；BERT 需要一个「微调」环节来弥合差距。
> 3. **生成比理解更通用**：能生成就几乎能做所有任务（问答=生成答案，分类=生成标签，翻译=生成译文），而理解类模型做不到这一点。**「万物皆可生成」这个统一性，是 Decoder-Only 胜出的根本原因。**

##### 补充：还有第三种——序列到序列（Seq2Seq）

T5、BART 用的是**混合方式**：编码器用去噪自编码（双向理解输入），解码器用自回归（单向生成输出）。

```
输入：translate English to German: The house is wonderful.
         ↓
      编码器（双向，理解整句）
         ↓
      解码器（单向，逐个生成）
         ↓
输出：Das Haus ist wunderschön.
```

这就是 2.3 节要讲的 **Encoder-Decoder 架构**的训练方式。

**四个维度的全面转向**（讲义 P21 的总结）：

1. **训练数据多元化**：不再只是自然语言文本，而是自然语言 + 编程代码 + 化学分子式 + 基因序列 + 图像等**多种数据的组合**
2. **训练方式**：从判别式预训练（BERT 为典型）全面转向**生成式预训练**（GPT 为典型）
3. **模型架构**：从双向 Transformer 转向**单向 Transformer**（Decoder-only）
4. **应用方式**：从微调走向更友好的**提示学习**；样本从「必须有一定标注样本」→ 少样本 → **零样本**；工作形式逼近**人机对话**

#### （2）范式的根本转变：In-Context Learning

GPT-3 论文揭示的关键现象：**不需要微调，只要在 Prompt 里给几个例子，模型就能「学会」任务**。

```
微调范式：  任务 → 标注数据 → 训练 → 新模型（每个任务一份）
提示范式：  任务 → 写成 Prompt → 同一个模型（零成本切换）
```

这就是讲义里写的 `Prompt based completion`——模型从「可迁移」变成「**可通用**」。

**一个具体例子**（把「情感分类」教给模型）：

```
【零样本 Zero-shot】不给例子，直接下指令
  文本：Datawhale 的 AI Agent 课程非常棒！
  情感：

【少样本 Few-shot】给几个例子，让模型「照猫画虎」
  文本：这家餐厅的服务太慢了。
  情感：负面

  文本：这个产品质量超出预期。
  情感：正面

  文本：Datawhale 的 AI Agent 课程非常棒！
  情感：

【微调 Fine-tuning】改参数（对比）
  收集 1 万条标注数据 → 训练 → 得到一个专用模型
```

**关键点：三种方式都能完成任务，但成本差了几个数量级。**

| 方式      | 要改参数吗 | 要多少数据      | 换任务成本 | 效果               |
| --------- | ---------- | --------------- | ---------- | ------------------ |
| 微调      | ✅ 要       | 几千~几万条标注 | 重新训练   | 最好（但只能专）   |
| Few-shot  | ❌ 不要     | 3~10 个例子     | 改 Prompt  | 很好               |
| Zero-shot | ❌ 不要     | 0               | 改一句话   | 好（复杂任务会差） |

> 🎯 **为什么 In-Context Learning 这么重要**：它把「适配新任务」的成本从**几万美元的训练**降到了**几行 Prompt**。这是大模型能够作为「通用平台」而非「专用工具」的根本原因——也是 Agent 能够存在的经济基础。

**两个里程碑**

1. **GPT-3（2020）**：证明「规模 + 提示」可行，但不会听指令
2. **ChatGPT / InstructGPT（2022）**：**指令微调（SFT）+ RLHF**，把「续写引擎」调教成「对话助手」

> ⚠️ **一个常被忽略的区别**：GPT-3 和 ChatGPT 的**基座能力差不多**，真正的差异在**后训练（Post-training）**——即 1.6 节的指令微调与 5.2 节的 RLHF。预训练给的是「能力」，后训练给的是「愿意按人的意图使用这些能力」。所以 4.1 节选型时，「模型大小」和「对齐程度」是两个独立维度。

#### （3）大模型时代的范式变化：两条并行路线

这是理解当今 AI 产业格局的关键一张表。大模型带来的不是单点技术改进，而是**整个生产关系的重构**。

**技术范式的迁移：从「各自造轮子」到「中心化基座 + 两端适配」**

| 阶段               | 形态                                                                                                                      | 谁在做                |
| ------------------ | ------------------------------------------------------------------------------------------------------------------------- | --------------------- |
| **过去**           | **个体化 training**：每个用户在每个任务上自建模型，自己完成全部机器学习训练                                               | 每个团队 / 个人       |
| **现在（训练侧）** | 中心节点完成一般化的大规模预训练，提供「接近完成」的模型，再作为**标准模块**进行后训练（指令微调 / 强化学习）适配广泛场景 | 少数大厂 + 下游调优者 |
| **现在（应用侧）** | **预训练 + 提示学习**：不碰参数，靠 Prompt 编排使用能力                                                                   | 所有人                |

于是形成**两条并行路线**：

```
路线一：预训练 + 后训练（造模型）
        预训练 → SFT → RLHF/DPO
        目标：造出一个能力更强、更听话的基座
        成本：百万到亿美元级，少数玩家

路线二：预训练 + 提示学习（用模型）
        上下文学习 / 思维链提示 / 工作流编排 / RAG / 工具调用
        目标：用现有基座解决具体业务问题
        成本：几乎为零，所有人可参与
```

> 🎯 **对开发者的意义**：绝大多数人应该走**路线二**。理解路线一是为了「知道基座的能力边界从哪来、为什么有幻觉、为什么有知识截止日期」，而不是为了自己去预训练一个模型。

**任务范式的统一：从「各自独立」到「统一序列到序列」**

| 过去                                                             | 现在                                            |
| ---------------------------------------------------------------- | ----------------------------------------------- |
| 分类、抽取、翻译、问答、摘要……每个任务一套模型、一套输入输出格式 | 全部转写成**序列到序列**：`输入序列 → 输出序列` |

**这个统一是 Agent 能够存在的前提**。因为任务形式统一了，模型才能用同一套接口处理任意任务，工具调用、多步规划、格式约束才有可能实现。

**后训练侧的关键手段**（讲义 P18 列的「新技能包」）：

- **提示工程**：上下文学习、思维链提示、工作流编排
- **轻量化训练**：LoRA、QLoRA 等参数高效微调

#### （4）能力从量变到质变：涌现能力

**定义**：当模型规模达到一定阈值后，会**突然**展现出在小规模模型中完全不存在或表现不佳的全新能力。

**为什么叫「涌现」而不是「提升」**：因为它是**非线性**的——不是「小模型 30 分、中模型 60 分、大模型 90 分」的平滑提升，而是「小模型接近 0 分、大模型突然 80 分」的跳变。

```
能力表现
   │                        ┌──────  ← 涌现点（突然跃升）
   │                       ╱
   │                      ╱
   │─────────────────────╱        ← 小模型长期接近 0
   └────────────────────────────→ 模型规模
                    ↑
              约 60B 参数
```

**代表性的涌现能力**：

| 能力                      | 说明                     | 为什么重要                     |
| ------------------------- | ------------------------ | ------------------------------ |
| **In-Context Learning**   | 从 Prompt 里的例子学规律 | Agent 能「临时学新工具」的基础 |
| **Chain-of-Thought**      | 分步骤推理               | 复杂任务正确率大幅提升         |
| **Instruction Following** | 理解并执行复杂指令       | 多约束任务的可行性             |
| **多步推理**              | 解决需要多步骤的问题     | 规划能力的来源                 |
| **代码生成与理解**        | 编写和调试代码           | 工具调用的前提                 |

**官方原书（3.3.1）的表述**：链式思考、指令遵循、多步推理、代码生成等能力，「都是在模型参数量达到**数百亿甚至千亿级别**后才显著出现的」。

> 🎯 **对 Agent 开发者的直接含义**：**能力的涌现意味着「选择一个足够大规模的模型」是实现复杂自主决策和规划能力的物质前提**。如果你的 Agent 在规划环节表现很差，先检查基座模型规模是否够——这不是 Prompt 能弥补的。

> ⚠️ **一个学术争议**：有研究认为「涌现」可能是**评估指标的产物**——用不连续的指标（如完全正确率）测量时看起来像跳变，换成连续指标（如 token 级准确率）则可能只是平滑提升。所以「涌现」是否真是相变，目前仍有争论。但**工程上按「规模阈值」来规划是实用的**。

#### （5）大模型的能力版图：三层结构

把大模型所有能力画成一张图，能清楚看到“哪些是天生就会、哪些是规模到才出现、哪些需要外部加持”。

```
                    LLM Capabilities
                          │
    ┌───────────┬────────┴────────┬───────────┐
    │           │                 │           │
 [Basic]    [Emerging]      [Augmented]       │
  基础能力     涌现能力        增强能力         │
```

| 层次                      | 能力大类                           | 具体能力                                        | 怎么得到          |
| ------------------------- | ---------------------------------- | ----------------------------------------------- | ----------------- |
| **Basic**<br>基础能力     | **Comprehension** 理解             | 摘要、多项选择 QA、简化、阅读理解、布尔 QA      | 预训练自然获得    |
|                           | **World knowledge** 世界知识       | Wikipedia QA、多项选择 QA                       | 预训练自然获得    |
|                           | **Multilingual** 多语言            | 翻译、XNLI、跨语言 QA、跨语言任务               | 预训练自然获得    |
|                           | **Coding** 代码                    | Function Calling、API calling                   | 预训练自然获得    |
| **Emerging**<br>涌现能力  | **Reasoning** 推理                 | 算术、符号、逻辑、常识                          | 规模到位才出现    |
|                           | **Instruction following** 指令遵循 | Few-shot、多轮、任务定义                        | 规模 + 指令微调   |
|                           | **In-context learning** 上下文学习 | Completion、Pos/Neg example、分步求解、符号引用 | 规模到位才出现    |
| **Augmented**<br>增强能力 | **Interacting with users** 交互    | 任务分解、分配规划、物理/虚拟动作               | 靠 Agent 架构外挂 |
|                           | **Tool utilization** 工具使用      | 工具规划、知识库利用                            | 靠工具调用外挂    |
|                           | **Self-improvement** 自我改进      | 自我批评、自我精炼                              | 靠反思循环外挂    |

> 🎯 **这张图对做 Agent 的人最重要的一点**：
>
> **Basic 和 Emerging 是“模型自己就能做的”，Augmented 是“必须靠外部系统才能做的”。**
>
> 而 Augmented 那一整列——任务分解、工具规划、知识库利用、自我批评——**恰好就是 Agent 的定义**。所以 Agent 不是让模型变强，而是把模型本来就有的能力**接上外部世界**。
>
> 这也解释了一个常见困惑：“为什么同一个模型，包一层 Agent 框架后好像变聪明了？”——因为它从 Basic+Emerging 跨到了 Augmented。

**四代演进的一句话总结**

```
统计语言模型     → 背下词组合            （记）
神经语言模型     → 学会用向量表示词      （表示）
预训练语言模型   → 学会语言，再适配任务  （迁移）
指令微调         → 把基座调成会听话的助手（听话）
大规模语言模型   → 一个模型做所有任务    （通用）
```

**这一代的代价**

规模换来了通用能力，但也带来了新问题：

| 代价           | 具体表现                          | 对应章节        |
| -------------- | --------------------------------- | --------------- |
| **幻觉**       | 自信地编造不存在的事实            | 5.2 节          |
| **成本**       | 训练百万美元级，推理按 token 计费 | 4.1 节 / 6.5 节 |
| **知识时效性** | 只知道训练截止日期前的信息        | 5.3 节          |
| **不可解释性** | 无法解释为什么给出这个答案        | 5.3 节          |
| **上下文限制** | 「中间丢失」现象                  | 5.3 节          |

> 📌 **一句话**：大模型不是「更好的模型」，而是**用规模和成本换取通用性**的一次范式转换。理解它的代价，才能知道什么时候不该用它。

## 路线 3：现代架构——LLaMA、RoPE、GQA 与 MoE

> 理解开源模型如何在位置编码、注意力、归一化和专家路由上优化 Transformer。

### 12.1 KV Cache：为什么生成会越来越慢

自回归生成时，第一个 token 需要处理完整输入；之后每生成一个 token，理论上只需要计算新 token。但如果每次都重新计算旧 token，会非常浪费。

```text
Prefill：一次处理完整输入，建立 K/V
Decode：每一步只处理新 token，复用历史 K/V
```

KV Cache 保存每层注意力中的 Key 和 Value：

```text
没有 KV Cache：每一步重算整个前缀
有 KV Cache：旧 token 的 K/V 直接复用，只计算新 token
```

**代价**：上下文越长，KV Cache 越大，推理显存越高。因此 MQA、GQA、MLA 都在解决同一个问题：**怎样减少需要缓存的 K/V**。

### 12.2 MQA、GQA：减少 KV Cache

| 方式    | Q 头 | K/V 头   | 特点                     |
| ------- | ---- | -------- | ------------------------ |
| **MHA** | 多个 | 多个     | 质量好，KV Cache 大      |
| **GQA** | 多个 | 少量分组 | 质量和显存的折中         |
| **MQA** | 多个 | 1 组     | Cache 最小，质量可能下降 |

```text
MHA：Q1→K1V1，Q2→K2V2，Q3→K3V3，Q4→K4V4
GQA：Q1,Q2→K1V1；Q3,Q4→K2V2
MQA：Q1,Q2,Q3,Q4→同一组 K/V
```

**选择思路**：

- 追求质量，显存充足 → MHA；
- 通用生产服务 → GQA；
- 极端低延迟、低显存 → MQA。

### 12.3 RMSNorm、SwiGLU、RoPE：LLaMA 之后的标准组件

**RMSNorm**：只用均方根做归一化，不计算均值，计算更简单。

```text
LayerNorm：减均值 + 除标准差
RMSNorm：  只除均方根
```

**SwiGLU**：对传统 FFN 的升级，用门控控制哪些特征通过：

```text
SwiGLU(x) = Swish(xW_gate) ⊙ (xW_up) W_down
```

**RoPE**：通过旋转 Q/K 向量编码位置，使点积天然包含相对位置信息。它是 LLaMA、Qwen 等现代模型的常见位置编码方案。

### 12.4 MoE：总参数很大，但每次只激活少量专家

MoE 将 FFN 拆成多个专家，并由路由器决定每个 token 走哪些专家：

```text
token → Router → Expert 2 + Expert 7 → 输出
```

必须区分：

- **总参数**：所有专家参数之和；
- **激活参数**：当前 token 实际经过的参数。

因此 MoE 可以做到：总容量很大，但单 token 的计算量相对较小。代价是：

- 路由负载不均会造成训练不稳定；
- 专家并行需要 GPU 之间频繁通信；
- 推理显存仍可能需要容纳全部专家权重。

## 路线 4：对齐与推理模型——从会续写到会思考

> 预训练让模型有能力，SFT/RLHF/DPO/GRPO 让模型更会按人类意图工作并进行推理。

### 1.6 指令微调（SFT）：让基座学会听指令

> 📌 本节对应官方原书 3.2.1 节「指令调优的影响」，并补充了 FLAN / InstructGPT 两条路线与训练细节（原书未展开）。

#### （1）解决什么问题：会续写 ≠ 会听话

早期的 GPT 模型（如 GPT-3）主要是**「文本补全」模型**——它们擅长根据前面的文本续写，但**不一定能理解并执行人类的指令**。

```
你输入：总结一下这篇文章
纯预训练模型可能输出：总结一下这本书
                      ↑ 它以为你在「写一个并列句」，而不是「执行一个任务」
```

原因是预训练目标只是「预测下一个词」，**从来没有教过它「指令 → 回答」这个映射**。

#### （2）核心做法：用（指令, 回答）数据做有监督微调

**指令调优（Instruction Tuning）** 是一种微调技术：使用大量**「指令-回答」格式的数据**对预训练模型做进一步训练。经过指令调优后，模型能更好地理解并遵循用户的指令。

```
训练样本格式：

指令：将下面这句话翻译成英文：今天天气很好
回答：The weather is nice today.
```

> 🎯 **我们今天日常工作学习中使用的所有模型（ChatGPT、DeepSeek、Qwen）都是其模型家族中经过指令调优过的模型。** 换句话说，「基座模型」和「你用的模型」之间，差的就是这一步。

#### （3）最直观的对比：提示方式的改变

这是理解指令微调价值最好的例子（官方原书原文）：

**对「文本补全」模型，你必须用少样本提示「教会」它做什么**：

```
这是一段将英文翻译成中文的程序。
英文: Hello
中文: 你好
英文: How are you?
中文:
```

**对「指令调优」模型，你可以直接下达指令**：

```
请将下面的英文翻译成中文：
How are you?
```

> 💡 **这个差别看似只是省了几个 token，实则是交互范式的改变**：前者需要用户「设计模板」来迁就模型，后者让模型来适应人的自然表达。**这是大模型走向大众产品的关键一步**——普通用户不会写 few-shot 模板。

#### （4）两条主要路线

| 路线                   | 代表                                   | 数据怎么来                                                                              | 优点                                        | 缺点                             |
| ---------------------- | -------------------------------------- | --------------------------------------------------------------------------------------- | ------------------------------------------- | -------------------------------- |
| **模板复用现有数据集** | **FLAN**（Wei et al., 2021）           | 把 **62 个 NLP 任务分为 12 类**，每个任务人工构造 **10 个指令模板**，套在现有标注数据上 | 成本低、任务覆盖广，直接提升 zero-shot 能力 | 模板风格人工痕迹重，回答不像真人 |
| **人类演示**           | **InstructGPT**（Ouyang et al., 2022） | 标注员根据指令**亲自撰写**高质量回答（约 **13k 条**）                                   | 质量高、风格像人                            | 贵、慢、难以大规模扩             |

**FLAN 的构造逻辑值得细看**：

```
现有数据集：SNLI（自然语言推理，标签是 蕴含/中立/矛盾）
                ↓ 套上 10 个不同措辞的模板
模板1：前提是「...」，假设是「...」，两者关系是？→ 蕴含
模板2：基于「...」，能推出「...」吗？→ 能
模板3：判断「...」是否支持「...」→ 支持
...
```

同一个标注数据，通过不同模板产生 10 倍训练样本，**且模型学到的是「理解任务」而不是「记住某种问法」**——这正是 zero-shot 泛化能力的来源。

#### （5）数据构造的两个要点

| 要点           | 含义                                               | 反面例子                               |
| -------------- | -------------------------------------------------- | -------------------------------------- |
| **任务数量**   | 决定广度。任务种类越多，模型见过的「任务形式」越多 | 只教翻译 → 模型不会摘要                |
| **任务多样性** | 决定泛化。同一任务要有多种措辞、多种输入格式       | 只教「请翻译」→ 换成「译成英文」就不会 |

> 📌 **一句话**：指令微调不是教模型「知识」，而是教模型「**怎么理解你要它干什么**」。

#### （6）关键发现：大模型效应

FLAN 论文最重要的发现是：**指令微调带来的提升存在明显的「大模型效应」**。

| 模型规模           | 指令微调的效果                           |
| ------------------ | ---------------------------------------- |
| 小模型（< 10B）    | 在**样本外任务**上几乎没有提升，甚至变差 |
| 中等模型（约 10B） | 开始有提升                               |
| 大模型（> 100B）   | 提升显著，zero-shot 能力大幅跃升         |

**为什么？** 因为指令微调本质是「**激活**模型已有的能力」，而不是「**注入**新能力」。小模型本来就没学到足够的语言能力，没什么可激活的。

> ⚠️ **两个阈值不要混淆**
>
> | 现象             | 阈值       | 含义                                                                      |
> | ---------------- | ---------- | ------------------------------------------------------------------------- |
> | **指令微调收益** | 约 **10B** | 模型太小，指令微调在「样本外任务」上几乎没有提升（FLAN 的「大模型效应」） |
> | **涌现能力**     | 约 **60B** | 上下文学习、思维链等能力突然出现                                          |
>
> 即：10B 是「能学会听指令」的门槛，60B 是「会自己推理」的门槛。两者是不同现象，不要混为一谈。

#### （7）SFT 在整个训练流程中的位置

```
第 1 步：预训练（Pre-training）
   海量无标注文本 → 基座模型（会续写，不会听话）
         ↓
第 2 步：SFT / 指令微调（本节）
   （指令, 回答）数据 → SFT 模型（会听话了）        ← 你在这里
         ↓
第 3 步：对齐（RLHF / DPO，见 5.2 节）
   人类偏好数据 → 对齐模型（听话且安全、有用）
```

**三者的分工**：

| 阶段    | 学什么                           | 类比                           |
| ------- | -------------------------------- | ------------------------------ |
| 预训练  | 学**知识**与**语言**             | 读完整个图书馆                 |
| **SFT** | 学**任务格式**与**指令理解**     | 学会「别人问你问题，你要回答」 |
| 对齐    | 学**人类偏好**（有用/诚实/无害） | 学会「什么话该说、怎么说」     |

> 🎯 **SFT 是 RLHF 的第一步**。它把「基座」变成「助手」，后续的对齐只是在这个基础上调风格与安全性。**没有 SFT，RLHF 无从谈起**——你没法对一个还不会听指令的模型做偏好对齐。

#### （8）实践中的 SFT 要点

如果你要自己做 SFT（比如做垂域模型），有几个经验点：

| 要点                         | 说明                                                                                          |
| ---------------------------- | --------------------------------------------------------------------------------------------- |
| **数据质量 > 数量**          | LIMA 论文发现：**1000 条高质量指令数据**就能得到不错的对话模型。1 万条垃圾数据不如 1 千条精品 |
| **答案风格要统一**           | 如果一半回答用敬语、一半用口语，模型会摇摆                                                    |
| **要包含「我不知道」的样本** | 否则模型会倾向于编造（幻觉的成因之一）                                                        |
| **格式要多样**               | 问答、摘要、改写、代码、JSON 输出……覆盖越广，泛化越好                                         |
| **留出评测集**               | 训完要能验证，别只靠肉眼抽查                                                                  |

> 💡 **最常见的失败原因**：不是数据太少，而是**数据里有大量低质/重复/自相矛盾的样本**。SFT 阶段模型学得很快，也学得「很老实」——你给的错，它就记住。

### 5.2 模型幻觉（Hallucination）

**什么是幻觉？**
模型自信地生成了不存在的事实或与输入矛盾的内容。

**两类幻觉**（学界标准二分，引自 Huang et al. 2023 survey）：

**1. 忠实性幻觉（Faithfulness Hallucination）**：输出未忠实反映**给定原文**

- **内在幻觉（Intrinsic）**：与输入直接矛盾
  - 例：输入说"天气晴朗"，输出说"下雨了"
- **外在幻觉（Extrinsic）**：添加了原文没有的信息
  - 例：摘要时凭空补上原文没提的数据

**2. 事实性幻觉（Factualness Hallucination）**：输出不符合**世界事实**

- 例：虚构论文引用、编造历史事件、说鲁迅和周树人是两个人

> 💡 **区分技巧**：忠实性看"有没有照原文说"，事实性看"说的对不对"。一个模型可以很忠实但说错（原文就错），也可以说对但不忠实（超出了原文范围）。
>
> 另一个角度：幻觉并不总是纯负面——它同时是模型**创造性和发散能力**的体现。温度调高时的"胡编"与创意写作的"想象"，底层机制相同，差别只在是否需要事实约束。

**产生原因**：

- 训练数据中的错误和偏见
- 模型的概率性质（生成最可能的续写，而非最真实的）
- 缺乏真实世界的知识更新
- 过度泛化训练模式

**缓解方法**：

**0. 先理解对齐：RLHF 三步流程**

在谈缓解之前，先把 RLHF（Reinforcement Learning from Human Feedback）讲清楚——它是现代大模型“可用”的前提，也是抑制幻觉的主要手段。

```
第一步：SFT（监督微调）
  数据：约 13k 条「指令 + 人工撰写的标准答案」
  产出：SFT 模型（会听指令了）
         ↓
第二步：RM（奖励建模）
  数据：约 33k 条「同一问题的多个答案 + 人工排序」
  做法：训练一个打分模型（InstructGPT 用的是 6B 小模型，便宜且稳定）
        损失：让好答案 y_w 的分数高于差答案 y_l
  产出：RM 奖励模型（会判断“什么样的回答人类喜欢”）
         ↓
第三步：RL（强化学习）
  数据：约 31k 条指令（无需标准答案）
  做法：用 PPO（近端策略优化）让模型生成，RM 打分作为奖励
        约束：同时保留原始语言模型损失，防止模型“跑偏”
  产出：对齐模型（InstructGPT / ChatGPT）
```

**为什么要分三步？** 因为“写出好答案”和“判断好坏”难度不同。让人排序两个答案，比让人凭空写出完美答案容易得多——RM 正是把这种廉价的人类判断能力“蒸馏”进了一个可自动打分的模型，再用来大规模地训练主模型。

**对齐三原则（HHH）**：

- **有用（Helpful）**：真的解决问题
- **诚实（Honest）**：不编造、不确定时承认
- **无害（Harmless）**：不输出有害、违法、歧视内容

> 📌 一个常被忽略的细节：SFT 模型和 RL 模型**初始是同一个**（都从 SFT 模型出发），差别在于 RL 阶段用奖励信号进一步调整了它的偏好。

**1. 训练阶段**

- **高质量数据**：清洗、去重、事实核查
- **RLHF（人类反馈强化学习）**：惩罚幻觉行为
- **DPO 等新方法**：直接用偏好数据优化，无需单独的奖励模型（Llama 3 等采用）
- **对比学习**：区分真实和虚假信息

**2. 推理阶段**

- **RAG（检索增强生成）**：

  ```
  用户问题 → 检索相关文档 → 基于文档生成答案
  ```

  - 提供事实依据，减少编造
  - 可以引用来源，增强可信度

- **思维链 + 自我验证**：

  ```
  1. 生成初步答案
  2. 让模型检查答案的逻辑性
  3. 标注不确定的部分
  ```

- **外部工具调用**：

  - 搜索引擎：获取最新信息
  - 计算器：精确计算
  - 数据库：查询结构化数据
  - API：调用专业服务

- **多模型投票**：

  - 用多个模型生成答案
  - 选择一致性高的结果

**3. 系统设计**

- **置信度评估**：让模型输出不确定性
- **来源引用**：强制要求引用依据
- **人工审核**：关键场景加入人工验证
- **错误反馈循环**：收集错误案例，持续改进

**4. Prompt 技巧**

```
如果你不确定答案，请明确说"我不知道"，不要编造信息。
请仅基于以下文档回答，不要使用文档外的知识。
请在答案中标注你的置信度（高/中/低）。
```

### 12.7 对齐与推理模型路线

把路线图中的技术串起来：

```text
预训练
  ↓
SFT：学会听指令
  ↓
RLHF / DPO：学习人类偏好
  ↓
GRPO / 可验证奖励：强化数学、代码等推理
  ↓
推理时计算：回答前增加思考预算
```

这条路线解释了为什么现代模型逐渐从“聊天模型”发展出：

- 推理模型；
- 工具调用模型；
- Agent 原生模型；
- 可以设置思考预算和推理强度的模型。

## 路线 5：推理部署与模型生态

> 模型训练完成后，还要解决 KV Cache、量化、服务框架、成本、评测和模型替换。

### 12.1 KV Cache：为什么生成会越来越慢

自回归生成时，第一个 token 需要处理完整输入；之后每生成一个 token，理论上只需要计算新 token。但如果每次都重新计算旧 token，会非常浪费。

```text
Prefill：一次处理完整输入，建立 K/V
Decode：每一步只处理新 token，复用历史 K/V
```

KV Cache 保存每层注意力中的 Key 和 Value：

```text
没有 KV Cache：每一步重算整个前缀
有 KV Cache：旧 token 的 K/V 直接复用，只计算新 token
```

**代价**：上下文越长，KV Cache 越大，推理显存越高。因此 MQA、GQA、MLA 都在解决同一个问题：**怎样减少需要缓存的 K/V**。

### 12.5 FlashAttention 与 vLLM：让模型跑得快

**FlashAttention**：不改变注意力结果，只改变计算顺序，减少 GPU 高带宽显存和片上高速缓存之间的数据搬运。

**vLLM / PagedAttention**：像操作系统分页管理内存一样管理 KV Cache：

- 减少显存碎片；
- 支持连续批处理；
- 提高多请求吞吐。

二者解决的问题不同：

| 技术           | 主要优化对象               |
| -------------- | -------------------------- |
| FlashAttention | 单次注意力计算的数据搬运   |
| PagedAttention | 多请求 KV Cache 的显存管理 |

### 12.6 投机解码与量化

**投机解码**：小模型先猜多个 token，大模型一次验证，正确的直接接受。

```text
小模型：我猜「今天 天气 很 好」
大模型：一次验证这 4 个 token
→ 接受正确前缀，拒绝错误部分
```

**量化**：用更低精度表示权重和激活，减少模型体积和显存。

```text
FP16 → INT8 → INT4
精度更低，体积更小，通常需要评测性能损失
```

常见方法：GPTQ、AWQ、GGUF。

> ⚠️ 量化不是“免费压缩”。不同模型、不同任务对量化的敏感度不同，生产前必须在自己的评测集上验证。

**实测显存需求（Qwen2 系列，官方口径）**：

上面是理论估算，下面是实测值。**注意推理和微调是两个量级**：

| 模型                        | 推理显存       | 微调显存      | 说明                           |
| --------------------------- | -------------- | ------------- | ------------------------------ |
| Qwen2-0.5B-Instruct         | 最低 **2.7G**  | 最低 **6G**   | 核显/手机都能跑                |
| Qwen2-1.5B-Instruct         | 最低 **5.2G**  | 最低 **8.5G** | 6G 显存显卡可跑                |
| Qwen2-7B-Instruct           | 最低 **16.7G** | 最低 **20G**  | 需 24G 显卡（3090/4090）       |
| Qwen2-72B-Instruct          | 最低 **143G**  | 最低 **156G** | 需多卡（如 4×A100 80G）        |
| Qwen2-MoE-57B-A14B-Instruct | 最低 **116G**  | 最低 **122G** | MoE 激活少，比同参数稠密模型省 |

> 🔑 **从这张表能读出三个重要结论**：
>
> 1. **微调比推理多约 20%~30% 显存**（要存梯度和优化器状态），很多人低估了这一点
> 2. **MoE 的显存优势很明显**：57B 总参的 MoE 只需 116G，而 72B 稠密模型需要 143G——因为激活参数只有 14B
> 3. **7B 是单卡分水岭**：16.7G 刚好卡在 24G 显卡内，而 72B 直接跳到多卡区间

**硬盘空间要求**（GGUF 量化版本参考）：

| 模型规格                | 体积   | 备注                          |
| ----------------------- | ------ | ----------------------------- |

| qwen2:1.5b              | 935 MB | 笔记本可跑                    |
| qwen2:7b                | 4.4 GB | **性价比甜点，推荐入门**      |
| qwen2:72b               | 41 GB  | 4-bit 量化                    |
| qwen2:72b-instruct-fp16 | 145 GB | 未量化，体积是量化版的 3.5 倍 |

> 💡 **量化收益直观对比**：72B 从 145G（FP16）降到 41G（4-bit），**体积只剩 28%**，而性能损失只有 1-3%（见 3.3 节末）。这就是为什么本地部署几乎总是选量化版。

### 模型生态与选型补充

### 4.1 选型考虑因素

#### （1）先别急着比模型：三步决策流程

很多人选型时直接去比 Benchmark 分数，结果选了个又贵又慢的模型做简单任务。**正确顺序是先缩小范围，再比细节**：

```
第一步：定约束（排除法）
  ① 数据能不能出域？ → 不能 → 只能本地部署 → 范围缩小到开源模型
  ② 预算是多少？     → 有上限 → 先算成本 → 排除超预算的
  ③ 有实时性要求吗？ → 需要低延迟 → 排除大模型/推理模型

第二步：定能力下限（够用就行）
  ④ 任务需要什么能力？ → 分类/抽取 → 小模型够；复杂推理 → 大模型
  ⑤ 上下文要多长？     → 短 → 普通模型；长文档 → 长上下文模型

第三步：在候选里比细节
  ⑥ 跑自己的评测集（见 4.3）→ 这一步最重要，胜过所有榜单
  ⑦ 看生态与稳定性 → 文档、SDK、限流策略、SLA
```

> 🎯 **一句话原则**：**先排除，再比较**。绝大多数人跳过第一步，导致在不需要的模型上花冤枉钱。

#### （2）八个评估维度：什么情况下它才是关键

官方列了八个维度，但没说**哪些情况该重点看哪个**。补上这个判断：

| 维度             | 关键场景                       | 可以妥协的场景         |
| ---------------- | ------------------------------ | ---------------------- |
| **性能与能力**   | 复杂推理、代码、多步任务       | 简单分类、抽取、格式化 |
| **成本**         | 高并发、大规模批处理           | 低频内部工具           |
| **速度（延迟）** | 实时对话、游戏 NPC、语音       | 离线批处理、日报生成   |
| **上下文窗口**   | 长文档分析、代码库理解、长对话 | 单轮短问答             |
| **部署方式**     | 数据敏感（医疗/金融/法务）     | 公开数据处理           |
| **生态与工具链** | 团队要长期维护                 | 一次性脚本             |
| **可微调性**     | 垂直领域、有私有数据           | 通用任务               |
| **安全性**       | 面向公众、涉及合规             | 内部实验               |

**怎么快速验证每个维度**（不要靠猜）：

| 维度   | 快速验证方法                                                   |
| ------ | -------------------------------------------------------------- |
| 性能   | 用你自己的 20 个 case 跑一遍，比看任何榜单都准                 |
| 成本   | 先估算月调用量 × 单价，再看优化空间（见 3.3 节）               |
| 速度   | 实测 P50 / P95 延迟，注意**首 token 时间**和**总时长**是两回事 |
| 上下文 | 实测「塞满后性能是否下降」（中间丢失问题，见 5.3 节）          |
| 生态   | 看 SDK 是否支持流式、工具调用、结构化输出                      |

#### （3）Benchmark 怎么用：看什么、不看什么

**主流公开榜单**：

| 榜单                     | 侧重                     | 适合看什么                       |
| ------------------------ | ------------------------ | -------------------------------- |
| **LMSys Chatbot Arena**  | 人类盲测投票（Elo 排名） | **综合体验**，最接近真实用户感受 |
| **Open LLM Leaderboard** | 开源模型多任务平均分     | 开源模型的横向对比               |
| **MMLU**                 | 57 学科知识问答          | 通用知识广度                     |
| **HumanEval / MBPP**     | 代码生成通过率           | 编码能力                         |
| **GSM8K / MATH**         | 数学推理                 | 推理能力                         |
| **C-Eval / CMMLU**       | 中文综合能力             | **中文场景必看**                 |
| **BFCL**                 | 函数调用准确率           | **Agent 场景必看**               |

**榜单的三个陷阱**：

| 陷阱               | 说明                                      |
| ------------------ | ----------------------------------------- |
| **数据污染**       | 测试集可能进了训练数据，分数虚高          |
| **指标不代表体验** | MMLU 高 ≠ 对话好用；代码通过率高 ≠ 能维护 |
| **榜单会过期**     | 模型迭代极快，三个月前的排名可能完全失效  |

> 🎯 **正确用法**：**用榜单缩小候选范围（前 5 名），用你自己的 case 做最终决定**。榜单告诉你"哪些值得试"，不告诉你"该选哪个"。

#### （4）成本对比：同一任务差 200 倍

这是选型时最容易被低估的维度。**同一个任务，不同模型的月成本可能差两个数量级**：

**场景**：每天 1 万次调用，输入 500 token / 输出 200 token（示意单价，实际以官网为准）

| 模型档位                  | 输入单价<br>(/千 token) | 输出单价<br>(/千 token) | 日成本 | **月成本** |
| ------------------------- | ----------------------- | ----------------------- | ------ | ---------- |
| **顶级闭源**（GPT-4o 级） | $0.018                  | $0.072                  | $234   | **$7,020** |
| **中端**（Qwen-Plus 级）  | $0.0028                 | $0.0084                 | $30.8  | **$924**   |
| **轻量**（Qwen-Turbo 级） | $0.0003                 | $0.0006                 | $2.7   | **$81**    |
| **本地 7B**（折旧+电）    | ≈$0.0001                | ≈$0.0003                | $1.1   | **$33**    |

**最大差距：$7,020 / $33 ≈ 213 倍**

**这个数字的实际含义**：

```
如果你的任务用轻量模型也能做到 90 分（顶级模型 95 分），
  多花 200 倍成本买 5 分提升，通常不值得。

如果任务只有顶级模型能做（如复杂代码重构），
  那 200 倍成本是必要投入。
```

**分层策略**（最实用的省钱方法）：

```
简单请求（70%）→ 轻量模型   → 成本占比 <5%
中等请求（25%）→ 中端模型   → 成本占比 ~20%
困难请求（5%） → 顶级模型   → 成本占比 ~75%
```

> 💡 **路由器（Router）模式**：先用小模型判断"这个问题难不难"，简单问题直接答，难题才升级到大模型。**这是目前性价比最高的方案。**

#### （5）Agent 场景的特殊考量（本书重点）

如果模型是用来做 Agent 的，**除了上面八个维度，还要看四个额外指标**：

| 指标               | 为什么重要                                            | 怎么测                                      |
| ------------------ | ----------------------------------------------------- | ------------------------------------------- |
| **工具调用准确率** | Agent 的核心动作，错了整个流程崩                      | 给 20 个不同工具定义，看它选对+参数对的比率 |
| **指令遵循度**     | 多约束任务（"输出 JSON 且不超过 100 字"）能否同时满足 | 构造 3 个约束叠加的 case                    |
| **长上下文稳定性** | 多轮工具返回后是否还记得最初目标                      | 模拟 10 轮工具调用，看第 10 轮是否跑偏      |
| **格式可靠性**     | JSON 是否合法、有无多余前后缀                         | 跑 100 次统计 `json.loads()` 成功率         |

**为什么这些榜单上没有？** 因为它们需要**多轮交互**才能测出来，而标准 Benchmark 大多是单轮问答。

> ⚠️ **一个实践教训**：很多模型在 MMLU 上分数很高，但做 Agent 时**工具参数经常少个引号**——这类问题只能自己测。**做 Agent 选型，自建评测集不是可选项，是必需项。**

### 4.3 怎么自己判断：建一个最小评测集

> 📌 **前面 4.2 的所有表格都会过期**——模型迭代太快，三个月前的对比可能完全失效。**但方法不会过期。** 这一节讲的是"怎么自己判断"，这比记住任何榜单都有用。

#### （1）为什么必须自建评测

**公开榜单的三个盲区**：

| 盲区             | 说明                                  | 你的任务可能正好踩中 |
| ---------------- | ------------------------------------- | -------------------- |
| **不测你的领域** | MMLU 考的是学科知识，不考你的业务术语 | 医疗/法律/内部黑话   |
| **不测你的格式** | 榜单不关心输出是否合法 JSON           | Agent 工具调用       |
| **不测你的边界** | 榜单不测"文档里没有答案时该说什么"    | RAG 场景             |

> 🎯 **一句实话**：**榜单能告诉你"这模型不差"，但只有你自己的评测能告诉你"这模型能用"。**

#### （2）最小可用评测集：20 个 case 就够起步

不需要一开始就搞几百条。**20 条精心设计的 case 就能筛掉 80% 不合适的模型**。

**case 的四个来源**：

```
① 真实业务样本（最重要）    → 从线上日志/历史工单里抽
② 边界情况                  → 空输入、超长输入、纯符号、混合语言
③ 对抗样本                  → 故意误导的提问、要求它做不该做的事
④ 格式压力                  → 多约束叠加（JSON + 字数 + 必须引用）
```

**一个 case 的结构**（JSON 化，方便批量跑）：

```python
cases = [
    {
        "id": "normal_001",
        "input": "这个产品用了三天就坏了，客服还不理人",
        "check": {
            "must_contain": ["负面"],           # 必须包含
            "must_not_contain": ["正面"],       # 必须不含
            "max_length": 100,                  # 长度约束
        },
        "weight": 1.0,                          # 权重（重要 case 可以设 2.0）
    },
    {
        "id": "edge_001",                       # 边界：文档里没答案
        "input": "根据文档，这款产品的保修期是几年？",
        "context": "（文档内容不涉及保修）",
        "check": {
            "must_contain": ["未找到", "没有提到"],   # 任一命中即可
            "must_not_contain": ["一年", "两年", "三年"],  # 关键：不能编
        },
        "weight": 2.0,                          # 幻觉 case 权重更高
    },
]
```

#### （3）一个可运行的对比脚本

```python
import json
from openai import OpenAI

def make_client(base_url, api_key):
    return OpenAI(base_url=base_url, api_key=api_key)

def run_case(client, model, case):
    """跑单个 case，返回 (是否通过, 输出, 延迟)"""
    import time
    t0 = time.time()
    try:
        resp = client.chat.completions.create(
            model=model,
            messages=[{"role": "user", "content": case["input"]}],
            temperature=0,          # 评测必须低温，排除随机性
            max_tokens=512,
        )
        out = resp.choices[0].message.content
        usage = resp.usage
    except Exception as e:
        return False, f"ERROR: {e}", time.time() - t0, None

    latency = time.time() - t0
    c = case["check"]

    ok = True
    if "must_contain" in c:
        ok &= any(k in out for k in c["must_contain"])
    if "must_not_contain" in c:
        ok &= not any(k in out for k in c["must_not_contain"])
    if "max_length" in c:
        ok &= len(out) <= c["max_length"]

    return ok, out, latency, usage

def evaluate(models, cases):
    """对比多个模型"""
    results = {}
    for name, (client, model_id) in models.items():
        passed, total_w, got_w = 0, 0, 0
        latencies, tokens = [], 0
        fails = []

        for case in cases:
            ok, out, lat, usage = run_case(client, model_id, case)
            w = case.get("weight", 1.0)
            total_w += w
            if ok:
                got_w += w
                passed += 1
            else:
                fails.append((case["id"], out[:80]))
            latencies.append(lat)
            if usage:
                tokens += usage.total_tokens

        latencies.sort()
        results[name] = {
            "加权准确率": f"{got_w/total_w*100:.1f}%",
            "通过数": f"{passed}/{len(cases)}",
            "P50延迟": f"{latencies[len(latencies)//2]:.2f}s",
            "P95延迟": f"{latencies[int(len(latencies)*0.95)]:.2f}s",
            "总token": tokens,
            "失败case": fails[:5],       # 只看前几个失败，便于分析
        }
    return results

# 用法
cases = json.load(open("my_cases.json"))
models = {
    "顶级": (make_client("https://api.openai.com/v1", "sk-xxx"), "gpt-4o"),
    "中端": (make_client("https://dashscope.aliyuncs.com/compatible-mode/v1", "sk-yyy"), "qwen-plus"),
    "轻量": (make_client("https://dashscope.aliyuncs.com/compatible-mode/v1", "sk-yyy"), "qwen-turbo"),
}

for name, r in evaluate(models, cases).items():
    print(f"\n=== {name} ===")
    for k, v in r.items():
        print(f"  {k}: {v}")
```

**输出示例**：

```
=== 顶级 ===
  加权准确率: 96.7%
  通过数: 19/20
  P50延迟: 2.31s
  P95延迟: 4.82s
  失败case: [('edge_003', '根据文档...')]

=== 中端 ===
  加权准确率: 93.3%
  通过数: 18/20
  P50延迟: 0.87s
  P95延迟: 1.65s

=== 轻量 ===
  加权准确率: 76.7%
  通过数: 15/20
  P50延迟: 0.31s
```

> 🎯 **拿到这张表，选型就变成算术题了**：
>
> - 如果 93.3% 已经够用 → 选中端（**延迟还低 2.6 倍**）
> - 如果那 6.7% 的差距会导致业务损失 → 才上顶级
> - 如果只是内部工具 → 轻量的 76.7% 可能也够

#### （4）评测的三个常见错误

| 错误                  | 后果                             | 正确做法                                     |
| --------------------- | -------------------------------- | -------------------------------------------- |
| **温度不为 0**        | 同一 case 每次结果不同，无法对比 | 评测时 `temperature=0`                       |
| **只看准确率**        | 忽略延迟和成本                   | 三个指标一起看                               |
| **case 全是正常样本** | 测不出边界能力                   | 至少 30% 是边界/对抗样本                     |
| **用模型自己评分**    | 自评有偏好偏差                   | 用规则判断（关键词/JSON 合法性），或人工抽检 |

> ⚠️ **关于「用模型当评委」（LLM-as-Judge）**：可以用，但要注意两点——① 同一个模型评自己会偏高；② 评委模型至少要比被测模型强。**最可靠的是规则判断 + 人工抽检 10%。**

### 4.4 换模型的工程实践：别把自己锁死

#### （1）为什么一开始就要考虑「换模型」

模型迭代太快，**今天的最优选择三个月后可能就过时了**。如果代码里到处是 `if model == "gpt-4o"`，换模型就是灾难。

**三个必须抽象的点**：

```
① 调用接口   → 统一用 OpenAI 兼容协议（国内厂商基本都支持）
② 参数映射   → 不同厂商参数名不同，做一层转换
③ 输出解析   → 不要依赖特定格式，用 response_format + 校验
```

#### （2）OpenAI 兼容层：一套代码调所有模型

大多数国内厂商都提供 **OpenAI 兼容端点**，只需改 `base_url` 和 `model`：

```python
from openai import OpenAI

PROVIDERS = {
    "openai": {
        "base_url": "https://api.openai.com/v1",
        "model": "gpt-4o",
        "key_env": "OPENAI_API_KEY",
    },
    "qwen": {
        "base_url": "https://dashscope.aliyuncs.com/compatible-mode/v1",

        "key_env": "DASHSCOPE_API_KEY",
    },
    "deepseek": {
        "base_url": "https://api.deepseek.com",
        "model": "deepseek-chat",
```

#### （3）故障转移：主模型挂了自动切备用

生产环境不能只依赖一家。**简单的降级链**：

```python
import logging

FALLBACK_CHAIN = ["qwen", "deepseek", "zhipu"]   # 按优先级排

def chat_with_fallback(messages, **kwargs):
    last_error = None
    for provider in FALLBACK_CHAIN:
        try:
            client, model = get_client(provider)
            resp = client.chat.completions.create(
                model=model, messages=messages, **kwargs
            )
            if provider != FALLBACK_CHAIN[0]:
                logging.warning(f"降级到 {provider}")
            return resp.choices[0].message.content
        except Exception as e:
            last_error = e
            logging.warning(f"{provider} 失败: {e}，尝试下一个")
            continue
    raise RuntimeError(f"所有模型都失败: {last_error}")
```

**需要注意的降级陷阱**：

| 陷阱               | 说明                                                             |
| ------------------ | ---------------------------------------------------------------- |
| **能力不对等**     | 主模型能做的备用模型可能做不了，降级后要降级处理（如缩短上下文） |
| **输出格式不一致** | 不同模型的 JSON 风格可能不同，解析要容错                         |
| **成本突变**       | 降级到大模型可能导致成本飙升，要监控                             |

#### （4）抽象层要留的三个「钩子」

```python
# ① 模型选择可配置（不要硬编码）
MODEL = os.getenv("LLM_MODEL", "qwen-plus")

# ② 关键参数可覆盖（不同模型最优温度不同）
TEMPERATURE = float(os.getenv("LLM_TEMPERATURE", "0.3"))

# ③ 输出校验可插拔（换模型后格式可能变）
def validate_output(text):
    try:
        return json.loads(text)
    except json.JSONDecodeError:
        # 尝试从文本中提取 JSON 片段（容错）
        import re
        m = re.search(r'\{.*\}', text, re.S)
        if m:
            return json.loads(m.group())
        raise
```

> 🎯 **一句总结**：**选型不是「选一个模型然后一直用」，而是「建一套能随时换模型的架构，然后持续对比」。** 前者会随着模型迭代而过时，后者不会。

## 路线 6：与模型交互——采样、Prompt 与 Token

### Prompt 与 Token 原文补充

### 3.1 采样参数：控制输出风格

#### （1）先理解模型是怎么「选词」的

模型每生成一个词，内部都会算出一个**概率分布**——「下一个词是每个候选词的概率」。

假设模型对下一个词算出的原始分数（logits）是：

```
猫   3.0
狗   2.0
鸟   1.0
鱼   0.5
石头 0.0
```

经过 softmax（2.2 节讲过）变成概率：

```
猫   0.6116   ████████████████████████
狗   0.2250   █████████
鸟   0.0828   ███
鱼   0.0502   ██
石头 0.0304   █
```

**采样参数的作用，就是在这个分布上做手脚**——决定「从哪些词里选」以及「选得多随机」。

**三种「做手脚」的方式**：

| 参数            | 干预方式                 | 一句话                            |
| --------------- | ------------------------ | --------------------------------- |
| **Temperature** | 调整分布的**陡峭程度**   | 让模型更保守或更发散              |
| **Top-k**       | **截断**到前 k 个候选    | 只在最可能的几个词里选            |
| **Top-p**       | **截断**到累积概率达到 p | 只在「占据 90% 概率」的那批词里选 |

#### （2）Temperature（温度）：调整分布的陡峭程度

**公式**：

```
              exp(logits_i / T)
P'(w_i) = ────────────────────────
           Σ exp(logits_j / T)
```

就是把 softmax 里的 `logits` 先除以 T。**T 越小，分布越陡；T 越大，分布越平。**

**用上面的例子实测**（这一步很关键，能直观看到温度的作用）：

| T       | 猫         | 狗     | 鸟     | 鱼     | 石头   |
| ------- | ---------- | ------ | ------ | ------ | ------ |
| **0.1** | **1.0000** | 0.0000 | 0.0000 | 0.0000 | 0.0000 |
| **0.5** | 0.8599     | 0.1164 | 0.0158 | 0.0058 | 0.0021 |
| **1.0** | 0.6116     | 0.2250 | 0.0828 | 0.0502 | 0.0304 |
| **2.0** | 0.4026     | 0.2442 | 0.1481 | 0.1153 | 0.0898 |

**看这张表能读出什么**：

- `T=0.1` → 猫的概率被放大到 **100%**，其他全部趋近 0。**模型几乎必然选猫**
- `T=1.0` → 原始分布，猫 61%，狗 22%
- `T=2.0` → 分布被抹平，猫只剩 40%，连「石头」都有 9%。**模型开始乱选**

> 💡 **一句话理解**：**T 是在「自信」和「发散」之间调旋钮**。T→0 时模型只选最可能的词（贪婪）；T→∞ 时所有词等概率（瞎猜）。

**温度选择建议**：

| 温度          | 效果                                       | 适用场景                                                     |
| ------------- | ------------------------------------------ | ------------------------------------------------------------ |
| **0**         | 完全确定（贪婪解码），同一输入永远同一输出 | 需要可复现：单元测试、数据标注、结构化抽取                   |
| **0 ~ 0.3**   | 精准、确定，重复率高                       | 事实性任务：问答、数据计算、代码生成、法律条文解读、技术文档 |
| **0.3 ~ 0.7** | 平衡、自然                                 | 日常对话、客服、邮件撰写、产品文案                           |
| **0.7 ~ 2**   | 创新、发散                                 | 诗歌创作、故事构思、广告 slogan、头脑风暴                    |
| **> 2**       | 过于随机，输出不连贯                       | ⚠️ 不推荐                                                     |

> ⚠️ **一个常见误解**：`T=0` 在数学上是「除以 0」，实际实现里是**特判成贪婪解码**（直接取 argmax），不是真的做除法。

#### （3）Top-k 采样：只在前 k 个里选

**原理**：把所有候选词按概率排序，**只保留前 k 个**，然后在这 k 个里重新归一化后再采样。

**用同一个例子实测**（T=1.0，k=3）：

```
原始分布排序：
  1. 猫   0.6116
  2. 狗   0.2250
  3. 鸟   0.0828
  ─────────────── ← 截断线（k=3）
  4. 鱼   0.0502   ← 被丢弃
  5. 石头 0.0304   ← 被丢弃
```

**重新归一化**（被保留的 3 个概率之和 = 0.9193，各自除以它）：

| 词       | 原始概率 | 归一化后        |
| -------- | -------- | --------------- |
| 猫       | 0.6116   | **0.6652**      |
| 狗       | 0.2250   | **0.2447**      |
| 鸟       | 0.0828   | **0.0900**      |
| 鱼       | 0.0502   | **0（被截断）** |
| 石头     | 0.0304   | **0（被截断）** |
| **合计** |          | **1.0000 ✓**    |

**Top-k 的问题**：**k 是固定的，但不同位置的分布差异很大**。

```
情况 A：模型很确定（猫 95%）
  k=50 → 保留了 49 个几乎不可能的垃圾候选，浪费了，还可能选中它们

情况 B：模型很犹豫（前 100 个词各 1%）
  k=50 → 只有 50 个候选，累积概率才 50%，多样性被人为压制
```

**这就是 Top-p 要解决的问题。**

#### （4）Top-p 采样（核采样）：按累积概率动态截断

**原理**：按概率从高到低累加，**累积和首次达到或超过 p 就停止**，把累加过程中包含的词组成「核集合（nucleus）」。

**用同一个例子实测**（p=0.9）：

```
累积过程：
  加入 猫(0.6116) → 累积 0.6116   ← 还没到 0.9
  加入 狗(0.2250) → 累积 0.8366   ← 还没到 0.9
  加入 鸟(0.0828) → 累积 0.9193   ← 首次 ≥ 0.9，停止！
  ─────────────────────────────────
  核集合 = {猫, 狗, 鸟}，共 3 个
```

**归一化后**（和 Top-k 结果一样，因为这个例子里刚好都是 3 个）：

| 词  | 概率   |
| --- | ------ |
| 猫  | 0.6652 |
| 狗  | 0.2447 |
| 鸟  | 0.0900 |

**Top-p 的优势：候选数量自适应**

```
情况 A：模型很确定（猫 95%，狗 3%，鸟 1%...）
  p=0.9 → 只累加到猫(95%)就超过 0.9 → 核集合只有 1 个词
        → 相当于自动变成贪婪解码，非常确定

情况 B：模型很犹豫（前 100 个词各 1%）
  p=0.9 → 需要累加 90 个词才达到 0.9 → 核集合有 90 个
        → 保留了丰富的多样性
```

> 🎯 **一句话对比**：**Top-k 是「固定名额」，Top-p 是「固定概率预算」**。预算制天然适应不同情况，所以 Top-p 通常比 Top-k 更好用。

#### （5）三个参数怎么配合：优先级与失效条件

**这是最容易困惑的地方，官方原文说得很清楚**：

**优先级顺序：温度调整 → Top-k → Top-p**

```
原始 logits
    ↓ ① 温度调整（改变整体分布的陡峭程度，不改变候选数量）
调整后的分布
    ↓ ② Top-k（保留概率最高的 k 个）
k 个候选
    ↓ ③ Top-p（从这 k 个里，取累积概率 ≥ p 的最小集合）
最终候选集 → 采样
```

**若同时设置 Top-k 和 Top-p，实际候选集是两者的交集。**

**失效条件（很重要，能省很多调试时间）**：

| 设置      | 后果                                                         |
| --------- | ------------------------------------------------------------ |
| **T = 0** | Top-k 和 Top-p **都变得无关紧要**——最可能的 token 必然被选中 |
| **k = 1** | 温度和 Top-p **都变得无关紧要**——只有 1 个候选通过 Top-k     |

> 💡 **实践建议**：**Top-k 和 Top-p 二选一即可**（推荐 Top-p）。同时设置时是交集，容易导致候选集过小、输出变得呆板。

#### （6）其他常用参数

除了三大采样参数，还有几个高频参数：

| 参数                   | 作用                         | 典型值            | 使用场景                           |
| ---------------------- | ---------------------------- | ----------------- | ---------------------------------- |
| **max_tokens**         | 输出长度上限                 | 512 / 2048        | 控制成本和延迟                     |
| **repetition_penalty** | 重复惩罚：降低已出现词的分数 | 1.1 ~ 1.3         | 防止复读机（> 1 惩罚，= 1 不惩罚） |
| **frequency_penalty**  | 按**出现次数**惩罚           | 0 ~ 1             | 抑制高频词反复出现                 |
| **presence_penalty**   | 按**是否出现过**惩罚         | 0 ~ 1             | 鼓励引入新话题/新词                |
| **stop**               | 停止词列表                   | `["\n\n", "###"]` | 精确控制输出边界                   |
| **seed**               | 随机种子                     | 任意整数          | 让采样可复现（配合 T>0 使用）      |

**`repetition_penalty` vs `frequency_penalty` 的区别**：

```
文本已生成："这个产品很好，很好，很好"

repetition_penalty（通常 > 1，如 1.2）：
  对每个已出现的词，把它的 logits 除以 1.2（正数）或乘以 1.2（负数）
  → 「很好」出现 3 次，每次都被惩罚，但惩罚力度固定

frequency_penalty（0~1）：
  惩罚力度 ∝ 出现次数
  → 「很好」出现 3 次，惩罚 3 倍；其他词出现 1 次，惩罚 1 倍

presence_penalty（0~1）：
  只要出现过就惩罚，不看次数
  → 「很好」和「这个」都被惩罚一次，哪怕前者出现 3 次
```

#### （7）场景 → 参数配置速查表

| 场景                   | temperature | top_p | 其他                                      |
| ---------------------- | ----------- | ----- | ----------------------------------------- |
| **代码生成**           | 0 ~ 0.2     | 0.95  | `frequency_penalty=0`（代码重复是正常的） |
| **结构化抽取（JSON）** | 0           | 1.0   | 配合 `response_format` 强制 JSON          |
| **事实问答 / RAG**     | 0 ~ 0.3     | 0.9   | 提示词要求"仅基于文档回答"                |
| **客服对话**           | 0.3 ~ 0.5   | 0.9   | `max_tokens` 限制长度                     |
| **创意写作**           | 0.8 ~ 1.0   | 0.95  | `presence_penalty=0.3` 鼓励新词           |
| **头脑风暴**           | 1.0 ~ 1.2   | 0.98  | 多跑几次取不同结果                        |
| **数据标注（批量）**   | 0           | 1.0   | 加 `seed` 保证可复现                      |
| **Agent 工具调用**     | 0 ~ 0.3     | 0.9   | ⚠️ 必须低温，否则参数格式容易出错          |

> ⚠️ **Agent 场景特别提醒**：工具调用需要模型输出**精确的函数名和参数格式**。温度高一点就可能导致 JSON 少个引号、参数名拼错——**这是 Agent 不稳定的常见原因之一**。做 Agent 时温度建议 **≤ 0.3**。

#### （8）一个完整的调用示例


### 3.2 提示工程（Prompt Engineering）

#### 三种提示方式

**零样本（Zero-shot）**：直接下指令

```
文本：Datawhale的AI Agent课程非常棒！
情感：
```

**单样本（One-shot）**：给一个示例

```
文本：这家餐厅的服务太慢了。
情感：负面

文本：Datawhale的AI Agent课程非常棒！
情感：
```

**少样本（Few-shot）**：给多个示例，让模型理解得更全面

```
文本：这家餐厅的服务太慢了。
情感：负面

文本：这个产品质量超出预期，物流也很快。
情感：正面

文本：东西还行，就是价格有点贵。
情感：中性

文本：Datawhale的AI Agent课程非常棒！
情感：
```

**三种方式怎么选？**

| 方式          | 何时用                                         | 代价                           |
| ------------- | ---------------------------------------------- | ------------------------------ |
| **Zero-shot** | 任务简单、模型熟悉                             | 最省 token，但边界情况容易跑偏 |
| **One-shot**  | 需要指定**输出格式**                           | 一个示例的成本                 |
| **Few-shot**  | 任务有**微妙的判断标准**（如"混合情感"怎么算） | 每轮都消耗这些 token           |

> 💡 **Few-shot 的价值不只是"教格式"，更是"教边界"**。比如情感分类里「东西还行，就是有点贵」算正面还是中性？给一个示例，模型就知道你的标准了。

#### 高级提示技巧

**1. 角色扮演（Role Prompting）**

```
你现在是一位资深的Python专家，拥有10年开发经验。请解释...
```

明确角色可以激活模型相关的知识和语言风格。

**2. 思维链（Chain-of-Thought, CoT）**

**做法**：在提示末尾加一句「请一步一步地思考并解答」或「Let's think step by step」。

**完整案例**（官方原书的篮球胜率题）：

```
一个篮球队在一个赛季的 80 场比赛中赢了 60%。在接下来的赛季中，
他们打了 15 场比赛，赢了 12 场。两个赛季的总胜率是多少？
请一步一步地思考并解答。
```

**模型输出**：

```
好的，我们来一步步计算。

第一步：计算第一个赛季赢得的比赛数。
80 场 × 60% = 48 场。

第二步：计算两个赛季的总比赛数和总胜利数。
总比赛数 = 80 + 15 = 95 场
总胜利数 = 48 + 12 = 60 场

第三步：计算总胜率。
总胜率 = (60 / 95) × 100% ≈ 63.16%

所以，两个赛季的总胜率约为 63.16%。
```

**为什么 CoT 有效**：

| 原因                   | 说明                                                             |
| ---------------------- | ---------------------------------------------------------------- |
| **给了模型「草稿纸」** | 模型的生成是逐 token 的，中间步骤变成 token 后就成了下一步的输入 |
| **降低单步难度**       | 一步算总胜率容易错，拆成三步每步都简单                           |
| **让错误可定位**       | 哪一步错了能看出来，方便纠正                                     |

**变体**：

| 变体              | 做法                             | 适用               |
| ----------------- | -------------------------------- | ------------------ |
| **Zero-shot CoT** | 只加「Let's think step by step」 | 通用，成本最低     |
| **Few-shot CoT**  | 给几个带推理过程的示例           | 需要特定推理格式时 |
| **CoT + 自验证**  | 推理完再让它检查一遍             | 高准确率要求场景   |

> ⚠️ **什么时候不该用 CoT**：简单任务（如情感分类）用 CoT 反而**增加成本且可能引入噪声**。CoT 主要对**数学、逻辑、多步推理**有效。

**3. 自洽性（Self-Consistency）：多跑几次投票**

**问题**：CoT 虽然好，但**每次采样路径不同，答案可能不同**。一次跑对不代表稳定。

**做法**：同一道题用较高温度跑 N 次（如 5~10 次），然后**对最终答案投票**，取出现最多的那个。

```
题目：...（同一道数学题）

第 1 次 → 63.16%
第 2 次 → 63.16%
第 3 次 → 62.5%    ← 算错了
第 4 次 → 63.16%
第 5 次 → 63.16%
                  ↓ 投票
最终答案：63.16%（4 票 / 5 次）
```

**关键前提**：必须**开启采样**（`temperature > 0`）。如果 `T=0`，每次结果完全一样，投票毫无意义。

**代价**：成本 ×N。所以只在高价值任务上用（如数学推理、关键决策）。

**4. 思维树（Tree of Thoughts, ToT）：探索多条路径**

**CoT 的局限**：一条路走到黑，走错了也不会回头。

**ToT 的做法**：把推理变成**树的搜索**——

```
                    问题
                     │
        ┌────────────┼────────────┐
      思路A         思路B        思路C
        │            │            │
    ┌───┴───┐    ┌──┴──┐      ✗ 评估：不可行，剪枝
   子思路A1 子思路A2 子思路B1 子思路B2
    │        │       │
   ✓可行    ✗剪枝   ✓可行
                     │
                 最终答案
```

**三个关键动作**：

1. **生成**：在每个节点产生多个候选思路
2. **评估**：让模型给每个思路打分（"这个方向可行吗？"）
3. **搜索**：保留高分的继续展开，剪掉低分的（BFS / DFS / 束搜索）

**什么时候值得用 ToT**：任务有**明确的中间评估标准**，且**试错成本高**——如数学证明、复杂规划、代码架构设计。

> ⚠️ **ToT 成本极高**（可能调用模型几十次），日常任务不建议使用。

**四种技巧的关系**（一张图看清）：

```
Zero-shot CoT     → 一条路，走一遍
      ↓ 加多次采样投票
Self-Consistency  → 多条路，走完投票选答案
      ↓ 加中间评估与回溯
Tree of Thoughts  → 多条路，边走边评估，走不通就回头
```

**5. 结构化输出**

让模型输出 JSON 而不是自由文本，**这是工程化的关键一步**——只有结构化才能被程序解析。

```
请以 JSON 格式返回结果：
{
  "sentiment": "positive/negative/neutral",
  "confidence": 0.0-1.0,
  "reason": "..."
}
```

**更可靠的做法：用 API 的 `response_format`**（不靠 Prompt 约束，靠解码约束）：

```python
resp = client.chat.completions.create(
    model="qwen-plus",
    messages=[{"role": "user", "content": "判断情感：这个产品太棒了"}],
    response_format={"type": "json_object"},   # 强制输出 JSON
    temperature=0,
)
```

> 🎯 **为什么这个很重要**：Prompt 里写"请输出 JSON"，模型有概率仍然加个「好的，以下是 JSON：」前缀，导致 `json.loads()` 失败。而 `response_format` 是**解码层面的约束**，能保证输出合法 JSON。**做 Agent 时这是必备的。**

**6. 约束与限制**

- 明确输出长度："用不超过50字回答"
- 指定格式："用项目符号列出"
- 设定边界："仅基于提供的文档回答"
- 明确不知道怎么办：**"如果文档中没有相关信息，请回答『未找到』，不要推测"**

> 💡 **最后这条是减少幻觉最有效的单条 Prompt 技巧**。不给模型"退路"，它就会编。

#### 官方六条工程指南（OpenAI GPT-4 使用指南）

前面讲的都是「技巧」，这六条是**工程原则**。前五条与上文重叠，**第六条是真正容易被忽略的一条**。

| #   | 原则                               | 对应上文                   |
| --- | ---------------------------------- | -------------------------- |
| 1   | **写出清晰的指令**                 | 结构化输出、约束与限制     |
| 2   | **提供参考文本**                   | RAG、设定边界              |
| 3   | **将复杂任务拆分为更简单的子任务** | 工作流编排、Agent 分步规划 |
| 4   | **给模型时间「思考」**             | Chain-of-Thought           |
| 5   | **使用外部工具**                   | 工具调用、计算器、搜索     |
| 6   | **系统地测试变更**                 | ⚠️ **下文详述**             |

**第 6 条为什么最容易被忽略？**

因为 Prompt 看起来像「自然语言」，很多人把它当文档改，改完看一眼效果差不多就上线了。但 Prompt 实际上是**代码**——改一个词就可能让某个边界 case 全面崩盘，而你只测了手边那一个例子。

**正确做法：把 Prompt 当代码管理**

```
1. 建立测试集：收集 20-50 个真实 case（包含正常、边界、对抗样本）
2. 固定预期：为每个 case 写下「合格输出」的判定标准
3. 每次修改后全量重跑：而不是只试你新想到的那个例子
4. 记录版本：prompt_v1 / v2 / v3 + 对应分数
5. 回归防线：新版本不得在旧 case 上退化
```

**一个最小可用的评测脚本骨架**：

```python
cases = [
    {"input": "...", "must_contain": ["退款"], "must_not_contain": ["我不知道"]},
    # ... 更多 case
]

def score(prompt, llm):
    passed = 0
    for c in cases:
        out = llm(prompt.format(**c))
        ok = all(k in out for k in c["must_contain"]) \
             and not any(k in out for k in c["must_not_contain"])
        passed += ok
        if not ok:
            print(f"FAIL: {c['input'][:30]} -> {out[:60]}")
    return passed / len(cases)

for name, p in [("v1", PROMPT_V1), ("v2", PROMPT_V2)]:
    print(name, score(p, call_llm))
```

> 💡 **一个经验法则**：如果一个 Prompt 你已经改到第 5 版还没稳定，问题通常不在 Prompt，而在**任务定义本身模糊**或**缺少外部知识**（该上 RAG 或工具了）。

#### 提示词结构模板（可直接复用）

把前面所有技巧整合成一套可复用的骨架。**好的 Prompt 通常包含六段**：

```markdown
# ① 角色（Role）
你是一位资深的<领域>专家，擅长<具体能力>。

# ② 任务（Task）
你的任务是：<一句话说清楚要做什么>

# ③ 上下文/输入（Context）
<需要模型参考的材料、数据、文档>

# ④ 约束（Constraints）
- 必须：<硬性要求>
- 禁止：<明确不允许的事>
- 不确定时：<该怎么办，如"回答『未找到』">

# ⑤ 输出格式（Format）
<JSON schema / Markdown 结构 / 字数限制>

# ⑥ 示例（Examples，可选）
输入：<示例输入>
输出：<示例输出>
```

**一个真实可用的例子**：

```markdown
# 角色
你是一位严谨的合同审查律师，擅长识别法律风险条款。

# 任务
审查下面的合同条款，找出对我方（甲方）不利的表述。

# 上下文
合同条款：<粘贴条款原文>

# 约束
- 仅基于条款原文分析，不要推测未写明的内容
- 如果条款没有明显风险，明确说明"未发现明显风险"
- 引用原文时用「」标出
- 不要给出法律意见，只做条款分析

# 输出格式
请以 JSON 返回：
{
  "risks": [
    {"clause": "原文片段", "risk": "风险说明", "severity": "high/medium/low"}
  ],
  "summary": "一句话总结"
}
```

> 📌 **模板的价值在于「不漏项」**。新手写 Prompt 常常只写了「任务」，忘了「约束」和「格式」——结果模型自由发挥，输出无法用。

#### 常见失败模式与排查

Prompt 不work 时，按这个清单排查（**按出现频率排序**）：

| #     | 症状                       | 根本原因                    | 解法                                                      |
| ----- | -------------------------- | --------------------------- | --------------------------------------------------------- |
| **1** | 输出格式不对，程序解析失败 | 只在 Prompt 里说"输出 JSON" | 用 `response_format` 强制约束；或加"不要输出任何解释文字" |
| **2** | 模型编造信息               | 没给"不知道"的退路          | 加约束："如果不确定，回答『未找到』"；上 RAG              |
| **3** | 时好时坏，不稳定           | 温度太高                    | 降到 0~0.3；关键任务加 `seed`                             |
| **4** | 忽略部分指令               | 指令太多或有冲突            | 精简到 5 条以内；用编号列表；把最重要的放最后             |
| **5** | 输出太长/太短              | 没约束长度                  | 明确"用不超过 N 字"；或 `max_tokens`                      |
| **6** | 理解错了任务               | 任务描述模糊                | 用"你的任务是：..."句式；给一个示例                       |
| **7** | 用了过时的知识             | 训练数据截止                | 把相关事实直接放进 Prompt（RAG）                          |
| **8** | 中文输出夹杂英文           | 术语没有中文对照            | 明确"全部用中文回答，专业术语首次出现时附英文原文"        |

**排查顺序建议**：

```
① 先检查格式约束（用 response_format 而不是靠 Prompt）
② 再检查温度（降到 0 试试）
③ 再检查任务描述是否模糊（给个示例）
④ 最后才考虑换模型
```

> 🎯 **一个反直觉的事实**：**大部分 Prompt 问题不是「Prompt 写得不好」，而是「任务本身没定义清楚」**。在写 Prompt 之前，先用一句话说清"输入是什么、输出是什么、怎么算对"——如果这三件事你自己说不清，模型更说不清。

### 3.3 分词（Tokenization）

**为什么需要分词？**
计算机只认识数字，必须把文字转成数字序列。

**三种方案对比**：

| 方案               | 优点               | 缺点                 |
| ------------------ | ------------------ | -------------------- |
| 按词分             | 直观               | 词表爆炸、未登录词   |
| 按字符分           | 词表小、无OOV      | 单字符无语义、效率低 |
| **子词分（主流）** | 平衡词表大小和语义 | 需要算法设计         |

**主流分词算法**：

**1. BPE（字节对编码，Byte-Pair Encoding）**

- 使用模型：GPT 系列、RoBERTa
- 工作流程：
  1. 初始化：把所有字符作为基本单元
  2. 迭代合并：找出现最频繁的相邻词元对，合并成新词元
  3. 重复：直到词表达到预定大小（通常 30k-50k）
- 优点：数据驱动，平衡词表大小和语义

**官方原书例子：用 4 个单词的迷你语料手推 BPE**

语料：`{"hug": 1, "pug": 1, "pun": 1, "bun": 1}`，目标词表大小 10。

先拆成字符（`</w>` 表示词尾），然后逐步合并最高频相邻对：

| 轮次    | 最高频词元对 | 频次 | 合并后词表                                             |
| ------- | ------------ | ---- | ------------------------------------------------------ |
| 初始    | —            | —    | `h u g </w>`、`p u g </w>`、`p u n </w>`、`b u n </w>` |
| 第 1 次 | `(u, g)`     | 2    | `h ug </w>`、`p ug </w>`、`p u n </w>`、`b u n </w>`   |
| 第 2 次 | `(ug, </w>)` | 2    | `h ug</w>`、`p ug</w>`、`p u n </w>`、`b u n </w>`     |
| 第 3 次 | `(u, n)`     | 2    | `h ug</w>`、`p ug</w>`、`p un </w>`、`b un </w>`       |
| 第 4 次 | `(un, </w>)` | 2    | `h ug</w>`、`p ug</w>`、`p un</w>`、`b un</w>`         |

**分词效果**：训练后遇到没见过的词 `bug`：

1. 查 `bug` → 不在词表
2. 查 `bu` → 不在词表
3. 查 `b` 和 `ug` → **都在**，于是切分为 `['b', 'ug']`

> 🎯 **这就是子词分词的精髓**：没见过的词也能被拆成见过的片段，**永不 OOV**，同时词表规模可控。

**可运行代码**：

```python
import re, collections

def get_stats(vocab):
    """统计词元对频率"""
    pairs = collections.defaultdict(int)
    for word, freq in vocab.items():
        symbols = word.split()
        for i in range(len(symbols) - 1):
            pairs[symbols[i], symbols[i + 1]] += freq
    return pairs

def merge_vocab(pair, v_in):
    """合并词元对"""
    v_out = {}
    bigram = re.escape(' '.join(pair))
    p = re.compile(r'(?<!\S)' + bigram + r'(?!\S)')
    for word in v_in:
        w_out = p.sub(''.join(pair), word)
        v_out[w_out] = v_in[word]
    return v_out

# 每个词末尾加上 </w> 表示结束，并切分好字符
vocab = {'h u g </w>': 1, 'p u g </w>': 1, 'p u n </w>': 1, 'b u n </w>': 1}

for i in range(4):
    pairs = get_stats(vocab)
    best = max(pairs, key=pairs.get)
    vocab = merge_vocab(best, vocab)
    print(f"第{i+1}次合并: {best} -> {''.join(best)}")
    print(f"新词表: {list(vocab.keys())}\n")
```

输出：

```
第1次合并: ('u', 'g') -> ug
新词表: ['h ug </w>', 'p ug </w>', 'p u n </w>', 'b u n </w>']

第2次合并: ('ug', '</w>') -> ug</w>
新词表: ['h ug</w>', 'p ug</w>', 'p u n </w>', 'b u n </w>']

第3次合并: ('u', 'n') -> un
新词表: ['h ug</w>', 'p ug</w>', 'p un </w>', 'b un </w>']

第4次合并: ('un', '</w>') -> un</w>
新词表: ['h ug</w>', 'p ug</w>', 'p un</w>', 'b un</w>']
```

**2. WordPiece**

- 使用模型：BERT
- 与 BPE 类似，但合并规则基于语言模型似然
- 特殊标记：`##` 表示子词（如 `playing` → `play` + `##ing`）

**3. SentencePiece**

- 使用模型：T5、LLaMA
- 直接在原始文本上操作，不需要预分词
- 支持多语言，对中文等无空格语言更友好
- 包含 BPE 和 Unigram 两种模式

**4. Tiktoken**

- 使用模型：GPT-3.5、GPT-4
- OpenAI 开发的高效分词器
- 基于 BPE，但有特殊优化

**开发者必知**：

- ✅ 上下文窗口是按 Token 数计算的，不是字符数
- ✅ API 按 Token 收费（输入 + 输出）
- ✅ 同样内容在不同语言下 Token 数差异很大
  - 英文：1 token ≈ 0.75 词
  - 中文：1 token ≈ 0.5-1.5 字（取决于分词器）
- ✅ 特殊字符和代码通常需要更多 Token

#### 实用：怎么估算 Token 数

**三种方法，从粗到细**：

**方法 1：经验公式**（快速估算）

| 语言/内容 | 大致比例                   | 例子                               |
| --------- | -------------------------- | ---------------------------------- |
| 英文文本  | 1 token ≈ 4 字符 ≈ 0.75 词 | `Hello world` (11 字符) ≈ 3 tokens |
| 中文文本  | 1 token ≈ 1~1.5 汉字       | `你好世界` (4 字) ≈ 3~4 tokens     |
| 代码      | 1 token ≈ 2~3 字符         | `def foo(x):` (11 字符) ≈ 5 tokens |
| JSON      | 1 token ≈ 2 字符           | 引号和括号很吃 token               |

**方法 2：用 tokenizer 精确算**

```python
# OpenAI 系（tiktoken）
import tiktoken
enc = tiktoken.encoding_for_model("gpt-4o")
print(len(enc.encode("你好，世界！Hello world")))   # 精确 token 数

# HuggingFace 系（Qwen / Llama 等）
from transformers import AutoTokenizer
tok = AutoTokenizer.from_pretrained("Qwen/Qwen2.5-7B-Instruct")
print(len(tok.encode("你好，世界！Hello world")))
```

**方法 3：API 返回的 usage**（最准，且是计费依据）

```python
resp = client.chat.completions.create(...)
print(resp.usage)
# CompletionUsage(prompt_tokens=15, completion_tokens=42, total_tokens=57)
```

#### 一个真实的成本计算

**场景**：做一个客服机器人，每天 1 万次对话，每次输入 500 token（系统提示 + 历史 + 用户问题），输出 200 token。

**假设单价**（示意，实际以厂商官网为准）：

- 输入：¥0.002 / 千 token
- 输出：¥0.006 / 千 token（输出通常贵 2~3 倍）

**每天成本**：

```
输入：10,000 次 × 500 token = 5,000,000 token = 5,000 千 token
     5,000 × ¥0.002 = ¥10

输出：10,000 次 × 200 token = 2,000,000 token = 2,000 千 token
     2,000 × ¥0.006 = ¥12

合计：¥22 / 天 ≈ ¥660 / 月
```

**优化空间**：

| 优化手段                                       | 效果                      |
| ---------------------------------------------- | ------------------------- |
| **精简系统提示**（从 300 → 100 token）         | 输入成本降 40%            |
| **用提示缓存**（重复的系统提示可缓存计费）     | 系统提示部分成本降 50~90% |
| **简单问题用小模型**（如 Qwen-Turbo 而非 Max） | 单价降 5~10 倍            |
| **限制输出长度**（`max_tokens`）               | 输出成本可控              |
| **压缩历史对话**（只保留最近 N 轮 + 摘要）     | 长对话成本不爆炸          |

> ⚠️ **一个常见的成本陷阱**：**多轮对话的历史会不断累积**。第 10 轮时，你要把前 9 轮全部重传一遍——**输入 token 随轮数线性增长**。所以长对话应用必须做「历史压缩」或「摘要替换」，否则成本会失控。

**中英文 token 差异的实际影响**：

```
同一段意思：
  英文："Please summarize the following document in 3 bullet points."
       ≈ 11 tokens
  中文："请用 3 个要点总结下面的文档。"
       ≈ 14 tokens

→ 中文通常比英文多消耗 30%~100% 的 token
→ 同样的上下文窗口，中文能装的内容更少
```

> 💡 **所以中文应用要特别注意**：同样是 128K 上下文，中文实际可用容量可能只有英文的 60%~70%。

## 路线 7：Agent 工程——让模型去做事

> 把模型接上工具、上下文、记忆和环境，形成可运行、可排错的 Agent 系统。

### 5.4 大模型能力的五个层级

判断一个系统「到底有多智能」，可以看它处在哪一层：

| 层级   | 形态                  | 代表                    | 典型应用             |
| ------ | --------------------- | ----------------------- | -------------------- |
| **L1** | Chatbots（对话）      | GPT-4、DeepSeek-V3      | 问答、对话、搜索     |
| **L2** | Reasoners（推理）     | o1、DeepSeek-R1         | 数学、逻辑推理       |
| **L3** | Agents（智能体）      | Operator、Deep Research | 工具调用、操控、探索 |
| **L4** | Innovators（创新）    | —                       | 创新与发明           |
| **L5** | Organizations（组织） | —                       | 组织与管理           |

**主线：语言 → 行动**，从「内容智能」走向「行为智能」，这是迈向通用人工智能的关键纽带。

> 这个阶梯解释了为什么 Agent 会成为焦点：L1、L2 都只是「说得好 / 想得清」，**只有到 L3 才真正「做得了事」**。本书后续章节就是在讲如何把一个 L2 模型搭成 L3 系统。

---

### 垂域、多模态与 Agent 基座补充

通用大模型只是起点。真正落地时会向三个方向延伸——这也是当前产业界最活跃的三条线。

```
                        ┌─→ 垂域大模型   （往「深」走：行业知识）
   通用大模型（基座）───┼─→ 多模态基座   （往「广」走：感知能力）
                        └─→ 智能体基座   （往「动」走：行动能力）
```

### 7.1 垂域大模型：往「深」走

**基本范式**：在通用大模型基础上做领域训练增强，让它懂某个行业的术语、规范和知识。

**四种实现方式**（成本从高到低）：

| 方式                 | 做法                         | 成本 | 效果                     |
| -------------------- | ---------------------------- | ---- | ------------------------ |
| **继续预训练**       | 用领域语料接着预训练         | 最高 | 最深，学到领域语言习惯   |
| **微调（SFT/LoRA）** | 用领域问答对做指令微调       | 中   | 好，能学到回答风格       |
| **提示工程**         | 系统提示词注入领域角色与规则 | 最低 | 快，但受基座能力上限约束 |
| **检索增强（RAG）**  | 外接领域知识库，生成前先检索 | 低   | 好，且知识可随时更新     |

**优势**：专业性强、落地速度快、成本效益高、合规性好（数据不出域）。

**常见领域**：教育、医疗、法律、金融。

> 💡 **实践建议**：绝大多数团队应该从 **RAG + 提示工程** 起步，而不是一上来就微调。微调的收益常被高估，而知识更新成本被严重低估——模型微调后，知识就「冻住」了，而 RAG 换个文档库就能更新。

### 7.2 多模态基座：往「广」走

**核心变化**：交互通道从「文本进、文本出」扩展到「任意模态进、任意模态出」。

```
单模态时代：  文本 ──→ [大语言模型] ──→ 文本

多模态时代：  文本/图像/语音/视频 ──→ [多模态大模型] ──→ 文本/图像/语音/视频
```

**通用工作模式**（三段式）：

```
多模态输入 → 多模态编码器 → 特征融合模块 → 多模态解码器 → 多模态输出
```

**两种主流架构**：

| 架构               | 结构                                | 代表                                             | 特点                                   |
| ------------------ | ----------------------------------- | ------------------------------------------------ | -------------------------------------- |
| **一体化架构**     | 编码器 + 融合 + 解码器端到端训练    | 大多数多模态大模型                               | 融合深，但训练成本高                   |
| **LLM 为中心架构** | 以 LLM 为调度中枢，外挂各类专家模块 | Visual-ChatGPT、HuggingGPT、MM-REACT、LLaVA-Plus | 灵活、易扩展，本质是「用语言调度工具」 |

> 📌 **LLM 为中心架构值得特别注意**：它把 LLM 当成「调度器」而非「全能选手」，用自然语言去调用视觉模型、语音模型、检索器等外部能力。**这已经是 Agent 的雏形了**——区别只在于调度目标是「模态模型」还是「任意工具」。

### 7.3 智能体基座：往「动」走

这是三条延伸线中与本书关系最密切的一条。

**定义**：基于大模型构建，能够**动态指导自身流程和工具使用**，并根据**实时反馈调整**自己操作的系统。

**关键区别：大模型 ≠ 智能体**

|      | 大模型                           | 大模型智能体（系统）                                 |
| ---- | -------------------------------- | ---------------------------------------------------- |
| 本质 | 一个函数：输入 → 输出            | 一个系统：感知 → 决策 → 行动 → 反馈                  |
| 能力 | 长序列处理、思维链推理、意图理解 | 上述能力 + 环境交互 + 持久运行 + 知识更新 + 工具集成 |
| 状态 | 无状态（每次调用独立）           | 有状态（记忆、经验库、迭代演化）                     |

**智能体的三组核心能力**：

1. **环境交互**：感知理解 → 规划决策 → 动作落实
2. **持久运行**：反思优化、迭代演化、安全防护
3. **能力外挂**：知识库/经验库（记忆）、APP/API/函数（工具）

#### ⚠️ 最关键的一个区分：工作流编排 vs 智能体

这是工程落地时最容易混淆、也最影响架构选择的一对概念：

|              | 工作流编排（Workflow）       | 智能体（Agent）                  |
| ------------ | ---------------------------- | -------------------------------- |
| **路径**     | 预定义，人工编排好每一步     | 动态规划，运行时自行决定         |
| **控制权**   | 在开发者手里                 | 在模型手里                       |
| **实现方式** | 常以 Prompt + 代码串联实现   | 常以训练方式拓展能力             |
| **本质**     | 把 AI 视为**可编排的组件**   | 给 AI **更大的自主性和可进化性** |
| **可预测性** | 高（适合生产环境）           | 低（但上限更高）                 |
| **适用场景** | 流程稳定、需审计、要求确定性 | 开放任务、路径未知、需探索       |

> 🎯 **选型原则**（来自 Anthropic《Building Effective Agents》）：
> **能用工作流解决的，就不要用智能体。** 先问「这个问题的最优路径我能不能提前写出来？」——能，就用工作流（便宜、可控、可调试）；不能，才上智能体。
>
> 很多团队一上来就做 Agent，最后发现 90% 的需求其实是确定性工作流。**复杂度是有代价的，而且代价通常由运维和调试承担。**

**为什么智能体现在才可行**：因为它依赖大模型的三项通用能力——

- 长序列处理（能读完多轮工具返回的结果）
- 思维链推理（能规划多步任务）
- 广泛意图理解（能听懂模糊的人类指令）

### 7.4 Agent Loop：模型、工具与上下文

网站路线图用一句话概括了 Agent：**调用模型 → 执行工具 → 把结果写回上下文 → 再调用模型**。它本质上就是一个带退出条件的 `while` 循环。

```python
while not finished:
    response = llm(messages, tools=tools)

    if response.tool_call:
        result = execute_tool(response.tool_call)
        messages.append(response)
        messages.append(result)
    else:
        return response.text
```

**四个步骤**：

1. 调用模型，让模型根据当前目标和上下文决定下一步；
2. 如果模型请求工具，校验工具名和参数；
3. 执行工具，把结果作为新的上下文写回；
4. 再次调用模型，直到模型给出最终答案或达到最大步数。

> 💡 Agent 的“自主性”不是模型凭空产生的，而是来自**循环 + 工具 + 反馈**。没有循环，模型只是一次性问答；没有工具，模型只能生成文字；没有反馈，模型无法根据真实结果修正计划。

### 7.5 上下文增长、压缩与缓存

每转一轮，历史通常都要重新发送：

```text
第 1 轮：系统提示 + 用户问题
第 2 轮：系统提示 + 用户问题 + 工具调用 + 工具结果
第 3 轮：前面全部内容 + 新一轮工具调用
第 4 轮：继续累积
```

因此会出现：

```text
调用轮数增加
→ 上下文变长
→ 输入 token 增加
→ 成本与延迟增加
→ 更容易超过上下文窗口
```

**四种控制方法**：

| 方法             | 做法                                  | 适用场景             |
| ---------------- | ------------------------------------- | -------------------- |
| **历史摘要**     | 把旧对话压缩成几句话                  | 长对话               |
| **工具结果摘要** | 原始网页/日志先压缩，再回填           | 搜索、代码执行       |
| **Prompt Cache** | 重复的系统提示和工具定义缓存          | 多轮 Agent、批量请求 |
| **外部记忆**     | 把长期信息写入文件/数据库，需要时检索 | 跨会话记忆           |

> ⚠️ 压缩不能只按字数截断。要保留：当前目标、已完成步骤、关键事实、失败原因和待办事项；否则 Agent 会“忘记自己为什么走到这里”。

### 7.6 规划：ReAct 与 Plan-and-Execute

规划不是神秘的新模块。它通常就是**模型写进上下文的一段计划**，或者一个专门的计划工具。

**ReAct：边想边做**

```text
Thought → Action → Observation → Thought → Action → ...
```

适合路径不确定、需要根据工具结果动态调整的任务。

**Plan-and-Execute：先计划再执行**

```text
用户目标
  ↓
生成完整计划：1. 搜集资料 2. 对比信息 3. 输出报告
  ↓
执行第 1 步 → 读取结果 → 必要时更新计划
  ↓
执行第 2 步 → 读取结果
  ↓
执行第 3 步 → 输出报告
```

| 方式                 | 优点                   | 缺点                           |
| -------------------- | ---------------------- | ------------------------------ |
| **ReAct**            | 灵活、能根据反馈调整   | 容易绕圈、步骤不可预测         |
| **Plan-and-Execute** | 路径清晰、便于审计     | 初始计划错了，后面可能整体偏离 |
| **混合方式**         | 先列粗计划，每步 ReAct | 工程复杂度更高，但通常更实用   |

### 7.7 记忆：短期与长期

**短期记忆 = 当前上下文**。会话结束后，模型不会自动保留它看到的内容。

**长期记忆 = 外部存储 + 下次检索**：

```text
本轮对话
  ↓ 选择值得保存的信息
文件 / 数据库 / 向量库
  ↓ 下次对话时检索
注入新的上下文
```

**记忆系统的基本流程**：

1. 判断哪些信息值得记忆；
2. 清理隐私、重复和过期内容；
3. 写入文件、数据库或向量库；
4. 新任务开始时检索相关记忆；
5. 让用户能够查看、修改和删除记忆。

> ⚠️ 记忆写错后，错误会持续影响未来任务。因此记忆不是“写进去就完了”，还需要来源、时间戳、置信度和删除机制。

### 7.8 MCP 与 Skills：工具连接与工具说明

| 概念       | 解决的问题                                 |
| ---------- | ------------------------------------------ |
| **MCP**    | 工具、资源如何以统一协议连接到 Agent       |
| **Skills** | 工具的使用说明、流程和领域知识如何按需加载 |

工具接得越多，工具定义越多，每次请求都可能携带大量说明：

```text
连接工具增加
→ 工具 schema 增加
→ 每次请求上下文变长
→ token 成本和模型干扰增加
```

Skills 的思路是：

```text
默认只放技能目录和简短描述
→ 模型判断需要哪个技能
→ 真正使用时再读取完整说明
```

> 📌 MCP 解决的是“怎么接”，Skills 解决的是“怎么用”。两者都不能自动保证工具安全，权限、参数校验和沙箱仍然需要应用层负责。

### 7.9 子 Agent 与失败模式

**子 Agent** 可以理解为：在一个工具里再运行一个独立的 Agent Loop。

| 优点                   | 代价                 |
| ---------------------- | -------------------- |
| 隔离大量中间上下文     | 总调用成本增加       |
| 主 Agent 只接收结论    | 可能丢失细节         |
| 适合并行研究或文件分析 | 调试和权限管理更复杂 |
| 可以使用专用工具       | 需要明确返回格式     |

**常见失败模式**：

| 失败模式           | 常见原因                 | 防护方法                     |
| ------------------ | ------------------------ | ---------------------------- |
| **死循环**         | 没有终止条件或重复检测   | 最大步数、相同调用检测       |
| **编造工具**       | 工具描述和 schema 不清楚 | 完整名称、参数类型和使用时机 |
| **上下文爆炸**     | 工具结果全部原样回填     | 摘要、截断、缓存             |
| **被外部内容带偏** | 网页/文件中包含伪指令    | 工具结果与系统指令隔离       |
| **改错文件**       | 权限、目标和修改范围不清 | 沙箱、diff、测试、人工确认   |
| **计划过度复杂**   | 一开始就规划太多细节     | 粗计划 + 动态调整            |

> 🎯 排查 Agent 时建议先看四件事：**目标是否可验证、工具是否可校验、上下文是否过长、是否有最大步数和回退机制**。

### 5.3 其他重要局限

**1. 知识时效性（Knowledge Cutoff）**

- 只知道训练截止日期前的信息
- 无法获取实时数据（股价、新闻、天气等）
- 解决方案：RAG、工具调用、定期重训练

**2. 数学和逻辑推理能力有限**

- 复杂计算容易出错
- 多步逻辑推理可能断链
- 解决方案：调用计算器、使用思维链、工具增强

**3. 数据偏见（Bias）**

- 反映训练数据中的刻板印象
- 可能产生歧视性输出
- 地域、性别、种族等方面的偏见
- 解决方案：数据清洗、RLHF、偏见检测

**4. 缺乏真实世界理解**

- 不理解物理规律（如重力、因果关系）
- 缺乏常识推理
- 无法真正"理解"概念，只是模式匹配

**5. 上下文长度限制**

- 即使有 128K 上下文，实际有效利用率有限
- "中间丢失"现象：难以关注中间部分的信息
- 长上下文推理成本高

**6. 可解释性差**

- 难以理解模型为何做出某个决策
- 黑盒性质，调试困难
- 解决方案：注意力可视化、探针分析

**7. 安全性问题**

- 可能被诱导生成有害内容
- 越狱（Jailbreak）攻击
- 隐私泄露风险（记忆训练数据）
- 解决方案：安全对齐、内容过滤、红队测试

**8. 资源消耗大**

- 训练成本高（百万美元级别）
- 推理成本高（大模型需要多卡 GPU）
- 环境影响（能耗、碳排放）

### 关键概念速查表

| 概念                     | 一句话解释                                                                   |
| ------------------------ | ---------------------------------------------------------------------------- |
| **Token**                | 模型处理的最小文本单元（可能是词、子词或字符）                               |
| **Embedding**            | 把词转成数字向量的过程                                                       |
| **NNLM**                 | 神经语言模型（2003），用神经网络预测下一个词，词向量是其副产品               |
| **静态词表示**           | Static Representation，同一个词在任何语境下向量都相同（Word2Vec/GloVe）      |
| **上下文相关表示**       | Contextual Representation，同一个词的向量随语境变化（ELMo/BERT/GPT）         |
| **Word2Vec**             | 预测派词嵌入，CBOW（上下文猜中心）/ Skip-gram（中心猜上下文），网络训完就扔  |
| **GloVe**                | 计数派词嵌入，分解全局共现矩阵，使 w_i·w_j ≈ log(X_ij)                       |
| **FastText**             | 子词派词嵌入，把词拆成字符 n-gram 求和，彻底解决 OOV                         |
| **CBOW / Skip-gram**     | Word2Vec 的两种训练架构，前者快、后者对低频词更好                            |
| **Negative Sampling**    | 负采样，不做全词表 softmax，只抽几个负样本，大幅加速训练                     |
| **预训练 + 微调**        | 先在无标注数据上学语言，再在标注数据上学任务的两阶段范式                     |
| **MLM**                  | 掩码语言模型，遮住部分词让模型猜，BERT 的预训练目标                          |
| **In-Context Learning**  | 上下文学习，不改参数只靠 Prompt 里的例子学新任务                             |
| **RLHF**                 | 人类反馈强化学习，把预训练模型对齐成对话助手的关键步骤                       |
| **对齐（Alignment）**    | 让模型愿意按人类意图使用已有能力，与"能力大小"是独立维度                     |
| **特征提取器**           | 只提供表示、不完成任务的角色定位，NNLM 与 Word2Vec 属于这一代                |
| **Attention**            | 用 Q 查 K、按权重取 V 的通用范式；让模型知道哪些位置更重要                   |
| **Q / K / V**            | Query 检索需求 / Key 索引标签 / Value 实际内容，图书馆检索三元组             |
| **注意力权重**           | softmax 后的归一化分数，和为 1，可可视化查看模型关注哪里                     |
| **Cross-Attention**      | 交叉注意力，Q 来自解码器、K/V 来自编码器，Encoder-Decoder 独有               |
| **Self-Attention**       | 句子内部词与词之间的注意力计算                                               |
| **Multi-Head Attention** | 多个注意力头并行工作，捕捉不同关系                                           |
| **Transformer**          | 基于注意力机制的模型架构，现代 LLM 的基础                                    |
| **Encoder-Decoder**      | 编码器理解输入，解码器生成输出                                               |
| **Decoder-Only**         | 只用解码器的架构，GPT 系列采用                                               |
| **Causal Mask**          | 因果掩码，确保只看到之前的词                                                 |
| **Position Encoding**    | 位置编码，让模型知道词的顺序                                                 |
| **Temperature**          | 控制输出随机性的参数（0=确定，>1=随机）                                      |
| **Top-k**                | 只从概率最高的 k 个词中采样                                                  |
| **Top-p**                | 累积概率达到 p 时停止采样（核采样）；固定概率预算，自适应候选数              |
| **采样优先级**           | 温度调整 → Top-k → Top-p；同时设置时取交集                                   |
| **采样失效**             | T=0 时 Top-k/Top-p 失效；k=1 时温度和 Top-p 失效                             |
| **repetition_penalty**   | 重复惩罚，>1 惩罚已出现词，防复读机                                          |
| **presence_penalty**     | 只要出现过就惩罚，鼓励引入新话题                                             |
| **response_format**      | 解码层强制 JSON 输出，比 Prompt 约束可靠                                     |
| **Self-Consistency**     | 多次采样 + 投票，需 temperature>0 才有意义                                   |
| **Tree of Thoughts**     | 树搜索式推理，生成/评估/剪枝，成本极高                                       |
| **Prompt**               | 给模型的指令、示例或上下文                                                   |
| **Zero-shot**            | 不给示例，直接让模型完成任务                                                 |
| **Few-shot**             | 给几个示例，让模型学习模式                                                   |
| **CoT**                  | 思维链，让模型展示推理步骤                                                   |
| **RAG**                  | 检索增强生成，先查资料再回答                                                 |
| **Hallucination**        | 模型编造不存在的事实                                                         |
| **RLHF**                 | 人类反馈强化学习：SFT → 奖励模型 → PPO 三步对齐                              |
| **SFT**                  | 监督微调，用（指令, 回答）数据教会模型听指令                                 |
| **指令微调**             | Instruction Tuning，提升零样本泛化；存在 10B 规模的"大模型效应"              |
| **FLAN**                 | 用 62 个任务的指令模板复用现有数据做微调                                     |
| **奖励模型 RM**          | 给回答打分的模型（常用 6B 小模型），RLHF 第二步产物                          |
| **PPO**                  | 近端策略优化，RLHF 第三步用的强化学习算法                                    |
| **DPO**                  | 直接偏好优化，无需单独奖励模型的 RLHF 简化版（Llama 3 采用）                 |
| **HHH**                  | 对齐三原则：Helpful 有用、Honest 诚实、Harmless 无害                         |
| **后训练**               | Post-training，预训练之后的指令微调与对齐阶段                                |
| **垂域大模型**           | 通用基座 + 领域知识增强（继续预训练/微调/提示/RAG）                          |
| **多模态基座**           | 支持文本/图像/语音/视频进出的模型，分一体化与 LLM 为中心两派                 |
| **工作流编排**           | 预定义路径串联 LLM 与工具，把 AI 当可编排组件                                |
| **智能体（Agent）**      | 自主规划路径、调用工具、根据反馈调整的系统                                   |
| **MoE**                  | 混合专家，用少量激活参数达到大模型性能                                       |
| **能力版图三层**         | Basic（基础）/ Emerging（涌现）/ Augmented（增强）                           |
| **Augmented 能力**       | 交互、工具使用、自我改进——必须靠外部系统才能实现                             |
| **MLA**                  | 多头潜在注意力（DeepSeek-V2），KV cache 省 90%+                              |
| **算法 + 数据 + 算力**   | 预训练三要素，三者任一成瓶颈都会限制效果                                     |
| **去噪自编码**           | Denoising Auto-encoding，挖空句子再补回（BERT 类），双向注意力，不能直接生成 |
| **自回归生成**           | Auto-regressive，接着往下写（GPT 类），单向 + 因果掩码，天然适合生成         |
| **因果掩码**             | Causal Mask，上三角屏蔽未来位置，保证训练与生成一致                          |
| **Seq2Seq 训练**         | 编码器双向理解 + 解码器单向生成（T5/BART）                                   |
| **个体化 training**      | 过去每个团队每个任务自建模型的旧范式                                         |
| **预训练 + 后训练**      | 造模型路线：预训练 → SFT → RLHF/DPO                                          |
| **预训练 + 提示学习**    | 用模型路线：上下文学习 / CoT / 工作流编排                                    |
| **百模大战**             | 截至 2024.4 国内已推出超 305 个大模型                                        |
| **LMSys Arena**          | 人类盲测 Elo 榜单，最接近真实体验                                            |
| **BFCL**                 | 函数调用准确率榜单，Agent 选型必看                                           |
| **分层路由**             | 简单请求走小模型、困难请求走大模型，性价比最高的省钱法                       |
| **LLM-as-Judge**         | 用模型当评委做评测，需注意自评偏差与评委能力下限                             |
| **AWQ / GGUF**           | 两种量化格式，后者专为 llama.cpp / Ollama 生态设计                           |
| **Fine-tuning**          | 在特定数据上继续训练模型                                                     |
| **Quantization**         | 量化，降低模型精度以节省资源                                                 |
| **Context Window**       | 上下文窗口，模型能处理的最大 token 数                                        |
| **Scaling Laws**         | 缩放法则，描述模型性能与规模的关系                                           |
| **前向传播**             | Forward，输入沿网络正向流动逐层变换得到预测                                  |
| **反向传播**             | Backward，用链式法则从损失往回逐层求梯度                                     |
| **损失函数**             | Loss，量化预测与正确答案的差距；语言模型用交叉熵 -log P                      |
| **梯度下降**             | `W ← W - η·梯度`，沿梯度反方向更新以减小损失                                 |
| **学习率**               | η，步长；太大震荡、太小不动，常用 warmup + 余弦衰减                          |
| **AdamW**                | 大模型标配优化器，一阶+二阶动量，每个参数自适应学习率                        |
| **梯度消失/爆炸**        | 链式法则连乘导致梯度趋近 0 或爆炸；用残差/归一化/梯度裁剪缓解                |
| **梯度裁剪**             | 梯度范数超阈值时等比缩小，防爆炸，几乎所有大模型都用                         |
| **zero_grad**            | PyTorch 梯度默认累加，每步必须清空，否则方向错误                             |
| **Emergent Abilities**   | 涌现能力，大模型突然出现的新能力                                             |

### 常见问题 FAQ

### 基础概念类

**Q1: 为什么 Transformer 能取代 RNN？**

A: 三个关键优势：

1. **并行计算**：可以同时处理所有词，训练速度提升数十倍
2. **长距离依赖**：注意力机制可以直接关注任意距离的词，不受序列长度限制
3. **梯度稳定**：避免了 RNN 的梯度消失/爆炸问题

**Q2: Attention 机制为什么有效？**

A: 传统方法把所有信息压缩到固定大小的向量，造成信息瓶颈。Attention 让模型动态选择关注哪些信息，就像人类阅读时会重点关注某些词一样。

**Q3: 为什么需要多头注意力？**

A: 单头注意力只能学习一种关系模式。多头就像多个专家并行工作，有的关注语法，有的关注语义，有的关注指代关系，综合起来理解更全面。

### 实践应用类

**Q4: 上下文窗口越大越好吗？**

A: 不一定，需要权衡：

- ✅ 优点：可以处理更长的文档
- ❌ 缺点：成本更高（Token 计费）、速度更慢、"中间丢失"现象
- 💡 建议：根据实际需求选择，大部分任务 4K-8K 就够用

**Q5: 开源模型和闭源模型怎么选？**

A: 决策树：

```
需要最强性能？ → 是 → GPT-4o / Claude 3.5
              → 否 ↓
数据敏感/需要定制？ → 是 → 开源本地部署
                  → 否 ↓
预算充足？ → 是 → 闭源 API（省心）
         → 否 → 开源模型（省钱）
```

**Q6: 如何减少模型幻觉？**

A: 多层防护策略：

1. **输入层**：提供明确的上下文和约束
2. **处理层**：使用 RAG、思维链、工具调用
3. **输出层**：验证、置信度评估、人工审核
4. **反馈层**：收集错误案例，持续改进

**Q7: Temperature 设置多少合适？**

A: 根据任务类型：

- **0-0.3**：事实性任务（问答、翻译、代码生成）
- **0.5-0.7**：日常对话、文章写作
- **0.8-1.2**：创意写作、头脑风暴
- **> 1.5**：实验性探索（通常不推荐）

**Q8: 如何优化 Token 使用，降低成本？**

A: 实用技巧：

1. **精简 Prompt**：去除冗余描述
2. **使用缓存**：重复的系统提示词可以缓存
3. **选择合适的模型**：简单任务用小模型
4. **流式输出**：及时停止不需要的生成
5. **批量处理**：合并多个请求

### 技术细节类

**Q9: 量化会损失多少性能？**

A: 经验数据：

- **8-bit 量化**：几乎无损（< 1% 性能下降）
- **4-bit 量化**：轻微损失（1-3% 性能下降）
- **3-bit 以下**：明显损失（不推荐生产使用）
- 💡 建议：优先使用 4-bit，性价比最高

**Q10: 本地部署需要什么配置？**

A: 参考配置：

- **7B 模型（4-bit）**：RTX 3060 12GB / M1 Mac 16GB
- **13B 模型（4-bit）**：RTX 3090 24GB / M2 Mac 32GB
- **70B 模型（4-bit）**：A100 40GB × 2 或云端部署
- 💡 提示：优先考虑量化，可以大幅降低硬件要求

**Q11: 如何判断模型是否适合我的任务？**

A: 评估清单：

1. ✅ 在类似任务上的 Benchmark 表现
2. ✅ 支持的语言（中文任务选中文友好的模型）
3. ✅ 上下文长度是否满足需求
4. ✅ 推理速度是否可接受
5. ✅ 成本是否在预算内
6. ✅ 社区生态和文档是否完善

**Q12: Few-shot 示例给多少个合适？**

A: 经验法则：

- **简单任务**：1-3 个示例
- **中等复杂度**：3-5 个示例
- **复杂任务**：5-10 个示例
- ⚠️ 注意：示例过多会消耗大量 Token，且可能过拟合示例模式
- 💡 技巧：示例要有代表性，覆盖不同情况

### 智能体相关（与第七章配套）

**Q13: 工作流和 Agent 到底怎么选？**

A: 先问自己一个问题：**「这个任务的最优路径，我能不能提前写出来？」**

| 你的情况                                       | 选什么                         |
| ---------------------------------------------- | ------------------------------ |
| 能写出固定步骤（如：先查库→再格式化→最后发送） | **工作流**。便宜、可控、可调试 |
| 步骤数量固定但内容需模型判断                   | **工作流 + 局部 LLM 节点**     |
| 路径取决于中间结果，无法预先枚举               | **Agent**（带工具调用与循环）  |
| 只是需求模糊，实际有固定流程                   | **先做工作流**，不要上 Agent   |

**判断口诀**：

```
需求稳定 + 要审计 + 要省钱  → 工作流
任务开放 + 路径未知 + 可容错 → Agent
```

> ⚠️ **最常见的错误是过度设计**。很多团队一上来就做 Agent，最后发现 90% 的需求其实是确定性工作流。**Agent 的复杂度代价，最终由运维和调试承担。**

**Q14: 为什么我的 Agent 跑几步就偏了？**

A: 这不是模型「笨」，而是四个具体原因，按排查顺序：

**1. 目标没有可验证的终点**（最常见）

- ❌ “帮我调研一下这个行业” —— 什么算调研完？
- ✅ “找出 5 家竞品，输出表格：名称 / 融资阶段 / 核心产品”
- 没有终止条件，Agent 就会无限游走

**2. 工具描述太差**

- ❌ `search(query)` —— 模型不知道什么时候该用
- ✅ `search_web(query: str) -> list[dict]`：当需要**实时信息或训练数据之外的事实**时使用；返回标题+摘要+链接
- **工具的描述就是它的 Prompt**，写得不清楚模型就不会用对

**3. 上下文被垃圾填满**

- 每轮工具返回的原始内容全塞进去，很快就被噪音淹没
- 解法：工具返回**先摘要再入上下文**；只保留与当前子目标相关的部分

**4. 没有反思与回退机制**

- 错了就一路错下去
- 解法：关键节点加**自检**（“当前结果是否满足目标？不满足则回退到哪一步？”），或限制最大步数

> 💡 **一条实用原则**：Agent 跑偏时，**先加约束，不要换模型**。90% 的跑偏问题来自任务定义模糊和工具描述不清，而不是模型能力不够。

**Q15: RAG 和长上下文怎么选？**

A: 现在模型动辄 128K-1M 上下文，很多人以为 RAG 要过时了。实际上两者解决的问题不同：

|            | 长上下文                       | RAG                      |
| ---------- | ------------------------------ | ------------------------ |
| **适合**   | 一次性、少量文档的深度分析     | 大规模知识库、需持续更新 |
| **成本**   | 每次调用都按全部 token 计费 💰 | 只传检索到的片段 ✅       |
| **更新**   | 换文档就重新传                 | 换索引即可               |
| **精度**   | 有“中间丢失”现象，中段易被忽略 | 检索精准时更可靠         |
| **可溯源** | 难                             | 易（可标出处）           |

**决策建议**：

- 文档总量 **< 20 页**且一次性分析 → **直接塞长上下文**，别搭 RAG
- 知识库 **持续增长 / 需引用来源 / 有成本压力** → **上 RAG**
- **两者结合**：RAG 检索出候选 → 放进长上下文做深度推理（当前最佳实践）

> 📌 **一个常被忽视的点**：长上下文的“中间丢失”（Lost in the Middle）意味着——**关键信息放在开头或结尾，效果比放中间好**。这个技巧比换模型便宜得多。

### 前沿趋势与展望

### 🚀 技术演进方向

**1. 更长的上下文**

- 从 4K → 128K → 1M+ tokens
- 技术：RoPE、ALiBi、长度外推
- 应用：处理整本书、完整代码库

**2. 多模态融合**

- 文本 + 图像 + 音频 + 视频
- 代表：GPT-4V、Gemini、Qwen-VL
- 趋势：Any-to-Any 模型

**3. 混合专家架构（MoE）**

- 用更少激活参数达到更好性能
- 代表：Mixtral、**DeepSeek-V2/V3**（V3 为 671B 总参 / 37B 激活）
- 优势：推理成本低，性能强
- 配套创新：**MLA**（多头潜在注意力，KV cache 省 90%）、无辅助损失负载均衡、多 Token 预测、FP8 训练

**4. 小模型的崛起**

- 1B-7B 模型性能快速提升
- 边缘部署、端侧 AI
- 代表：Qwen2.5-0.5B、Phi-3

**5. 推理时计算**

- 不只是预训练规模，推理时也要"思考"
- 代表：OpenAI o1、DeepSeek-R1
- 突破：数学、编程等复杂推理任务

**6. Agent 原生模型**

- 专门为 Agent 任务优化
- 内置工具调用、规划能力
- 多轮交互、记忆管理

**7. 训练范式的收敛**

- 主流配方已基本稳定：**预训练 → SFT → 偏好对齐（RLHF / DPO）**
- 差异主要在数据质量、算力效率与对齐细节
- 新方向：推理时计算（Test-time Compute）把"思考"从训练转移到推理

**8. 能力阶梯的上移**

- L1 Chatbots → L2 Reasoners（o1/R1）→ **L3 Agents**（Operator/Deep Research）
- 当前竞争焦点正从 L2 转向 L3：从"内容智能"到"行为智能"

### 写在最后

### 🎓 核心要点回顾

大语言模型是智能体的"大脑"，理解它的工作原理是构建可靠、高效智能体的基础。通过本章学习，你应该记住：

**技术层面**

- ✅ Transformer 是现代 LLM 的基石，注意力机制是核心
- ✅ Decoder-Only 架构主导了生成式 AI
- ✅ 提示工程是控制模型行为的关键技能
- ✅ 模型选择需要权衡性能、成本、速度等多个因素

**实践层面**

- ✅ 模型不是万能的，有明确的局限性（幻觉、时效性、推理能力等）
- ✅ RAG、工具调用、思维链等技术可以增强模型能力
- ✅ 量化、优化等技术可以降低部署成本
- ✅ 持续学习和实践是掌握 LLM 的唯一途径

**哲学层面**

- 🤔 LLM 是强大的模式匹配器，但不是真正的"理解"
- 🤔 技术是中性的，关键在于如何使用
- 🤔 人机协作，而非人机对抗，才是未来方向
